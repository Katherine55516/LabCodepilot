# 回归轮次失败归因规范

面向「一轮回归里挂掉的用例，为什么挂」的判定。产出**建议**，不是结论——人工据此决定下一步。

## 分类（四选一，穷尽可行动方向）

| 分类 | 判据 | 典型证据 |
|------|------|----------|
| `产品缺陷` | 被测应用自身行为与预期不符 | 断言失败且实际结果指向业务逻辑错误；接口返回 5xx / 错误业务码；数据未按预期写入 |
| `测试用例问题` | 用例本身过时或写错 | 预期与当前 PRD 不一致；选择器/断言依赖了已改版的实现细节；前置数据假设不成立 |
| `环境问题` | 与被测代码无关的外部因素 | 被测地址不可达、超时、鉴权/证书失效、依赖服务不可用、`blocked` 状态 |
| `疑似 flaky` | 同一版本下结果不稳定 | 跨轮结果反复翻转（本轮失败但近若干轮多次通过）；错误信息指向竞态/等待不足 |

## 判定原则

1. **只用给定证据**：实际结果（`actual`）、错误（`error`）、关键接口（`api`）、跨轮历史。禁止臆造未提供的信息。
2. **跨轮历史是重要输入**：连续多轮失败 → 强烈指向 `产品缺陷` 或 `测试用例问题`，**不要**判 `疑似 flaky`；跨轮反复翻转 → 才考虑 `疑似 flaky`。
3. **`疑似 flaky` 是候选不是定论**：跨轮翻转可能只是版本在变。理由里要写明「需同版本连跑复核」。
4. **`blocked` 一律归 `环境问题`**，除非错误明确指向应用崩溃。
5. **不下修复方案**：`act` 只写下一步动作（转缺陷跟踪 / 复核并更新用例 / 检查环境 / 同版本连跑复核），不写「改哪行代码」「什么时候发版」。

## 输出格式

对**每一条**失败用例输出一行，一行一条，按给定顺序：

```
@@VERDICT {"id":"TC-004","cls":"产品缺陷","act":"生成结构化缺陷并跟踪修复","why":"连续 4 轮失败：会话超时后未跳转登录页，接口 401 但页面无提示"}
```

- `id`：用例在本轮执行结果里的 id，原样照抄。
- `cls`：必须是上表四个分类之一，**不得自创**。
- `act`：一句话动作建议。
- `why`：一句话理由，引用真实证据；内层引用一律用中文引号「」。

**只读不写**：禁止修改任何文件——平台按你的输出行落盘。输出完后自检行数是否等于失败用例数。
