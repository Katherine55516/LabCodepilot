# 冒烟测试规范（轻量主流程验证）

**目标**：仅验证被测模块的**主流程是否走得通**。边界值、异常输入、权限、并发等非主流程场景**本次一律不覆盖**——不是遗漏，是刻意的范围裁剪。

> 本规范用于测试工作台的「冒烟测试」任务形态。与功能测试（八维覆盖的结构化用例）、回归测试（发版必跑的沉淀用例库）是三种并列形态，规则互不套用。

---

## 0. 与功能测试的边界（读代码/写 prompt 前必知）

| 维度 | 功能测试 | **冒烟测试** |
|---|---|---|
| 回答的问题 | 新功能对不对 | **主流程通不通** |
| 用例形态 | 12 列结构化用例，操作↔预期 1:1 | **轻场景**：只有「验证目标 + 预期结果」，**不含操作步骤** |
| 执行方式 | 按用例步骤逐步操作 | **自主探索**：自行找路径达成验证目标 |
| 覆盖面 | 正向/异常/边界/状态/权限/业务规则/数据一致性/体验 八类 | **仅主流程正向路径** |
| 结论口径 | 双口径通过率 + 回归集红线 | **是否通过冒烟 / 是否具备进一步测试的条件** |

**范围铁律**：用户给的场景写的是「验证什么」，不是「怎么点」。**不要**因为场景没写步骤就去补边界用例、异常分支、权限校验——那是功能测试的活。冒烟只回答"主流程能不能走通"。

---

## 1. 全局规则（必须遵守）

### 1.1 测试数据可识别

凡需新建的数据，**统一使用平台下发的前缀**（形如 `冒烟测试_20260730_`，在执行提示里给出）。例：新建机构名写 `冒烟测试_20260730_机构A`。

目的：便于回查与清理，也是下面「数据安全」的锚点——没有前缀就无法区分哪些数据是本轮造的。

### 1.2 数据安全（最高优先级）

**所有写操作（新建、修改、状态变更、删除）只能针对本次测试自己新建的数据**（即带上述前缀的数据）。

**严禁操作任何存量数据 / 他人数据**：
- 需要"任选一条记录"做修改/删除/状态切换时，**必须先自己新建一条**，再对它操作；
- 列表里已有的记录一律**只读**（可用于验证"查询能查到已有数据"这类只读场景）；
- 拿不准某条数据是不是自己造的 → 当作存量数据，不碰。

违反本条的破坏不可逆，优先级高于"把场景跑完"——**宁可把场景判 `blocked` 并说明原因，也不动存量数据**。

### 1.3 自主执行

你自行探索页面完成每个场景。操作前先用 `browser_snapshot` 观察真实页面结构再定位元素，**不要凭猜测点击**。

进入模块的路径由平台在执行提示里给出（「目标模块入口」）；若按该路径进不去，先用 `browser_snapshot` 找等价入口，仍找不到再判 `blocked` 并说明。

### 1.4 判定原则

每个场景都要**对照「预期结果」判定**，而不是"点完了就算成功"。

判定依据必须是**能在页面上被观察到的事实**：提示文案、列表行的增减、详情页字段内容、状态标识变化、URL 变化等。观察不到就不能判 `pass`。

### 1.5 失败不中断

某场景失败时：
1. 如实记录（现象 + 实际 vs 预期 + 截图）；
2. **跳过依赖它的后续场景**（判 `blocked`，注明"依赖场景 X 未通过"）；
3. **继续执行其余可独立进行的场景**；
4. 最后统一汇报。

**唯一例外**是登录态整体失效（整站进不去）——此时裸写
`@@AUTH_INVALID {"reason":"login_state_invalid"}` 后立即停止全部工具调用与文字输出；
当前与剩余场景不再产出 `@@RESULT`，不做收尾总结，由平台直接跳过冒烟报告并通知用户。
个别页面权限不足或单个接口偶发 401 不属于整站登录态失效，不得触发该信号。

### 1.6 截图规范

每个场景的关键状态都截图留证。失败场景额外补一张现场截图。截图落到平台指定的证据目录（执行提示里给出），文件名与场景 id 对应。

### 1.7 截图稳定性

截图用 `fullPage: false`、禁用动画、设置 timeout。若截图挂起，先关闭页面重置连接再重试一次；仍失败则跳过截图继续执行（**不要因为截图失败就中断整个场景的判定**）。

### 1.8 顺带记录体验问题

执行过程中观察到的**非功能性**问题（响应慢、提示不清、按钮点了没反馈、状态不同步、布局错乱等），按执行提示里的 `@@OBSERVATION` 格式顺手记一条。

**与四态判定正交**：体验观察**不影响** pass/fail、不计入通过率、不产生 Bug。它是"顺手记下的瑕疵"，不是缺陷判定——不要因为发现体验问题就把一个功能正常的场景判 `fail`。

---

## 2. 四态判定

沿用统一口径：

- `pass`：预期结果完全出现（有可观察证据）；
- `fail`：预期明确未出现且可复现（疑似应用缺陷；保留事实，不放水、不给修复方案）；
- `partial`：部分满足 / 场景被部分跳过；
- `blocked`：前置条件、路径、登录态无法建立，或依赖的前序场景已失败——**不是应用 bug**。

冒烟特有的 `blocked` 情形：依赖场景失败（§1.5）、模块入口进不去（§1.3）、为守数据安全而放弃操作（§1.2）。

---

## 3. 交付：冒烟报告结构

报告必须包含以下五节，顺序固定：

1. **测试环境与执行时间** —— 系统、环境、被测地址、执行时间、数据前缀；
2. **场景结果表** —— `| 场景 | 验证目标 | 预期 | 实际 | 结论 | 截图 |`，与场景一一对应，不多不少；
3. **Bug 清单** —— 结构化列出：编号 / 标题 / 严重级别（致命·严重·一般·建议）/ 关联场景 / 实际 vs 预期 / 证据；仅 `fail` 场景产出 Bug；
4. **奇怪交互 / 体验问题** —— §1.8 记录的非功能观察，逐条列出（无则写"无"）；
5. **整体结论** —— **主流程是否通过冒烟、是否具备进一步测试的条件**。存在 `fail` 即判"未通过"，并说明卡在哪个主流程环节。

**结论口径铁律**：冒烟报告**不出**需求覆盖矩阵、不出双口径通过率、不出回归集红线（冒烟没有这些口径）。结论只回答两件事：主流程通不通、能不能进入下一阶段测试。

**QA 边界**（沿用平台统一纪律）：报告只陈述事实与分类，**禁止**写 bug 修复方案 / 改哪行代码 / 发布与否 / 优先级 / 指派责任人；不向用户提问、不留 TBD 占位。
