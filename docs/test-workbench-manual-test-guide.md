# 「测试」workbench — C 类手动测试指南

> A 类(lib 纯逻辑 + 文件系统类 API)、B 类(DB CRUD + 路由守卫)已**全部自动化**,共 **151 个测试全绿**。
> C 类是**无法有意义自动化**的部分 —— UI 交互、4 步 AI flow、Playwright 真实浏览器执行、打包态特有逻辑。本指南供你登录打包版后照着测。
>
> 相关:[QA 测试报告](test-workbench-qa-report.md)

---

## 为什么这部分要手动测

| 原因 | 涉及 |
|---|---|
| **非确定性**:LLM 每次输出不同,无法写确定性断言 | 4 步 AI flow、缺陷报告、对话修订 |
| **需真实登录态**:dev 无用户体系,managed 模型/账号下发为空 | 模型选择、测试账号、执行预登录 |
| **需真实浏览器**:Playwright 驱动真实页面,证据是真实截图/录像 | 执行阶段、证据采集 |
| **重 UI 交互**:状态机/SSE 流式渲染/拖拽/弹窗,E2E 成本高且依赖真实数据 | 整个 InlineTestingPanel |

## 测试环境准备

1. **登录**:打开 `/Applications/AI Native Lab.app`(已是含全部修复的最终包),完成登录。
2. **测试项目**:准备一个真实项目目录,建议:
   - 有 `docs/` 或 README 里的需求描述(给需求分析步用);
   - 有一个可访问的前端地址(给执行步用,如本地起的被测应用)。
3. **(可选)测试账号**:进 `设置 · 测试账号`,为该项目配 local/SIT 环境(前端/接口地址 + 账号),用「获取登录态」抓 storageState。配了执行步才能预登录跑。

> 提示:纯 UI 交互(C1)在 `npm run dev`(localhost:3000)也能测大部分(不需登录),但涉及真实 AI/账号的(C2–C6)必须用打包登录版。dev 的 DB 已随本次 `npm rebuild better-sqlite3` 修好,可正常起。

## C2. 4 步 AI flow 端到端(需真实 AI + 登录)

进入一个任务的「流程」,选模型,依次:

| 步 | 操作 | 预期产物 / 现象 |
|---|---|---|
| 需求分析 | 点「运行」 | 对话流式输出;产 `AI_LabTest/requirements/{任务}-需求.md`;步状态→「待批准」 |
| (批准) | 点「批准」 | 进入用例步 |
| 用例设计 | 自动/点运行 | 产 `AI_LabTest/testCase/.data/{任务}.cases.json`;用例阶段卡可展开、可编辑(弹窗)、可改 oracle/验证性质;→「待批准」 |
| (批准) | 点「批准」 | **自动链**:执行 + 报告自动接着跑 |
| 测试执行 | 自动 | AI 经 Playwright 逐条跑,对话里出 `▶ 用例 N/总数` + 工具调用;每条留 `@@RESULT` |
| 测试报告 | 自动 | 产 `{任务}-{env}.run.json` + `{任务}-{env}.md`;报告页出四态 + 通过率 + 用例表 |

**重点验证**:
- 需求/用例两步是**人工门控**(待批准才进下一步);执行/报告是**自动链**。
- 执行步四态计数(pass/fail/partial/blocked)由**平台代码归约**(A 类已自动化验证逻辑),报告显示的应与 run.json 一致。
- 「追加指令」(composer 输入喂下一步) vs 「修订」(改当前产物)按钮区分正确。

## C3. 报告「功能验证通过率」口径(H1 重点回归)

> 这是本轮修复的最严重 bug,务必端到端确认。

1. 造一个**含回归基线用例**的任务:用例设计时,让部分用例 `verification=回归基线`(oracle=现状锁定),部分 `功能验证`(oracle=PRD/产品确认)。
2. 跑执行 + 报告。
3. 打开报告,看概要的 **「功能验证通过率」**:
   - ✅ 正确:分母**只算功能验证用例**,回归基线不计入(例:7 功能验证 5 pass → 71%,而不是把 3 个全 pass 的回归基线也算进去)。
   - ✅ **全是回归基线**时显示 **N/A(仅锁现状)**,**绝不能显示 100%**。
   - 对比「执行通过率(参考)」= 全部 pass / 全部用例(含回归基线)。
4. 历史报告(报告浏览器里打开旧报告)的功能验证通过率也应正确(M6 修复了持久化侧)。

**若看到全回归基线报 100%,或功能验证率把回归基线算进分母 → H1 回归,请反馈。**(自动化侧 `funcPassRateStr` 已锁,但端到端是最终确认。)

## C5. Playwright MCP 真实浏览器执行

> 仅执行步注入 Playwright MCP,且**真实效果只有真跑浏览器才能验**(A 类只验了纯 fs 的证据收口逻辑)。

1. 配好测试账号(含 storageState 登录态)+ 被测前端地址。
2. 跑执行步,观察:
   - AI 是否真的打开浏览器、逐条操作(navigate/click/type/snapshot)。
   - 截图/录像是否落到 `AI_LabTest/report/_evidence/{任务}-{env}/`(证据收口 + chdir 垫片的真实效果)。
   - 预登录是否生效(storageState 注入后 AI 开跑即已登录,不用再登)。
3. 环境/连接问题(地址不可达)应判 **blocked**(非应用 bug);401 大面积出现应触发**熔断**提示(run.json circuitBroken → 报告红 banner)。

## C6. 打包态特有逻辑

| 点 | 怎么验 |
|---|---|
| 随包浏览器 | 打包版执行步用随包的 `chromium_headless_shell`(不依赖本机 ~/.cache/ms-playwright);断网装一台干净机器跑能成功即证明 |
| 规则 fallback | 打包态 `outputFileTracingExcludes` 剥掉 `**/*.md`,`loadRule` 读不到 → 用各 prompt 内置精简规则(产物质量可能略降);对比 dev(全量规则)与打包版(精简)的产出 |
| 模型/账号下发 | 登录后模型下拉应有 managed 模型(dev 为空);测试账号下发配置可用 |

## 附录 A:用 chrome-devtools / CDP 验证 UI(开发者向)

按项目 CLAUDE.md 的 UI 验证纪律:
```bash
npm run dev                      # localhost:3000 (DB 已修好可正常起)
```
用 chrome-devtools MCP 打开对应页面 → 截图确认渲染 → `read_console_messages` 查无报错 → 模拟点击/输入验证交互。dev 无登录,涉及真实 AI 的步会停在 `No API credentials`,可按 CLAUDE.md 用 CDP 注入 `fetch` 拦截返回 mock SSE(text/tool_use/@@RESULT)来验证渲染逻辑(历史上就是这么验流程/报告/对比视图的)。

## 附录 B:给 workbench 写 Playwright E2E(开发者向)

项目已有 E2E 框架(`src/__tests__/e2e/*.spec.ts`,`npm run test:e2e`)。给 workbench 写 E2E 的要点:
- 起 dev server,Playwright 打开 → 点侧栏「测试」→ 走看板/流程/报告。
- **AI 步必须 mock**:dev 无 credentials,用 `page.route('**/api/test/run', ...)` 拦截返回固定 SSE 帧(text/tool_use/`@@RESULT`/`run_json`),即可确定性地验证 SSE 渲染、四态、自动批准链、报告表格。
- 证据/媒体:`page.route('**/api/test/media', ...)` 返回固定图片字节。
- 这样能把 C1(UI 交互)大部分转成可回归的 E2E;但 C2/C5(真实 AI + 真实浏览器)仍只能人工。
