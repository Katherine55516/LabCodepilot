## 结论先行

**建议暂缓方案 A′（执行期断言取证），转向两个证据更强的根因。**

计划自设的中止条件是「若断言臆造率 < 15% 则中止」。实测：取证方案能改善的断言占**全部断言的 4.7%**（6/127）。即便按「真实失败记录」这个更宽的口径算也只有 **1/4**。而同一批数据里，另外 3/4 的真实失败指向两个计划里没列为主攻方向的根因。

**这不是「A′ 是错的」，是「按当前证据它排不进优先级」。** 样本很小（见局限声明），若后续 UI 密集型项目的数据推翻本结论，可重启。

## 三项指标

### 1. 标记服从率 — 100%，不是瓶颈

| 任务 | run.json 用例 | 有轨迹的用例 | 服从率 |
|---|---|---|---|
| 学科管理回归 | 6 | 6 | 100% |
| 测试 | 4 | 4 | 100% |

`@@CASE_START` 零漏采。这说明**标记契约本身是可靠的**——只要标记与用例判定绑定，模型就会服从。

但这也不能直接外推到 `@@EVIDENCE`：`CASE_START` 是判定链路的一环（漏了用例轨迹就归不了属），而 `EVIDENCE` 不影响任何判定，模型的服从动机弱得多。

### 2. 首轮 verified 率 — 已经很高

| 任务 | 合格 | verified | needs_review | failed |
|---|---|---|---|---|
| 学科管理回归 | 4 | 3 | 1 | 0 |
| 测试 | 2 | 2 | 0 | 0 |
| 回归用例库 | 9 | 9 | 0 | 0 |
| **合计** | **15** | **14 (93%)** | **1** | **0** |

唯一的 `needs_review` 是 TC-005，原因是 `ECONNREFUSED ::1:5173` —— **被测应用没起，不是脚本问题**。

生成侧目前没有明显缺口。这本身就削弱了「投入改造生成质量」的理由。

### 3. 断言证据链 — 取证方案的作用面只有 4.7%

127 处 `expect` + 9 处 `page.evaluate` 内的 `querySelector`：

| 分类 | 数量 | 占比 | 取证方案能否改善 |
|---|---:|---:|---|
| `non-dom`（`response.status()` / `postData.x` / 变量断言） | 105 | 83% | ❌ 完全无关 |
| `structural`（Tailwind class / `querySelector`） | 12 | 9% | ❌ 计划已列为边界外 |
| `semantic-unverifiable`（语义定位器，但该用例无元素清单） | 6 | 5% | ✅ **这就是全部作用面** |
| `semantic-with-evidence`（已能在证据链里找到出处） | 4 | 3% | — 已经没问题 |

**83% 的断言压根不涉及 DOM 定位。** 这是取样最出乎意料的一项：这批回归用例的主体是接口测试，断言打在 HTTP 状态码和响应体字段上，`@@EVIDENCE` 记录「我看到了哪个元素」对它们毫无意义。

而那 6 处 `semantic-unverifiable` 的实际内容是：`"Loading"`（加载态文案）、`"详情页测试学科"`/`"这是用于详情页测试的描述文本"`（脚本自己创建的测试数据，本就不该在页面元素清单里）、`"导出"`。**真正因「断言目标缺证据」而有臆造风险的，实测接近于零。**

## 真实失败根因（最有价值的一组数据）

全部 4 条 `repairNote`，即脚本真正跑挂并被 AI 修好的记录：

| # | 用例 | 失败原因 | 根因归类 |
|---|---|---|---|
| 1 | TC-051 | 正则匹配到 **3 条同名「前端开发」卡片** → strict mode violation。修法：拼当天日期构造唯一正则 | **测试数据不唯一**（脚本反复跑创建同名数据） |
| 2 | TC-058（回归用例库） | 卡片实际是 `div[role="button"]` 而非 `<button>`，选择器 `button[class*="text-left"]` 匹配 0 个 → `cardCount=0` 断言失败 | **结构耦合选择器** |
| 3 | TC-058（测试） | 同上，`.grid.gap-4 > button` 改 `.grid.gap-4 > div` | **结构耦合选择器**（同一问题在另一任务重演） |
| 4 | TC-034 | 页面渲染是「0 阶段」（数字在前），断言正则写成 `/阶段\s*\d+/`（标签在前），**永远匹配不上** | **模型对页面文本顺序推断错误** |

**只有第 4 条是 A′ 能治的**——执行期若记录下「我看到的文本是 `0 阶段`」，生成模型就不会把正则方向写反。

### 关键发现：结构耦合断言不是模型臆造，是用例设计的传导

计划里把 `structural` 断言归因为「aria 树给不出 role/name，模型只能臆造 CSS class」。**真机数据推翻了这个归因。**

看 TC-058 的用例原文：

```
step0.expected: 【UI检查】页面渲染学科卡片，每张卡片包含学科名称、描述文本（若有）、
                颜色标识圆点（w-3 h-3 rounded-full）
step1.expected: 【UI检查】卡片以 2 列响应式网格排列（md:grid-cols-2）
```

**Tailwind 实现类是用例设计阶段就写进 `expected` 的。** 生成模型写出 `.w-3.h-3.rounded-full` 和 `.grid.gap-4.md\:grid-cols-2` 是在**忠实执行用例**，不是臆造。

更能说明问题的是失败 #2/#3：卡片是 `div[role="button"]`——**用 `getByRole("button")` 本来就能正确匹配**。是「用例把实现细节写死 → 生成模型跟着用结构选择器 → 结构选择器对 DOM 元素类型做了错误假设」这条链把它带沟里的。

同一根因在静态校验的 warning 里也是绝对多数：**13 次「未使用语义化定位器」**，是所有 warning 里最高的一项。

## 建议：改投两个根因

按本次证据，投入产出比高于 A′ 的是：

### P0 — 用例 `expected` 禁写实现细节（占真实失败 2/4，占 warning 绝对多数）✅ 已落地 2026-07-27

治理点在**用例生成阶段**，不在脚本生成阶段。已改 4 处（上游 2 + 下游 2）：

| 落点 | 改动 |
|---|---|
| `rules/test-case-completeness.md` §1.5 | 新增「预期结果写用户看得见的事实，禁写实现细节」铁律：禁写清单 + 三层后果 + 改写对照表 + `data-testid` 例外 |
| 同上 §2.4 / §5 步骤6 | 「视觉体验」维度改为「用户能数出来的布局事实」；生成后自查加一条逐条扫 `expected` |
| `prompts.ts` cases 生成 prompt | 同步铁律。**顺带删掉原文的「有源码依据」** —— 那句话本身就在诱导模型读源码抄 Tailwind 类 |
| `api/test/revise` 用例修订 prompt | 同步约束：用户说「写详细点」时细化的是可观察现象，不是实现方式 |

下游防线（存量用例已经写死了实现类，改不了，但脚本不该跟着走偏）：

| 落点 | 改动 |
|---|---|
| `script-generator.ts` 生成 prompt | 用例 `expected` 里的 CSS 类/DOM 标签是历史遗留、不是断言目标；要断言它描述的用户可见事实。特别点名「用例说是 button 时不要写 `div > button`，真机常是 `div[role="button"]`，`getByRole("button")` 才对」 |
| 同上 修复 prompt | 结构选择器命中 0 个时**先换语义定位器，不要做 `> button` → `> div` 的同层替换**（那正是 TC-058 两次修复都做错的事） |

⚠️ **这些都是 prompt 软约束，服从率待真机验证。** 若下一轮真机数据显示 `expected` 里仍出现实现类，下一步是加**确定性检测**（用例落盘时扫 `expected`，命中 CSS 类/标签模式即标缺口），把约束从「模型自觉」变成「平台可判定」。

附带收益：这类用例本身就脆——Tailwind 类一改，用例和脚本一起失效，而产品行为根本没变。

### P1 — 唯一化测试数据（占真实失败 1/4）

即先前列为「第一梯队」的方案 J，一句生成 prompt：写操作创建的数据名必须带唯一后缀，创建/断言/cleanup 共用同一变量。TC-051 的失败与其修法（拼日期构造唯一正则）已经是这条规则的人工版本。

### P2 — A′ 降级为观察项

保留计划文档，等出现**UI 密集型被测项目**的真机数据再重新评估。重启的信号是：`structural` + `semantic-unverifiable` 占断言总数超过 20%，且其中多数**不能**追溯到用例 `expected` 里写死的实现细节。
