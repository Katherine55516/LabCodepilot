## 1. 结论及比较边界

当前主要差距是编辑组织和解释能力：**本模块更像把选中的来源组件分配进模板；Gamma 更善于先确定一页要回答的问题，再选择足够的文字、对比和关系图来回答。** 本模块已经具备全文读取、唯一模型页数建议、全局蓝图、来源绑定、原生媒体和发布检查，下一步应提高这些机制输出的质量及检查的有效性，不能重复增加一套估算器或规划器。

本模块保留了更多原表行、方法边界和可编辑公式，这是优势。但较多文字并没有转化为更完整的解释：前半段密集照录双语原文，后半段多页内容过薄；权重组合被漏选，机制描述没有变成机制图，泄漏检查分散重复。Gamma 的概览取舍、叙事衔接和组件用途更明确，也存在删减条件、图形过小及导出裁切，不能把它的所有压缩结果当正确答案。

## 2. 两份 Gamma 附件实际是什么关系

对 PPTX ZIP 的 97 个包内文件逐一比对，只有两个文件不同：

- `docProps/core.xml`：创建/修改时间。
- `ppt/slides/slide13.xml`：对象位置和尺寸。

**全部文字、图片、字体声明，以及另外 17 页都一致。** 因而这两份不是两次独立的提取、大纲或内容生成样本；本轮可分析的是一套 18 页方案，以及第 13 页的局部几何修复效果。

G2 第 13 页底部 CPCV 说明框的归一化位置约为 `y=0.8879, h=0.1183`，底边约 `1.0062`，已经超过页面底边。G3 将主要对象上移 0.25 英寸，调整五段时间区间和底部两列的宽高，底部该框约为 `y=0.8546, h=0.0789`，底边约 `0.9335`。正文没有重写。

这直接支持本模块的一个方向：**保留正确内容和全局计划，以实际导出边界为依据局部修复对象，而不是重写整份大纲。** 同时说明 Gamma 成稿也需要原生导出检查，不能用网站预览或品牌代替验收。

## 3. 量化概况：文字更多，不代表解释更深

| 指标 | M24 | G2 / G3 | 可解释范围 |
|---|---:|---:|---|
| 物理页数 | 24 | 18 | 不作为好坏评分 |
| 文本框及表格抽取字符 | 18,209 | 6,632 | 包含双语、页眉等；不含全部数学对象内容 |
| 英文/数字词项 | 2,538 | 843 | 词项匹配统计，不是语义单元 |
| 平均每页抽取字符 | 759 | 368 | M24 约为 Gamma 的 2.06 倍 |
| 非空文本形状 | 131 | 145 | 对象粒度不同，不表示质量 |
| 图片实例 | 32 | 25 | 含模板照片、装饰、公式图片等，不能当解释性媒体数量 |
| 原生表格 | 4 | 2 | M24 的表格保真和完整比较维度较强 |
| OMML 数学节点 | 38 | 0 | 不是 38 个独立公式；Gamma 仍有可见公式，部分为图片 |
| 备注页包文件 | 0 | 18 | Gamma 备注只是页码，不是完整细节存档 |
| 显式 run 字号，字符加权中位数 | 14pt | 15pt | 未计算全部继承样式，不宜当投影可读性的唯一指标 |
| 显式最小字号 | 11pt | 8pt | Gamma 三重障碍小标签也有可读性问题 |

M24 第 2–11 页占 11,415 个字符，为整份的 **62.7%**，但只占 10/24 页。后半段的第 12、13、14、17、18、19、21、24 页，每页抽取字符不超过 500；结合实际渲染，可见多页大面积空间没有承担解释任务。封面留白另当别论。

这不是要按字数填满后半段。应检查“这页承诺解释什么、需要什么关系/示例/条件、是否已表达”，不能再用字数公式给出第二个推荐页数，也不能靠照片和无关图标填空间。

## 4. 各维度评审

| 维度 | M24 的表现 | Gamma 的表现 | 对模块的判断 |
|---|---|---|---|
| 全局主线 | 大体遵循来源章节，后段泄漏/生产主题往返 | 为什么难→标签/特征→权重/验证→模型/持仓→评价/监控 | 需要让依赖顺序和读者决策优先于原文章节号 |
| 核心消息 | 多数标题已精炼，但正文有的过载、有的过薄 | 多数页用一个清楚的判断组织内容 | 标题句式通过不代表读者任务完成 |
| 内容提取 | 多细节、多条件、完整表格；关键组合关系仍漏选 | 压缩较好，但有省略和条件弱化 | 需要语义义务闭包，不能只检查所选 ID 是否渲染 |
| 内容切割 | 中性化/编码挤一页；唯一性/衰减分两页却没组合 | 互补机制经常在同页建立关系 | 根据共同解释任务分组，不机械“一小节一页” |
| 深度 | 前段保留原文，后段高度摘要，标准深度不一致 | 概览的解释粒度较一致 | standard 应约束解释充分性，不是文本总量 |
| 双语 | 主要语言模式下仍有长双语段落和突兀中文单段 | 英文主信息与短中文对应项较稳定 | 在来源保真的前提下做可审计语言投影 |
| 媒体用途 | 原表/公式强；自然语言机制常未成图；模板环图无实际任务 | 对比、步骤、时间轴、强调数字与主题匹配较好 | 从关系类型选择组件，不能只数媒体个数 |
| 自适应布局 | 能放下，未必符合内容的阅读方式 | 多数页面有清楚分组和主次 | 真实内容区域、对齐和关系表达需一起验收 |
| 条件保留 | 保留不少部署、表格、边界细节 | 某些概览结论过于绝对 | 改进精炼时保住本模块的优势 |
| 原生导出 | 有实际验证，表格和数学可编辑 | G2 第 13 页裁切，G3 修正 | 模板/网页预览/导出必须分别检查 |
| 收尾 | 泛泛原则句加 Thanks，行动信息弱 | 标签/权重/验证优先，进阶方法解决明确问题，下一步建完整流水线 | 结尾要回收开头问题与实际决策，不能机械致谢 |

## 6. 四个需要优先处理的实例

### 6.1 来源 ID 有去向，关键解释关系仍然能丢失

原输入 §4.4 明确规定：使用三重障碍/分桶分类时，类别频率不平衡，应将类别权重与唯一性、时间衰减相乘，而不是二选一。M24 已选三重障碍及分类主题，却在权重两页都未体现此关系。

项目 `contentSelection.entries` 中：

| 来源 ID | 原始内容 | 实际选择 |
|---|---|---|
| `b_0165` | `w_i = u_i × d_i` | excluded |
| `b_0170` | 英文类别不平衡及三项相乘解释 | excluded |
| `b_0171` | 上述中文对应段 | excluded |
| `b_0172` | `w_i^final = u_i × d_i × w_i^class` | excluded |

四项均使用概览排除理由 `Outside the selected overview...`，不在任何页面 `sourceArtifacts` 中。不是渲染吞字，也不是来源丢失；是**编辑取舍合法但不理想，而且现有检查没有把关系闭包作为独立义务**。不可简单修成“所有公式必须出现”；应要求当页承诺介绍权重机制时，交代三个问题如何组合及类别项适用条件，或者在确认大纲时明确减少了此范围。

### 6.2 有媒体回执不等于有解释性媒体

P6 的实际媒体回执包含 `list` 和 `text`，状态均为 `ready`；正文仍显示画图说明。P15 的实际回执是 `symbolic-interval / ready`，原生区间组件确实存在，但端点、主轴及边界文字的视觉映射仍不够直接。不能误写成 P15 实际降级为普通列表。

P12、13、14、18、19、24 的 `mediaTasks` 为空。P18 的模板环图并不因此变成“模型到持仓”的有效媒体。需要区分：模板装饰存在、来源对象完成绑定、指定关系被完整表达、读者确实能看懂，这四件不同的事。

### 6.3 标准深度不是前面照录、后面一句话

P3/P5/P6/P8/P10 的长双语段落挤占阅读注意力；P13/P14/P19 等又缺少标题承诺的具体机制。应检查每个 reader task 的必要解释，而不是全文字数达到阈值就认为标准深度合格。`source_only` 允许对来源进行有依据的改写、组织和关系表达；不能把它误解为只能原段照贴。

### 6.4 工程通过的含义必须准确

本次快照 `quality.status=passed_with_warnings`、`publishEligible=true`。四轴中来源完整性、编辑语义、物理排版是 `automated_checked`；原生导出为 `verified`，`humanVisualReview=not_verified`。

fixture 中的 `PAGE_GROUPS` 固定了主要标题和来源 ID；`input:understand` 返回受控建议；writer 返回空 `sourceCommentary`/`contentBlocks`，依赖原生来源组件；review 分支返回受控评审。它适合验证读取、选择、来源绑定、容量、版本和导出等工程链路，**没有独立证明真实模型的取舍、解释或审美达到了 Gamma 水平**。

正确的收尾措辞应分别报告：工程合同通过、受控语义断言通过、实际渲染发现什么、哪些人类或真实模型评估仍未覆盖。不能因为这轮发现质量差距就否认已验证的导出保真，也不能反过来用导出通过证明编辑质量优秀。

### 6.5 导航标签和引用还带着原文章节的痕迹

M24 P23 主体是 PIT/交易限制，页眉仍标为 `15 Summary`；P21 的 `12 Industry Sidebar` 也不能帮助读者识别当前生产流程任务。正文表格还出现 `Source cites §12.2` 等直接继承的说明。原文章节号与当前演示页码不是同一套导航，来源段落经过重新分配后，这些文字可能让读者误以为对应当前演示中的章节。

生成时应把“来源位置”“本演示章节”“主标题”“组件小标题”分开：本演示导航由全局蓝图产生，来源位置保留在可追溯的引用字段；必要引用应以读者能理解的形式可见，不能用清理引用为理由删除出处，也不转入备注。当前 writer 已有避免陈旧 secondary label 的提示，仍需要实际输出检查，不能只要求模型在 schema 中填一个 label。

## 8. 建议的优先顺序：改哪里、怎么改、如何验收

### P0-1：先补语义义务与概念关系闭包

**Code：**在现有 source inventory/reader groups/selection 之间增加派生 obligation 清单，复用原始 ID、quote spans 与已有 relationship，不新建竞争事实来源。区分核心结论、必要定义、变量、条件、比较集合、组合关系，以及可选证据。选择结果标明义务由哪页、哪个可见组件完成；多个 ID 合起来形成一个解释时要整体审核。

**Prompt：**reader 先回答“讲清这个主题不可缺少什么”，再建议范围和页数；planner 明确保留/合并/取舍的解释理由，不能用通用 `outside overview` 掩盖重要的条件或组合关系。

**验收：**分类与三重障碍已入选、权重两项也入选，却把类别条件及组合式都排除时必须产生定向问题；修复可补该页可见组合/条件或提出范围取舍，不要求所有原公式无差别上页。

### P0-2：确认 N 内的全局叙事和解释分配

**Code：**扩展现有 editorialBlueprint 的检查：每页是否有一个主要 reader task、是否有来源支持的新增答案、依赖定义是否在前面或同页、尾段是否只剩空壳，过载页是否混入多个独立决策。聚合语义重叠作为人工/模型复核候选，不以句面相似度直接删页。

**Prompt：**先列出全部 N 页的 question→answer→必要支持→关系组件→前后引用，再并行写作；在 24 页下增加来源支持的机制和边界解释，不能把 18 页内容简单稀释。短页若与邻页共同回答一个问题，可提出合并/重分配，标题冻结后走明确的结构修改流程。

**验收：**P11 多任务问题被发现；P12/P13 不再只拆主题而丢掉组合；P17/P22/P23 的重复有定位和具体增量说明；确认 24 后实际仍为 24，除非用户同意更改。

### P0-3：标准深度与主要语言的有依据改写

**Code：**独立验证 language projection 与 explanation completeness。双语原段必须保留不可变来源；可见正文投影为主要语言、必要术语保留次语言，审核否定、数量、条件、比较与限定是否等价。不能用正则直接删除中文半段。深度检查按内容类型看机制、例子、条件和结论，不用固定 1:3:8 字数比例。

**Prompt：**标准页应说明“是什么、为什么/如何、何时适用或不能这样做”中与该任务有关的部分；用来源支持的短句组织，不重复英文后又逐句贴长中文。主标题采用主要语言，次语言只在用户策略要求时作为较小辅助层级，不能重复标题字号。

**验收：**P3 等不再原段双语堆积；P2 的中文单段有合理主要语言投影；P13/P19 不靠增加空泛句子达到字数。表格风险行、h/τ 边界、条件中性化和分类权重前提保持。

### P1-1：把自然语言关系送进原生媒体系统

**Code：**在已有 typed graph 前增加有来源审核的 prose→relation proposal，不做第二套渲染引擎。支持：机制/分支、带变量的时间边界、重叠窗口、乘法组合、比较、流程、滚动循环。每个节点、边、条件都指回原文片段；叙事先后与事实因果分开。

**Prompt：**先说明图要让读者看懂哪条关系，再选图形；允许图不优于表时继续用表。不得编造回测数值或市场价格路径。示意路径如确需生成，应明确是非数据机制示意且符合原始条件；不伪装来源实测。

| 本次页面 | 应表达的关系 | 合适的原生组件 | 必须保住的内容 |
|---|---|---|---|
| 三重障碍 P6 | 从起点到首次触发，三类退出 | 带价格/时间轴及触发注释的机制示意，或可解释的分支图 | 上/下/时间障碍、首次事件、标签及到期处理条件 |
| 权重 P12–13 | 三个独立问题相乘组合 | 组合式 + 三项短说明/分类条件 | uniqueness、decay、class condition；不是三选一 |
| 随机划分 P14 | 两个窗口共享未来信息 | 两条时间窗口/重叠区示意 | 起止、h、共享部分和泄漏原因 |
| Purge/Embargo P15 | 时间区间和不同删除规则 | 端点对齐的原生时间区间图 | `t_a-h`、`t_a`、`t_b`、`t_b+τ` 与规则对应 |
| 模型到持仓 P18 | 分数到可交易头寸的转换 | 来源支持的过程链，风险/成本是约束 | ranks、vol scaling、risk、turnover、calibration；不编造配置 |
| 滚动评价 P19 | 内层选择与前向冻结评价，窗口推进 | 滚动窗口/泳道 + 指标对照 | 训练/验证/测试边界，避免未来用于调参 |
| 生产 P21–22 | 版本化数据、模型、预测、组合与监控/停用 | 来源支持的流水线及控制点 | 可复现版本、时间戳、成本、回滚/停用条件 |

**验收：**不再出现可见 “Diagram description”；不能用装饰环图证明 score→position 已解释；媒体 receipts 明确区分绑定、关系覆盖、表示功能与布局检查。

### P1-2：按任务适配模板内容区，而非保留空壳

**Code：**复用 template roles/layout catalog/component profile，区分品牌装饰、可替换主题媒体和真实内容组件。正文区域根据表格、机制、比较或流程选合法版式；受保护的品牌元素保持，未绑定来源的数据图型模板组件需明确标为装饰或移除/替换。容量允许不代表设计完成。

密度诊断分开 text、explanatory media、data media、decorative media；把 P18 大环图和 P17 大照片排除在“已经讲清楚”的证据之外。允许有目的的留白，但不能凭任意占用率强迫添字或加图。

**Prompt：**说明每个主要区域的任务；低对比图标只作装饰，不承担关键信息。图和表的标签靠近对象，对齐、色彩和大小表达真实关系；不要求每 8 页固定四种版式，不为多样化而改掉适合的连续表格。

**验收：**P13/P19 等能选用适合解释任务的内容区；正文可读下限不变，无新裁切；Mood Board 风格仍一致；原表选中行、完整风险和公式变量不为排版临时删除。

### P1-3：把“通过”拆成有证据的不同结果

**Code：**保持现有四轴，增加可审计的 `obligationCoverage`、`readerTaskCompletion`、`representationFulfillment` 和重复/深度诊断。不要把 warning 改名为 success；关键已选事实/关系不完整时不能正式发布。较疏页面需评审其任务，合理的封面/结尾允许例外，而不是全页最低字数硬门禁。

原生导出检查继续使用实际 PPTX/PDF 边界及字体环境证据。Gamma G2→G3 说明几何局部修复必须保留；只重验受影响页及其依赖，保留已正确的内容与页数。

**验收：**选择账本、模型自评、媒体节点数都不能单独证明整体编辑优秀；未人工检查显示未验证；缺字体时先报告环境错误，不误判源文件缺字。未通过仍保留可预览草稿与定向修复入口，不转备注、不正式导出。

这比“直接把当前 24 页合成 18 页”更适合本次用户已经增加页数的设置：把新增页用于必要机制和边界，把重复检查回收成完整且位置合理的一页。是否足以在 Mood Board 每个实际版式下容纳，仍须后续量测；本报告没有把该蓝图称为已实施或已通过的成品。

## 10. 应保留的优势及不应照搬的 Gamma 行为

- 保留 M24 原生表格、完整已选行列、公式与变量、源证据和边界条件；不要为了看起来更像 Gamma 丢掉这些能力。
- Gamma P9 删除 5–10 天行，是其概览取舍；不是本模块应在生成时自动执行的截断规则。
- Gamma P11 将部分中性化操作说得过于绝对，P12 类别权重适用条件也不充分；精炼不能吞掉条件。
- Gamma P8 的三重障碍图小且没有真实时间/价格机制，仍有改进空间；“有一个图”不是完成标准。
- G2 P13 的裁切是导出缺陷，G3 的修复值得学习的是局部保内容调整，而不是默认 Gamma 所有原生输出均正确。
- 本次不从模板主题差异推断媒体生成模型优劣；本模块已有较多模板图片，但它们不能替代关系媒体。
- 不增加备注兜底、不自动改用户 N、不靠任意缩字号/删除表格来使门禁通过；失败保留草稿并说明具体原因。

## 12. 补充一：主题合并、页面节奏和组合关系如何落到现有管线

### 12.1 可学习的 Gamma 行为，以及不能从界面推断的内部实现

本节使用前述 G2/G3 的内容和[已有 Gamma 实测记录](ppt-gamma-template-first-editor-workflow-audit-20261019.md#16-实际局部优化及visual-editor观察a7a9)。可以核实页面怎样组织、局部修改落在哪一页；无法据此确认 Gamma 私有模型、隐藏提示词、并发数或真实页数估算算法。以下是适用于本模块的设计建议，不能写成对 Gamma 内部架构的逆向结论。

Gamma 有三种值得区分的组织方式：

| 类型 | 本次可见例子 | 为什么能组合 | 本模块应学什么 |
|---|---|---|---|
| 同一问题的不同支撑 | P5 的非平稳、重叠、有效样本、反身性 | 共同解释金融数据为什么难，四项是并列原因 | 用一个上位问题组织独立面板，各面板保留自己的作用，不假造因果 |
| 同一机制的不可分关系 | P7 回归/残差/标准化；P12 三项权重 | 前者有步骤依赖，后者有乘法与条件 | 机制的节点、关系、适用条件应整体规划，不能只分别覆盖关键词 |
| 一个主要图及紧邻的用途区分 | P13 区间边界 + WF/CPCV 比较 | 先解释删除边界，再说明验证策略的不同角色 | 图内时间顺序与图外方法比较必须分开；不能把 CPCV 画成 embargo 后的时间步骤 |

Gamma P15 将模型家族与持仓转换放在一页，是“模型只是流水线的一段”的概览安排，不表示这两个主题在所有深度下都必须合页。P17 将解释、数据伪影和监控放在一起也有压缩代价。**可合并不是必须合并；有关联也不表示应在同一物理页。**

### 12.2 用“解释任务”定义合并，避免两个极端

当前不理想的两端是：把相近小节各分一页，造成过薄；把来自同一来源章节的所有内容放一页，造成多任务过载。仅靠语义相似度或字数都解决不了这个问题。

建议使用以下规则，由 LLM 提出、有来源证据的代码合同验证：

1. 先提炼读者需要完成的具体判断，例如“这三种权重分别解决什么，如何一起使用”。“介绍权重”“理解第 4 节”不足以证明一个任务已定义清楚。
2. 为任务列出必要的定义、变量、原因、关系、条件和代表证据。分配支持角色，而不是给每个来源段落一个同等大小的文本框。
3. 只有共享一个具体任务，或者能用明确上位问题容纳少数独立面板时，才提出合页。相邻章节、同一个关键词、两段都短只是线索。
4. 检查合页后读者是否仍能识别“哪种机制解决哪种问题”。若必须加多层转折才能解释为什么放一起，通常应拆页或用跨页引用连接。
5. 用实际合法布局和可读下限验证候选。代码判断候选是否可容纳，不输出另一套页数建议。
6. 保持已确认的 N。大纲确认前可以在 N 内重分；确认后任何合页、拆页或标题/所有权变化应作为明确的结构候选，不能由 writer 静默执行。

| 本次内容 | 建议关系 | 处理方式 | 不应采用的处理 |
|---|---|---|---|
| 唯一性、衰减、类别权重 | 独立问题相乘，类别项有条件 | 一页展示组合，必要时另页解释唯一性机制；两页之间引用同一组合合同 | 只保留唯一性与衰减，组合式及分类前提都排除 |
| 随机划分、purge、embargo | 问题→修复，以及两类时间边界 | 可用“重叠反例 + 修复图”两页；短概览在一页分明区域 | 仅因为都有 leakage 就塞成无层级列表 |
| WF 与 CPCV | 对比/用途互补 | 同页比较，或紧邻区间图但明确是另一维度 | 五段时间轴后接第六段 CPCV |
| 日期内归一化与交互 | 数据变换→经济交互，任务可分 | 概览可合为步骤，标准深度按公式与例子负担决定 | 为合页丢掉“不能用全样本统计”的条件 |
| 行业编码与中性化 | 输入表示与暴露控制，属于不同决策 | 默认分任务；必要时共同放入有清楚区分的上位面板 | 因都属于 feature engineering 就原文合堆 |
| P17/P22/P23 泄漏与错误清单 | 重复检查 + 部分生产独有条件 | 集中五陷阱，生产页只保留独有控制并引用前页 | 去重时连成本、部署监控等新条件一起删除 |
| 模型家族与分数到持仓 | 上下游依赖 | 18 页概览可用主区+流程条，24 页可分别解释 | 以无标签环图代替持仓转换 |

### 12.3 关系闭包需要记录什么

沿用现有 inventory、relationship、reader groups、pageContract 和 editorialBlueprint，添加可审计的派生约束；不另建一套与原文竞争的事实 IR。建议的合同信息为：

- `obligationId`：这个解释义务的稳定标识，来源变化时失效。
- `sourceUnitIds + quoteSpans`：原文依据，不能只给模型新写的一句话。
- `relationType`：并列、顺序、乘法组合、条件、对比、时间区间等；叙事顺序另外记录。
- `requiredParticipants`：必要节点、变量和关系；可选材料明确标 optional。
- `applicability`：原文的适用条件，例如只在相应分类任务下引入类别权重。
- `placement`：应同页、同组件或允许跨页引用，以及原因。不能把所有有关联的内容一律设为同页。
- `ownerSlideId + visibleBindings`：由哪一页、哪些实际对象完成；图和正文合起来也可以完成一个义务。
- `disposition`：保留、等义摘要、受用户确认的取舍、未完成；“原文仍存着”不能代替可见解释。

以权重为例，最小解释不仅是三项名称，还包括“重叠、过时、类别不平衡是不同问题”“组合方式是相乘”“类别项有分类场景前提”。Gamma P12 的组合式值得学习，但本模块应保留它没有充分展开的分类条件。义务数量不转为硬编码页面数，也不把一个具体领域的三项组合写成所有输入的通用模板。

若一个合法的概览确实不涉及分类，可以在大纲取舍中明确排除该分支；此时不能还用标题或正文暗示已经完整讲解分类权重。检查的是**承诺的范围是否被完整解释**，不是强迫打印全文。

### 12.4 页面节奏：按理解负担安排，不按固定版式配额

页面节奏包括三个层次：

1. **整份顺序**：建立问题和必要定义，再解释方法，随后验证、使用和监控。原文章节号只是来源定位，不自动成为演示章节。
2. **相邻页的推进**：前页提出的问题，后页要增加机制、证据、条件或决策；不能换个标题重述同一消息。必要回顾要明确 `repeatPurpose`，且只回顾足以继续阅读的内容。
3. **单页注意力分配**：主结论或主题、主要解释组件、必要边界有层级。允许有目的的留白；有一段文字并不必然需要把整页填成文字。

可供 planner 选择的任务包括建立语境、解释机制、比较方案、展示有口径的证据、核对约束、整合决策。它们不是强制轮换的六种页面角色。比如两张连续表格若回答不同且必要的问题，可以保留；一张短结尾也可以成立，前提是它完成了真实的回收任务。

对 M24，建议首先处理以下节奏断点：

- P2 将受众介绍、引言和多个数据困难混排，应该突出核心挑战，把其他材料分配到相应解释页；不需要单独为每段开页。
- P3/P5/P6/P8/P10 要精炼来源表达和双语投影，把重要条件从长段里显出来。
- P12/P13 从“两个短主题”变为“一个组合解释及必要机制”；不能保留两张空壳页却漏掉类别权重。
- P14/P15/P16 形成“重叠为何泄漏→边界如何修复→两种验证策略如何使用”的推进。
- P17/P22/P23 的重复归并后，腾出的解释空间用于持仓流程、滚动评价及生产控制；是否换标题/所有权在结构候选中明确。
- P24 回收前文的优先顺序和下一步，不能只放泛原则与致谢。

标题可以是清楚的主题、比较对象或有来源的判断，不强制每页写成口号式 takeaway。节奏也不通过“至少几种版式”“一页多少字”或图文轮换硬规则验收。

### 12.5 读取 input 到生成 outline 的完整建议流程

```text
完整解析：正文、双语、表、公式、代码、图说明及来源定位
  ↓
LLM 完整阅读：brief、具体 reader tasks、核心概念/关系/条件、粗解释组
  ↓
在模板/深度/语言合同下，LLM 给唯一 recommended/min/max 与理由
  ↓
用户调整并确认 N；保留原建议与选择理由
  ↓
全局分配 N 个物理页面：任务、答案、支持角色、关系闭包、相邻增量
  ↓
为每页选择来源范围、语言投影、关系组件和合法布局候选
  ↓
来源取舍 + 关系完整 + 节奏/重复 + 实际容量检查
  ↓
用户确认大纲；冻结标题、N、所有权和必要义务
  ↓
有限并发写作/媒体合成；每页读取已冻结的全稿蓝图与只读邻页上下文
  ↓
目标级审查与修复；超出授权范围才提出结构候选
```

**先阅读与粗分组，再估算；先确认页数，再展开最终逐页大纲。** 粗解释组不是提前生成的最终 outline，也不要求一组只能对应一页。

容量检查失败时，先在 N 内换合法表示、局部精炼和重分配；代码报告哪页、哪些义务和布局不兼容，不给另一个“校准推荐页数”。若确实需要改变范围/深度/N，保留草稿并让用户决定。用户只调整 N 时复用有效的输入理解；来源、展示合同、模板或深度变化时按依赖使相关结果失效，不能复用不适配的旧容量证明。

### 12.6 Prompt、代码与验收的具体增量

| 环节 | Prompt 应增加/收紧 | Code 应增加/修正 | 验收 |
|---|---|---|---|
| Reader | 输出具体解释任务与关键关系，说明哪些是必要条件 | 校验派生义务的来源定位和关系类型；保留唯一估算 | 全文后段、表末尾和条件不被早段长度挤掉 |
| Planner | 解释 merge/split reason 和每页新增答案，先完整列 N 页 | 让 requiredRelations/Units 真正约束选材；诊断泛问题、重复和多任务过载 | 24 页不是 18 页的稀释版；重要组合关系无通用理由漏选 |
| Selection | 概览取舍以解释范围为单位，不能割裂条件 | 概念/关系闭包与 existing selection 联合检查 | 权重负例、时间顺序/并列混淆负例被检出 |
| Writer | 只完成本页任务，以来源支持的机制/示例补足解释 | 分离 fit 与解释完成；保持冻结 N/标题/所有权 | 原文能装下不等于只需照录；不增加无依据内容 |
| Media | 描述图需表达的关系和条件，不只指定“画流程图” | prose relation→已审核 typed graph→既有 scene/media task | 图有节点还不够，边、条件、端点与来源对应 |
| Reviewer | 阅读整份问题推进与当前页实际内容，解释不足定位到具体义务 | 完全字符串判重之外增加语义复核候选；相关问题不同仍可评估合并 | 相同措辞但合理回顾与不同措辞但无增量重复能区分 |

## 13. 补充二：选中目标旁的 AI 局部优化交互

### 13.1 已有能力与这次真正需要改的部分

已有实测中，Gamma 的 inline composer 会显示 `Paragraph · …` 或 `Card · …`，用户在看到明确范围后发指令；段落修改及单页关系图改造都曾验证其他页的采样文字、样式和图片来源保持。它的候选/恢复交互可以借鉴，但本模块保留现有“预览→应用/放弃→撤销/版本”的事务能力，不必复制先应用再切回的所有细节。

当前代码已经不是只能改整页：

- [`PptCanvas.tsx`](../../src/components/ppt/canvas/PptCanvas.tsx) 的文字编辑区可上报选区起止和文本。
- [`StructuredPptEditor.tsx:132`](../../src/components/ppt/editor/StructuredPptEditor.tsx#L132) 已有 `textTarget`，支持 range、paragraph、item、graph-node；`onTextSelection` 目前会 `setTool('ai')`，进入右侧面板。
- 同文件 `proposeAi` 复用 `/ai-edit`，请求带 `baseRevision`、scope、slide/node 和可选 target；已有候选、局部预览、应用与撤销。
- [`edit-target.mjs`](../../apps/cowork-server/lib/ppt/edit-target.mjs) 已校验 UTF-16 范围、选中文本、重复项稳定 ID、公式原子范围；不应另写 substring 替换接口。
- [`proposal-service.mjs`](../../apps/cowork-server/lib/ppt/proposal-service.mjs) 已校验 plan/target 内容与候选质量。新交互应复用这些检查。

**本次主改动是交互入口、选择锚点与候选反馈，不是重建 AI 服务。** 进一步的组件内重排/原生页布局变化有能力边界，需要单独实现与验收。

### 13.2 建议的用户操作

| 用户动作 | 就近出现的输入框 | 明确显示的范围 | 默认允许改变什么 |
|---|---|---|---|
| 从缩略图或页面明确选择“优化本页”，或点击页面容器的 AI 入口 | 页面右上/右侧的浮层 | `第 6 页 · 本页` | 本页允许编辑的内容；标题冻结/模板锁继续生效 |
| 单击一个组件，完成选择而非拖动 | 组件外侧的小输入框 | `本组件 · 三重障碍` 等可读名称 | 该组件内容；不自动修改整个页面 |
| 在编辑状态拖选文字，或键盘形成选区 | 选区附近输入框 | `所选文字 · …`，可展开看完整原文 | 该范围的文字；默认保留外部内容与样式 |
| 选择一个列表项/图节点 | 项目或节点附近输入框 | `列表第 2 项` / `图节点 · …` | 稳定 item/node ID 对应内容，保留关系 |
| 多选多个对象 | 显示选择数量及一个明确入口 | `已选 3 个对象` | 仅在多对象原子候选已支持时提交，否则清楚提示可用范围 |

不把拖动画框、移动对象、调整控制点的过程中途当成“已完成选择”。画布空白点击仍能清除选择；框选手势不自动触发整页 AI。整页目标使用可见、明确的入口，避免用户本来只是取消选择却误改整页。

输入框默认包含：目标 chip、自由指令、少量常用快捷动作、发送按钮。快捷动作如“精简”“解释更清楚”“翻译”“调整表达形式”仍需服从目标能力。翻译参数、模型/执行策略及完整诊断放在可展开高级设置，不能把所有现有右栏控件原样塞进浮层。

示意：

```text
[已选文字高亮]
                 ┌─────────────────────────────┐
                 │ 所选文字 · 保留公式及条件       │
                 │ 用更短的英文说明这一机制……      │
                 │ 精简  更清楚  翻译      发送 ↗   │
                 └─────────────────────────────┘
```

这是本模块拟议交互，不是 Gamma 截图。浮层是编辑器 UI，不属于 slide IR，不参与保存、截图式页面预览或 PPTX/PDF 导出。

### 13.3 防止焦点切换后改错目标

建议维护一个共享的 selection/composer controller，而不是右栏与浮层各维护一份 instruction/proposal。状态分为选择、编辑指令、请求中、候选可预览、应用/放弃、冲突/失败。

1. 用户完成选择时立即冻结 `projectId/slideId/nodeId`，range/item 等目标信息、原始文本 hash 和当时的页面编辑上下文。
2. 浮层出现不自动抢走文字焦点。用户主动点输入框时保留冻结的范围和高亮；不要重新读取此时已经折叠的浏览器 selection。
3. 当前文字来自 textarea 的原始字符串，可直接使用其 UTF-16 offsets。若未来从富文本 DOM 选区读取，必须通过 run/DOM→source 映射，不能拿可见字符串索引直接替换原文。
4. 若用户在文字编辑器里有未保存修改，先完成实际保存并取得新 revision，再按编辑事务核对/重建目标；无法证明同一目标时提示重新选择，不靠搜索相同句子猜测。
5. 指令输入期间即使用户浏览邻页，请求仍对应冻结目标；界面显示正在改哪页。若用户重新选目标，未提交草稿可按目标保留，但不能让旧请求结果应用到新目标。
6. 实际发送及应用继续核对服务器上下文。目标文本、计划、锁或版本变化时返回冲突，不用新的 `baseRevision` 偷换旧目标使请求通过。
7. 一个任务内固定 `operationId/requestId` 处理双击发送、迟到响应及重试；取消后结果不自动应用。前端忽略响应与后端停止模型是两回事，未完成服务器取消能力前不要声称调用已终止。

`Enter` 在指令框中换行，`Cmd/Ctrl+Enter` 发送，并检查输入法 composition 状态。`Esc` 先关闭当前浮层/候选，不能顺便删除对象或撤销已经应用的操作。键盘用户应能从已选对象打开 AI、到达所有按钮、关闭后回到原目标。

### 13.4 浮层位置、缩放和滚动

- 对象目标以当前可见 DOM bounding rect 或选择框的实际屏幕矩形定位；多行文字以选区矩形与用户操作位置定位。不要直接把 EMU 当 CSS px。
- 优先放右侧，其次下方/上方，并限制在编辑器可用视口内；避开选择控制点、顶部工具栏及候选按钮。靠边时翻转位置，而不是越出屏幕。
- 缩放、滚动、面板开合和视口变化时重新量锚点。目标滚出视口时可收为固定的小目标条，保留草稿及明确范围，不能悬挂在错误对象旁。
- 原生图背景、旋转对象、group bounds 也通过实际选择框定位；不为实现浮层去改变对象坐标。
- 使用独立 UI overlay/portal，事件隔离只阻止画布选择/拖动处理，不阻止输入框正常选字和光标。避免全局 `preventDefault` 导致无法输入。

### 13.5 请求和候选的范围合同

现有 API 无需为新入口换成另一套聊天服务。首阶段复用现有 `scope/type/target`，由同一 controller 驱动右栏和就近输入框。目标信息要以 chip 显示，不能只在请求 JSON 中存在。

| 范围 | 模型上下文 | 可写部分 | 校验重点 |
|---|---|---|---|
| 文字 range/段落 | 原目标、来源依据、少量只读上下文 | 目标文字 | 数字、否定、条件、术语、公式原子及范围外文本 |
| 列表项/图节点 | 所属组件和关系，只读邻项 | 指定稳定 ID/字段 | 不错改同名项，不丢边，不把局部标签改成新事实 |
| 单个组件 | 当前组件、来源和页面只读上下文 | 合法组件对象/原子 patches | 表行列身份、图关系、样式和边界 |
| 本页 | 全局蓝图及邻页摘要只读，本页完整合同 | 本页已授权范围 | N、标题锁、来源取舍、必要关系和其他页稳定 |

不得把不支持的表格单元格、组合对象或公式内部选区静默降级成整组件/整页。表格如需支持单元格文案，要扩展稳定 row/column 身份目标并复用既有表格身份检查；数字/表头/行列重排走有来源的数据/结构候选。

**富文本需专项处理。** 当前 `patchEditTarget` 更新后会删除部分 `richText/rawText/paragraphs` 派生字段，需要核查后续重建能否保住目标外的 bold/link/字体等 run 样式。不能因为纯字符串范围正确，就认为所有富文本样式都保真。建议以 run-aware splice 处理，目标之外的 runs 保留；原生文本的段落结构限制继续生效。

### 13.6 页面/组件优化与原生模板的能力边界

当前原生 preserve 模式对 layout/data/structure 有限制。把入口改成浮层不会自动获得 Gamma 的自由布局能力，也不能简单删除这些禁用判断。

首阶段让现有内容、样式、选区候选在就近输入框可用，按真实能力显示动作。后续若支持“把本页改成区间图”，应增加**模板允许内容区域内**的受控重排合同：固定品牌/背景/用户锁定对象不动，来源与已确认取舍不变，明确会替换哪些组件；若需要移动外部对象或改变其他页，另列影响范围。候选通过来源、关系、物理布局及原生导出检查后才能应用。

### 13.7 生成反馈、失败、应用及撤销

用户发送后在目标附近显示真实状态及取消入口，不用全页遮罩阻断浏览。保留原页面，候选在临时预览层展示，不把未验收流式片段写入正式 deck。

当前请求返回完整候选 JSON；首阶段显示真实请求状态即可。若后续增加增量文字预览，应由后端返回绑定 operation/target 的真实片段和终态，不能前端用 timer 伪造流式生成；增量片段不构成可应用候选，最后仍需完整合同校验。

候选出现后就近提供“应用”“继续修改”“放弃”和可展开差异；复杂页面候选可打开更大的 before/after。保留现有 `AiBeforeAfterPreview`、`AiCandidateControls` 和版本记录能力，不在浮层再建一份候选存储。

- 文字候选显示原文/新文及实际变化范围；样式或布局候选显示受影响组件，而不只展示字数倍率。
- 对象外必须发生的重排要明确说明并纳入授权范围，不能偷偷移动其他手工对象。
- 超时、额度、连接、目标冲突和门禁失败显示具体原因，保留指令和目标；重试前检查目标仍有效。
- 仅局部修改有问题时修该范围和必要依赖，不重写全稿。问题是来源缺失/条件冲突时不要把反复重试当修复。
- 应用写入一条可追溯的操作；撤销针对该操作，不回滚其他已发生操作。历史版本只读预览与明确恢复继续分开。

## 14. 补充三：子标题白色底条的已确认原因与修复方案

### 14.1 现象不是文字颜色问题，也不是模板必然带有白底

用户截图框出的是主标题上方的细长导航文字区域，内部命名为 eyebrow/section label。它与主标题、翻译副标题和普通内容小标题应分别识别。本例文字颜色没有明显错误，错误是文本框的**面填充**为白色，而页面背景为浅绿色。

本轮读取最终项目快照及实际 PPTX，已核实：

| 层级 | 实际证据 |
|---|---|
| 页面背景 | `templateSpec.palette.background`、模板页背景和 renderTree background 均为 `#ecf0db` |
| 出问题的对象 | 第 2 页 `node_b5b5569895fa454614dcd543`，`semanticRole=eyebrow`，`content.derivedFrom=source-navigation`，没有 `nativeRef` |
| 对象样式 | `fontSizePt=11`、DM Sans、文字色 `#2e2f23`；**没有 `style.fill`** |
| 导出 XML | 同对象映射到 `<p:sp>`，`<p:spPr>` 中实际含 `<a:solidFill><a:srgbClr val="FFFFFF"/></a:solidFill>` |
| 影响范围 | 本份 24 页中查到 23 个上述系统 eyebrow，23 个都导出为白色填充；不只截图这一页 |

可复核明细：[eyebrow-fill-audit.json](../../outputs/ppt-ml-compare-20261020/eyebrow-fill-audit.json)。此统计只针对已识别的系统新增 eyebrow，不声称 PPT 中所有白色对象都是错误。

### 14.2 从生成到导出的具体原因

1. [`ppt-section-eyebrow.mjs:239`](../../apps/cowork-server/lib/ppt-section-eyebrow.mjs#L239) 在原生模板没有 section slot 且存在安全区域时新增一个导航文本节点，指定几何、字体及文字颜色，没有指定 fill。这对透明文字是合理的默认意图。
2. React 画布 [`PptCanvas.tsx:645`](../../src/components/ppt/canvas/PptCanvas.tsx#L645) 的背景处理主要针对 shape，该新增 text 没有背景色。
3. SVG 预览 [`preview.mjs:60`](../../apps/cowork-server/lib/ppt/exporters/preview.mjs#L60) 的文本分支用 `style.fill || 'transparent'`，同样把缺省值显示为透明。
4. 原生模板导出的 [`import-pptx.mjs:307–309`](../../apps/cowork-server/lib/ppt/import-pptx.mjs#L307) 在 `add_source_artifact` 的新增文本分支里，使用 `style.get('fill', '#ffffff')` 并执行 `shape.fill.solid()`，把无填充语义改成白色实体填充。

因此根因是**各渲染端对同一缺省填充的解释不一致**。不是容量估算、LLM 文案或 RGB 色差引起，也不应通过给 prompt 加“不要白底”来修复。

### 14.3 最小修复与不能采用的补丁

建议先做可独立验证的最小修复：新增普通文本没有显式填充时，原生导出使用 no-fill/透明；有合法显式填充时保留该色。新增纯文本的轮廓也不应凭默认样式出现；原始模板的轮廓与填充不能顺带清除。

在当前 python-pptx 导出路径中，应通过其 no-fill 语义写出 `<a:noFill/>`，而不是只删除颜色节点，避免主题重新继承出填充。具体 API 行为须用小型 fixture 输出 XML 和实际渲染确认，本轮未修改该代码。

不能采用的修法：

- 给所有文本框硬编码 `#ecf0db`。这只遮住本例，深色页、图片、渐变、卡片内文本及换主题都会错误。
- 将整份的白色 shape/text/table 填充全部清掉。白色卡片、品牌条、表格行和强调区域可能是模板明确设计。
- 把 `style.opacity` 设为 0。这会隐藏文字或整个节点，不是只让背景透明。
- 不校验 schema 就传 `style.fill='transparent'`。当前 `command-schema.mjs` 对 fill 按颜色格式校验，该字符串并非现有可接受的通用清除操作。
- 只改画布 CSS 或截图后处理。真实 PPTX 的 XML 仍会白底，用户编辑和另行导出仍能复现。

### 14.4 建立统一填充语义，避免透明与继承混淆

最小修复后，应将填充解析集中为所有渲染端共享的规范。建议保留现有合法 `style.fill` 颜色字段，通过一个纯解析器输出 resolved fill；只有确需支持用户“清除原生填充”时，再扩展可选的显式 none 状态并同步 schema/types。

| 对象来源与操作 | 未提供 fill 的含义 | 显式颜色的含义 | 显式清除的含义 |
|---|---|---|---|
| 系统/用户新增的普通文本 | 透明/no-fill | 使用指定填充 | 透明/no-fill |
| 已存在原生模板文本，普通文字编辑 | 保留原有 fill，包括主题/渐变/图片填充 | 授权样式编辑才覆盖 | 仅明确授权时写 no-fill |
| 新增有背景的卡片/强调 shape | 由合法组件样式决定，不从普通文本规则推导 | 使用组件/用户明确颜色 | 根据组件合同，不能使必要对比消失 |
| 表格/图表/媒体底板 | 保留其专用样式合同 | 按相应组件编辑 | 不受“移除 eyebrow 白底”批处理影响 |

这里“透明”指无面填充；与文字/整个对象的 opacity 分开。`inherit/preserve_native` 也不同于透明：前者保留已有原生样式，后者明确清除填充。旧项目不带新字段时，依据 nativeRef/对象创建来源兼容，不把所有缺省原生 fill 都改成透明。

建议 resolved 结果至少表达 `preserve_native / none / solid` 及 provenance；对未编辑的原生 gradient/picture/theme 不做扁平化转换。若新增 `style.fillMode` 等可选清除字段，需拒绝互相矛盾的 none+solid 输入，并明确迁移和缓存版本；具体字段名在实施时以现有 schema 最小扩展为准，不创建两个竞争颜色字段。

### 14.5 各端与验收要一起修

| 部位 | 待改内容 | 为什么不能只修一处 |
|---|---|---|
| `import-pptx.mjs` 新增文本分支 | 缺省不再强制白色；输出显式 no-fill | 本截图的直接修复点 |
| `import-pptx.mjs` 原生对象样式 patch | 缺省继续保留；显式清除才 no-fill | 不损坏已有模板色块，并支持后续清除操作 |
| `PptCanvas.tsx` | 文本和 shape 都根据 resolved fill 显示；不能把 text 的显式 fill 一概忽略 | 当前文字白底缺省虽透明，显式填充的文字仍有预览一致性风险 |
| `exporters/preview.mjs` 与实际 PDF 路径 | 使用同一填充解释，继续透明穿透底图 | 避免 SVG、原生 PPTX/PDF 又分叉 |
| `command-schema.mjs` / `types.ts` | 若增加明确 clear 操作，同步类型、白名单和兼容校验 | 不能前端有“无填充”而后端不接受或丢弃 |
| 颜色/背景检测 | 文字对比度使用实际下层背景，不是无条件页面纯色 | 文本可能位于图片、渐变、卡片之上 |
| Export verifier / manifest | 比较 fill 意图与 OOXML 实际状态，识别意外白底 | 文字、位置和页数完全正确也可能出现此视觉错误 |

不要仅比较文本框与页面背景色是否相同。无填充文字在照片上没有单一背景色；应验证无填充的真实输出意图，像素采样只作辅助。若采样，选字形之外的框内区域及框旁同一底图区域，避免将抗锯齿、文本字形或图片纹理误报为底色错误。

### 14.6 对已生成项目如何处理

对当前项目，先从实际 node/provenance 识别 23 个新增导航文本，再在修复后的渲染策略下重新生成 PPTX/PDF。文字、来源、N、公式、表行和用户几何均不需要因这个问题重写。

重新导出要使旧的 renderer/export cache、renderHash 及相应验证证明失效，不能修改导出器后仍返回旧白底缓存。通过新验证后产出可追溯的新 artifact/revision，保留原交付文件作为历史，不直接覆盖旧归档文件冒充同一次验收。

不在旧项目上批量搜索 `FFFFFF` 替换为背景色；用户自己添加的白底副标题、已有品牌框和表格白行都可能合法。默认只修系统新增、没有显式填充意图的对象；其余对象遵循原生样式/用户编辑合同。

### 14.7 需要的 fixture 与实际导出检查

### 16.1 测试中发现并修正的问题

- 新 prose graph 在 selection 编译时原先会被旧的段落/流程降级逻辑覆盖；现在先验证合法图投影并保留，等材料化后再独立审核，不能用早于 outline 的 ASCII 审核代替。
- 图内的 `$+1$` 等文字经过 rich math 投影后，与原始字符串直接对比会误报丢字；改为同时比对可见文本和数学树，并拒绝陈旧 rich/plain 字段不一致。
- DAG 容量原先把各层最高节点高度乘以所有层，造成假溢出；改为逐层真实高度求和，并检查最终安排框和连线。并列组允许末个重要条件占整行。
- 原生模板容量探测与实际绑定使用相同合法原型修复；不因方向型原型不可镜像就禁止完整复用该原型。已写入/接受/锁定页面仍受保护。
- range 编辑从 textarea 转焦点到 AI 输入框时，未改变的正文不应先提交一次修改；现在空变化是 no-op，避免刚冻结目标就人为产生版本冲突。
- 工作区 SSR 尚未 hydration 时按钮看起来可点但无处理器；hydration 前主区 inert，并以明确交互状态开始实际浏览器验收。
- 非 Office 备用呈现把 `\\binom{N}{k}` 误写成分数斜线；改为 `choose` 组合记法，Office 中仍保留原始 OMML。
- 新窗口/端点媒体使紧凑 18 页暴露等宽列搜索不足：三组件只试等宽列，五段区间窄于可读下限。补充保持阅读顺序及 atomic groups 的不等宽列搜索，实际 40%/60% 布局可在原字号容纳；确认前的精炼说明仍维持数值及必要条件；没有修改来源、删已选行、缩小到不允许字号或自动增加页数。具体通过证据见最终验收记录。
- 首次浏览器测试在生成阶段因测试客户端 30 秒查询超时结束，任务实际继续完成；保留同一项目后完成了局部改稿、版本恢复和实际重导出。后续测试记录有限超时/HTTP重试，不把传输失败当成任务失败或自动新建任务。
