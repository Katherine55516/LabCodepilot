## 0. 一句话

在 v1「自动沉淀 + 全量一键重跑」之上，对标成熟测试管理产品补齐**回归执行骨架**（轮次实体、环境选择、失败复测、套件化选例）与**报告可读性**（按来源任务分组、轮次对比），再用自有执行引擎做竞品普遍缺失的**健康度治理**与 **AI 原生能力**（就地复核、失败归因、变更选例）形成差异化。

## 1. 现状：v1 已有什么、缺什么

v1（2026-07-08 完成，批 A-E + B3）已实现：用例设计完成后自动把 `tags` 含「回归测试」的用例 upsert 进项目级 `AI_LabTest/testCase/回归用例库.json`（按来源任务溯源、幂等）；库弹窗查看/移除；跨任务一键重跑（聚合 → 复用执行+报告机器 → 发版红线）；AI 推荐回归集可视化审阅；审计三动作。

v1 自记与本次摸底发现的缺口（详见 §3 矩阵）：

- **重跑产物覆盖**：同环境再跑直接覆盖上一轮 `run.json`，无轮次概念，历史丢失；
- **报告平铺**：runId 命名空间化后平铺呈现，idMap 反解能力已具备但未消费，「哪个功能的回归挂了」看不出；
- **环境硬编码**：`runLibrary` 写死 `env:'local'`，发版回归无法打 staging；
- **只能全量**：无法只跑 P0/某模块/上轮失败；
- **无治理**：无检索过滤、无 flaky/长期失败/stale 标记，库有变僵尸清单风险（insights 自记）；
- **信任缺口**：AI 打「回归测试」标签的准确度未验证，用例却直通可执行池；
- **交付断点**：tech-debt #13——打包版执行步跑不起来（@playwright/mcp 不在 asarUnpack + Chromium 未随包），库功能再好也触达不了打包用户；
- 另发现一个样式 bug：库弹窗删除按钮用了未定义的 `status-danger-*` token（全局只有 `status-error-*`），危险色 hover 静默失效（已建独立修复任务）。

## 2. 竞品调研撷要（谁的什么值得抄）

| 产品 | 核心可借鉴设计 |
|------|----------------|
| **TestRail** | ① Case→Test→Result 三层分离：结果挂「轮次实例」而非用例本身，append-only；② **Dynamic Filter**：回归套件=保存的查询，新命中用例自动入列；③ **Rerun**：按上轮状态（Failed/Blocked）一键重建复测轮；④ **Close 即快照**：关轮时归档当时的用例内容，历史报告永远可信；⑤ Comparison for Cases：用例×轮次矩阵报告；⑥ 评审流 Design→Review→Ready，只有 Ready 可入回归池 |
| **Xray / Zephyr Scale** | ① 库与执行严格分离 + 每轮执行快照用例内容；② Test Plan 合并「每用例最新状态」，按状态一键生成只含失败用例的下一轮——**回归收敛环**；③ 用例显式版本化并与执行绑定；④ 需求覆盖状态 OK/NOK/UNCOVERED 由最新执行实时推导 |
| **MeterSphere / 禅道** | ① 「复制上一轮计划」是最低成本轮次化；② 等级 P0-P3 + 适用阶段多选直接驱动选例；③ 失败一键转 Bug 自动拼重现步骤；④ Excel/Xmind 双向导入导出是国内团队入场券；⑤ 共同短板：无动态套件（社区明确痛点「852 条只想跑 P0 的 502 条」）、无 flaky 治理——**我们的差异化空间** |
| **Azure Test Plans / PractiTest / qTest** | ① **Query-based Suite**：查询即套件、自动同步、内容只读；② Configurations 环境矩阵（变量→命名配置→自动乘出 test point）；③ **flaky 全闭环**：同版本重跑翻转自动标记 + 「是否计入通过率」开关；④ qTest：未审批不可执行的版本门禁；⑤ PractiTest filter-tree：用例不入固定目录、靠动态过滤视图组织 |
| **方法论趋势** | ① 回归分层三档：快速子集（变更影响+上轮失败+新增）/风险加权/发版全量，核心用例白名单永不被裁剪；② **逐用例执行历史是一切智能治理的地基**，schema 一次设计到位；③ quarantine 状态机：隔离但夜间续跑、稳定复归、30 天不修则退役；④ AI 介入点：自动选例、self-healing（带置信度闸门+审计）、语义去重、失败归因 |

## 3. 能力对标矩阵（成熟产品 vs 当前 v1）

| 能力 | 成熟产品普遍做法 | 当前 v1 |
|------|------------------|---------|
| 用例组织与检索 | 目录树/过滤树/双维度视图，任意字段过滤排序 | **部分**：仅按来源任务分组平铺，无搜索无过滤（module/priority 字段已有但未消费） |
| 用例字段与模板 | 模板决定表单 + 结构化步骤 + 共享步骤 | **基础较好**：steps[]{content,expected} 等字段齐备，缺模板管理，字段不参与过滤 |
| 用例版本与变更 | 逐字段 diff + 版本号 + 执行绑定版本 | **缺失**：upsert 直接覆盖，AI 改写后历史不可追 |
| 生命周期与评审 | Design→Review→Ready，未批准不可执行 | **部分**：推荐审阅弹窗已有，但入库后无 reviewState，AI 打标直通执行池 |
| 静态套件 | 树形勾选固化清单 | **缺失**：只有隐式全量 |
| 动态套件（保存的查询） | Azure Query-based / TestRail Dynamic Filter | **缺失**：唯一「查询」是硬编码的回归标签 |
| 计划与执行轮次 | Plan→Run→Test 实例化，结果挂轮次 | **缺失**：无轮次实体，同环境重跑覆盖上一轮 |
| 失败复测环 | 按上轮状态一键重建复测轮 | **缺失**：只能全量重跑 |
| 环境配置矩阵 | 变量→命名配置→套件指派 | **缺失**：env 硬编码 'local' |
| 执行历史与趋势 | append-only 结果 + 用例×轮次矩阵 + 常败榜 | **缺失**：只有最新一轮聚合 |
| 健康度治理 | Azure flaky 闭环；其余产品也普遍缺失 | **缺失**（行业空白 = 差异化机会） |
| 需求/缺陷追溯 | 覆盖状态实时推导 + 失败一键转 Bug | **部分**：requirement 字段已有，缺覆盖视图与缺陷实体 |
| 报告分组与轮次对比 | 按模块/文件夹分组下钻 + 轮次 delta | **缺失**（handover 自记）：平铺 runId，无上轮对比 |
| 导入导出 | Excel/Xmind 双向 | **缺失**：导出未做（i18n 键已预置），无导入 |
| 执行快照审计 | Close 即快照，防篡改 | **部分**：审计 JSONL 已有；聚合 cases.json 每轮被覆盖，无内容快照 |
| 自动化↔用例绑定 | automation_id 双向匹配 | **已领先**：AI 按 cases.json 逐条执行，用例即脚本输入，无需照搬 |

## 4. 缺口分级

**P0（直接影响「发版前跑一遍回归」核心闭环）**

1. 无执行轮次实体，同环境重跑覆盖历史，无法回答「这轮比上轮多挂了什么」；
2. 重跑报告不按来源任务分组（idMap 已具备未消费）；
3. 重跑环境硬编码 local，发版回归打不了 staging/预发；
4. **tech-debt #13 打包版执行步不可用**——批判代理判定：这是 v2 触达真实用户的前置条件，应定为**一期硬门槛**而非「并行推进」，否则一期闭环只对源码用户成立。

**P1**：失败复测缺失；库无检索过滤；无轮次用例快照（AI 高频改写下执行历史可信度缺地基）；健康度治理空白；回归集只有全量单一口径；评审门禁缺失；**复测轮红线合成口径**（批判新增：复测轮 2/2 通过≠可发版，需按合并最新状态评估）；**缺陷结构化闭环**（批判新增：失败→缺陷→修复→复测→关闭的链路完全缺失，回归的终点是缺陷被修掉而非报告）。

**P2**：导出/导入；需求覆盖视图（批判指出字段现成、成本极低）；保留任务名冲突校验；status-danger token bug（已建独立任务）；轮次产物磁盘保留策略（批判新增：每轮截图/trace/快照无限膨胀）。

## 5. v2 方案：四大支柱

设计红线（全部尊重 v1 既有决策，只叠加不推翻）：入库不看执行结果、upsert by 来源任务、项目级作用域、复用执行+报告机器、**本地文件型**（JSON 落项目目录，不引入中心服务）。

### 支柱一：套件与轮次（回归执行骨架）

| 功能 | 要点 | 优先级/工作量 |
|------|------|---------------|
| 执行轮次实体化 | 新增 `testCase/.data/回归轮次.json` 索引（roundId/时间/env/套件/模式/counts/**status: running·done·aborted·partial**/parentRoundId）；产物改落 `report/回归用例库/{roundId}/` 子目录；reports 扫描兼容。归约逻辑零改动只改落点。**中断态明确定义**：应用退出/断流的轮标 aborted，残轮在对比矩阵与 stats 中默认排除（批判修正） | P0 / M |
| 重跑环境选择 | 弹窗 env 下拉读项目 `environments.json`（带可达性状态点），去掉硬编码；复用 env 解析/可达性闸门/NO_CREDENTIALS 链路。**执行前预检卡**：将执行 N 条、涉及 M 任务、**预计时长与 token 消耗估算**（按近 3 轮均值）（批判修正） | P0 / S |
| 失败复测 | 轮次行「复测 N 条失败」：读该轮 run.json 失败集 → idMap 反解 → `buildRunnableCases` 加 include 过滤 → 其余全复用；新轮 mode=failed-only、parentRoundId 串链。**红线合成口径**（批判修正）：复测轮不单独给可发版结论，按「与上一全量轮合并后的每用例最新状态」评估（Xray Plan 语义） | P1 / M |
| 回归套件 | 新增 `testCase/回归套件.json`：静态勾选 + **保存的查询**（AND 组合、命中实时预览、内容只读只改条件）；内置「全量」=v1 行为向后兼容；**核心必跑白名单（pinned）**：任何套件/复测模式始终并入。**用户拍板提至一期**：条件字段一期先做 优先级/模块/来源任务/上次结果（上次结果由一期轮次实体提供），「评审态」条件待二期门禁落地后启用 | P0 / M |
| 打包版执行可用性 | tech-debt #13：@playwright/mcp 入 asarUnpack + Chromium 随包/首启下载。**定为一期硬门槛**，纳入打包验收 | P0 / L |

### 支柱二：检索、报告分组与轮次对比

| 功能 | 要点 | 优先级/工作量 |
|------|------|---------------|
| 库检索与多维过滤 | 搜索（ID/标题）+ 来源任务/模块/优先级/评审态/健康度过滤 + 排序；纯前端内存过滤 API 零改动；弹窗扩宽加列；顺手修 status-danger token bug | P0 / S |
| 报告按来源任务分组 | 消费 idMap：reduce.ts 按 `_source.task` 出 taskCounts 小计入 run.json；报告 md prompt 按任务分节；前端折叠分组 + 组通过小计红绿 badge | P0 / S |
| 轮次 delta 摘要 | 报告顶部三卡：较上轮新增失败/已修复/持续失败（对比上一**全量**轮），点击过滤列表。批判认定 delta 卡覆盖 80% 发版决策价值，优先于矩阵 | P0 / S |
| 轮次对比矩阵 | 行=用例（按任务分组）× 列=近 N 轮，色块 + 翻转/连败派生列；`GET /api/test/library/rounds` 只读拼装。批判建议后置——排二期末，delta 卡先行 | P1 / M |
| 库导出 xlsx | 复用 report-xlsx 通路（i18n 键已预置）；国内团队「发钉钉/给领导看」刚需 | P2 / S |

### 支柱三：版本快照与信任治理

| 功能 | 要点 | 优先级/工作量 |
|------|------|---------------|
| 轮次用例快照 | 每轮把聚合 cases.json 复制为 `{roundId}/cases.snapshot.json`——TestRail「Close 即快照」的本地版，一次文件拷贝换执行历史永远可信 | P1 / S |
| 入库版本号 | LibraryEntry 加 `rev`（自增）+ `updatedAt`。批判修正：**字段级 diff 时间线降级**——AI 是唯一改写者，「谁改了哪个字段」审计价值低，rev + 轮次快照对照已够，省出 M 级工作量 | P1 / S |
| 评审轻门禁 | entry 加 `reviewState`：自动入库默认 pending（不改自动入库决策）；推荐审阅通过/库内单条/批量确认置 approved；发起弹窗「仅执行已确认」开关。批判修正：开关默认关（兼容），但弹窗**显性展示 pending 占比**并提示先评审；**存量 entries 迁移默认回填 approved**（老用户开开关不至于空集） | P1 / M |
| 保留任务名冲突校验 | 新建任务/导入入口拦截 `回归用例库` 同名；补记 tech-debt 条目 | P2 / S |
| 手工/混合执行兜底 | 批判新增：AI 执行不了的用例（需人工判断/短信验证码）提供「人工标记本轮结果」入口，结果与自动执行同轮归约——否则红线永远只是「可自动化子集的红线」 | P1 / M |

### 支柱四：健康度治理 + AI 原生差异化

| 功能 | 要点 | 优先级/工作量 |
|------|------|---------------|
| 逐用例执行历史 | 轮次完成后把 {roundId, env, result} 追加进 `回归用例库.stats.json`（每用例环形近 20 轮）；这是 flaky/stale/趋势/复测的唯一数据源。**轮次产物同步定保留策略**（默认保留近 20 轮目录，超出归档/清理，与 stats 口径一致——批判修正） | P1 / M |
| flaky / 连败 / stale 标记 | 读取时派生：翻转≥阈值→疑似 flaky；连续失败≥3→长期失败；久未跑/从未跑→stale。**批判修正——跨轮翻转≠flaky**（版本在变，翻转常是「真回归又被修」）：跨轮翻转只出「疑似」，**终判靠 AI 就地复核**（同版本连跑 3 次），把 Azure 被动检测变主动实验 | P1 / M |
| 隔离区 quarantine | 一键隔离/人工恢复；聚合排除且不计红线。**滥用护栏**（批判修正）：报告横幅强制显示「隔离中 N 条未计入」，隔离占比>10% 顶部告警；连续失败默认建议**转缺陷而非隔离**（防用隔离掩盖真回归） | P2 / M |
| AI 失败归因 + 缺陷闭环 | 报告步 prompt 扩展：失败用例附 stats 历史，AI 输出归因（产品缺陷/环境/用例过时/疑似 flaky）+ 建议动作，结构化写入 run.json；**失败一键转缺陷**：AI 拼重现步骤+截图+环境生成结构化缺陷记录（本地 JSON，后续可经 MCP 直连禅道/Jira），复测通过自动提示关闭——补上批判指出的「回归终点是缺陷被修掉」 | P1 / L |
| 用例自愈（远期） | 归因为「用例过时」时 AI 直接生成修订建议一键应用并升 rev；带置信度闸门 + 审计，核心用例强制人审 | P2 / L |
| 变更驱动选例（远期） | 产品跑在开发者桌面、天然拿得到 git diff：AI 读改动圈出受影响回归子集——TestRail/MeterSphere 结构性做不到的硬差异化 | P2 / L |
| 语义去重（远期） | 跨任务沉淀必产生语义重复（不同任务的「登录成功」），入库时 embedding 相似度提示合并——治「库变僵尸清单」的本 | P2 / M |

### 明确不做（为对标而对标、本地文件型不成立）

- 多测试库/Baseline 分支（TestRail 自己都不推荐，桌面单项目场景无收益）；
- 工作项化/中心服务端实体模型（Azure 模式，与本地 JSON 架构冲突）；
- 深度 Jira 双向实时同步（初期无必要，缺陷闭环先落本地实体）；
- 字段级 diff + 选择性还原（AI 单一改写者场景 ROI 低，rev+快照替代）。

## 6. 分期计划

**一期：可信可圈选的发版回归（最小闭环，可独立交付）**
不动入库机制，把「发起一轮回归」做到可信、可读、可圈选、可选环境：
轮次实体化（含中断态）→ **回归套件（静态勾选 + 查询套件构建器 + pinned 必跑，用户拍板提前）** → 发起弹窗重做（套件/环境/模式三选 + 预检：条数/时长/token 估算）→ 报告按任务分组 + delta 三卡 → 库检索过滤 → 轮次快照 → token bug 修复。
**硬门槛**：tech-debt #13 打包版执行可用（否则一期只对源码用户成立——如接受此限制需在验收结论中如实标注）。

**二期：回归收敛环与信任治理**

## 8. 原型说明

七屏可交互（mock 数据、亮暗双主题、每屏带「对标出处/分期」标注，可一键关闭标注）：

1. **库总览**（一期检索过滤 + 二期评审/批量 + 三期健康度徽标 + 详情抽屉：字段/步骤/rev 时间线/执行历史点阵）
2. **回归套件**（内置全量🔒 / 静态 / 查询三型，条件构建器 + 命中实时预览 + pinned 白名单）
3. **发起回归**（套件/环境/模式三选 + 仅已确认开关 + pending 提示 + 时长/token 预检 + 复测轮合并口径提示；「开始执行」可模拟跑完一轮落进轮次历史）
4. **轮次历史**（轮次表 + 通过率迷你趋势 + 复测轮「合并 13/14」红线 + 报告/复测/快照操作）
5. **轮次报告**（红线横幅含隔离曝光 + delta 三卡可点击过滤 + 按来源任务折叠分组 + 失败行 AI 归因/转缺陷/证据）
6. **对比矩阵**（用例×7 轮色块 + 翻转/连败派生列 + 只看失败行开关）
7. **健康度**（指标卡 + flaky/连败/stale 三队列各带动作 + 隔离区与护栏说明）

浏览器打开 `docs/research/prototypes/regression-library-v2-prototype.html` 即可体验（无外部依赖）。

## 9. 决策记录与待拍板问题

**已拍板（用户 2026-07-09）**：
- **模块不做独立功能**：不建模块树、不做模块管理 UI、不做模块维度报告。`module` 仅保留为用例既有字段（AI 生成时自动填，零成本），用作库检索过滤和查询套件的条件字段之一。「按范围圈选执行」统一由**套件**承担（查询套件按模块/优先级等条件圈，静态套件手工圈），不再引入第二套组织概念。
- **回归套件是核心功能，提至一期**（P1→P0）：与发起弹窗重做同批落地避免返工；套件只依赖库本身，无轮次数据依赖。一期条件字段=优先级/模块/来源任务/上次结果；「评审态」条件随二期门禁启用。轮次保持原子性（一轮=一套件×一环境×一模式），多套件诉求用并集套件解决，未来高频再评估「批次」容器。

**待拍板**：

1. 一期是否接受「tech-debt #13 为硬门槛」（影响一期工期，但决定交付对象是打包用户还是源码用户）；
2. 复测轮合并红线口径确认（推荐 Xray 合并语义）；
3. 评审门禁存量迁移默认值（推荐存量回填 approved、新入库 pending）；
4. 缺陷实体先落本地 JSON 还是直接对接禅道/Jira（推荐先本地）。
