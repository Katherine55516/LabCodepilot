# 测试报告就地展示 —— 让「跑完」和「看见结果」在同一处

> 技术实现见 [docs/handover/test-report-inline-display.md](../handover/test-report-inline-display.md)

## 用户问题

测试工作台跑完四步后，「测试报告」节点显示「已完成」，但流程页那块详情卡只有一行占位字「详细执行过程见下方对话 ↓」——**完成了却看不到报告**。真正的报告藏在另一个独立的「报告」Tab 里，用户要切走才能看，断了「跑任务 → 看结果」的连续心流。

附带两个老问题：
- **缺陷报告不够「可定位」**：给开发的缺陷单缺结构化的接口信息（方法/URL/状态码/请求体/响应体），开发拿到难复现。
- **证据只有截图**：失败现场没有过程录像，靠几张截图难还原操作序列。

## 设计决策（都由原型逐项确认驱动）

这个功能没有一上来写代码，而是先出 5 份原型、逐项跟用户确认，再分阶段实现。关键取舍：

1. **就地展示用「混合式」**：概览条 + 产出资料列表 + 内嵌报告全文。
   - 「产出资料」列表参照用户给的参考截图（ai-lab-test-framework 的「本步产物 · 点开修改」），但**渲染器复用已有的** `ReportView` / `ReactMarkdown`——既满足「展示报告」，又不重造轮子。
   - 没有把整张逐用例结果表塞进面板（内嵌全文里已有失败明细），避免面板过高。

2. **md 预览 = 渲染 + 可编辑**：测试报告/缺陷报告点开是 markdown 渲染，可切「编辑」就地改并存回。复用 CodeMirror 编辑器（与 Skill 编辑同一套），因为自动生成的报告常需人工补注。

3. **Excel 预览 = 表格、只读**：xlsx 是从 markdown 派生的可选交付物，要改应改源头，故只读 + 导出，不做单元格编辑。

4. **缺陷报告 = 逐条结构化模板**，含接口信息子项。这要求接口数据真能采到——

5. **接口信息走「执行阶段结构化采集」**（而非生成时现采或 best-effort）。理由：只有在执行现场用浏览器的 network 能力抓到失败请求，缺陷报告里的接口字段才可靠不为空。代价是把改动从「报告展示」扩到「执行管线 + run.json schema」，用户明确选了「最可靠」。

6. **证据加录像，且关联到具体用例**。发现 `@playwright/mcp` 原生支持 `browser_start_video`/`stop_video` 且能按 filename 命名——于是**每条用例录一段、命名成 `{用例ID}.webm`**，天然挂到该用例；媒体接口本就支持 webm + 拖动播放，证据列里直接点开看。

7. **录像只留失败 + 部分通过**。每条用例都录（失败与否要跑完才知道），但 pass 段丢弃、只保留 fail/partial——在「证据完整」与「存储/耗时」之间取平衡，由用户拍板。

## 为什么这样而不是别的

- **不只列文件、也不只渲染全文**：纯文件列表不够「展示报告」，纯全文又丢了「产出物可下载/可改」的操作性，混合式两头都顾。
- **不另起新组件渲染报告**：`ReportView` + markdown 渲染早已存在且在「报告」Tab 用着，复用保证两处口径一致（尤其功能验证通过率的 oracle 双轴口径）。
- **不在缺陷报告生成时才去抓接口**：那时浏览器现场已散，重开页面复现失败既慢又可能复现不出；执行现场采集是唯一可靠点。

## 已知局限与未来方向

- **录像起停需真跑验证**：本地 CDP 用 mock 验证了 UI 全链路；录像/接口的真实采集要一次带失败用例的真执行来确认（也是录像能力的 POC）。若 MCP 不支持「丢弃 pass 段」，退化为平台侧清理未引用录像。
- **接口体脱敏**：请求/响应体可能含 token/密码，目前只截断不脱敏，是下一步要补的安全项。
- **Excel 按需**：只有用户要过「导出 Excel」才有 xlsx，故产物列表里 Excel 行「存在才显示」。
- **未来**：录像章节标记（`browser_video_chapter`）做「一段会话录像 + 按用例跳章节」的备选形态；大报告的懒渲染；缺陷报告一键带接口信息回放。
