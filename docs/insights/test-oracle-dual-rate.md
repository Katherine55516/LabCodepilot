# 测试质量：为什么要 oracle 双轴 + 双口径通过率

> 技术实现见 [docs/handover/test-oracle-dual-rate.md](../handover/test-oracle-dual-rate.md)
> 上游方案见 [docs/research/framework-flow-test-integration.md](../research/framework-flow-test-integration.md) §2.1

## 解决的用户问题：AI 测试最危险的「自我证明」

AI 自动化测试有一个隐蔽但致命的陷阱：**当被测对象和判分标准（oracle）同源时，测试只是在复述代码现状，永远 pass，却看起来像"验证通过"**。

具体到本平台的流程：需求分析阶段，若没有 PRD，AI 会「从代码反推需求」（`REVERSE_ENGINEERED`）。这本身没问题——但如果用例的「预期结果」也来自同一份代码，那么：

- 预期 = 代码现在的行为
- 实际 = 代码现在的行为
- 结果 = 永远相等 = 永远 pass

这种用例**发现不了任何「代码与意图不符」的缺陷**，因为它根本没有「意图」作参照，只有「现状」。可它跑出来是绿的，报告里写「通过率 100%」，使用者会误以为「功能验证通过、可以发布」——实际上一个真正的功能验证都没做。这是 AI 测试比人工测试更容易踩的坑：人知道自己在「照抄现状」，AI 不声明就分不清。

## 设计：用两根独立的轴拆开「覆盖维度」和「验证性质」

framework 的方法论给出的解法是 **oracle 双轴**，我们把它落进了平台：

- **用例类型**（覆盖维度）：正向/异常/边界/状态转换/权限/业务规则/数据一致性/用户体验——回答「测了哪种场景」。
- **验证性质**（oracle 性质）：**功能验证** vs **回归基线**——回答「这条用例在验对错，还是只锁现状」。

| | oracle 来源 | 作用 | 红线 |
|---|---|---|---|
| **功能验证** | PRD/设计稿/API契约/产品确认（应然） | 抓「代码≠意图」的缺陷 | — |
| **回归基线** | 现状锁定（代码反推/照抄 UI 现状） | 锁定当前行为、防未来回归 | 报告里**不得**说「功能正确/验证通过」，只能说「现状已锁定、无回归」 |

承接需求来源做映射：`USER`/`PROJECT_DOC` → 功能验证；`REVERSE_ENGINEERED`（未经产品确认）→ 回归基线。回归基线不是没价值——它防回归——只是**不能冒充功能验证**。

## 双口径通过率：不让回归基线虚抬数字

有了验证性质，报告就必须分两个口径报通过率，否则前面的区分白做：

- **功能验证通过率** = 功能验证 pass ÷ 功能验证总数（回归基线**不计入**）——这才是「功能对不对」。
- **执行通过率（参考）** = 全部 pass ÷ 全部（含回归基线）——只说明「跑通了多少」，不代表功能正确。

**铁律**：一个模块若用例全是回归基线，功能验证通过率记 `N/A（仅锁现状）`，**禁止报「100% 通过」**。这一条直接戳破上面那个「自我证明」陷阱——没有权威需求来源时，平台会诚实地说「我只锁了现状，没验证对错」，而不是给一个虚假的安心。

这个口径我们放在 `reduce.ts` 用**代码确定性计算**（不靠 LLM 汇报），和既有「四态计数由代码算」的诚实数据原则一脉相承：通过率是会被用来做发布决策的数字，不能让模型有再解释的空间。

## 为什么需求自审「内化」而不是做成独立一步

framework CLI 是 6 步，需求评审是独立的 Step3（产 `review.json` + 4 维评分 + 强制用户交互补缺口）。但 framework 自己的桌面 app（`requirements.js`）把它**内化**成了需求生成的第二趟自审——不产评审报告、不打断用户。

LabCodepilot 跟 app 走，理由：

1. **平台是非交互的**。4 步流程是「生成产物 → 用户门控审阅/批准」，AI 步内部无法向用户提问。CLI 那套「发现缺口就追问用户」在这里跑不通。
2. **不增加用户认知负担**。多一个「评审」步 = 多一道 gate、多一份要读的 review.json。内化成自审后，用户感知到的还是「需求 → 用例 → 执行 → 报告」四步，只是需求质量更高了。
3. **评审的价值在「修订」不在「评分」**。一个 75 分的评审报告对自动化流程没用——AI 真正该做的是把发现的模糊措辞、缺失的异常分支、非原子需求**直接改好**。所以自审趟的产物是「修订后的干净需求文档」，不是评分。

代价：规则文件（`requirement-review.md`）里 CLI 独有的「强制交互/产 review.json」内容仍在，靠 prompt 显式声明「本平台跳过这些」来压制——这是「保持规则与 framework 权威原文一致、便于 upgrade」与「行为贴合平台」之间的取舍。

## 已知局限与未来方向

- **效果依赖 AI 标对 oracle**。整套机制的前提是 AI 在用例阶段如实标注验证性质。prompt 给了明确的映射铁律，但「代码反推的用例有没有被诚实标成回归基线」需要在真实项目里观察——这是纯方法论改造，dev 本地无模型跑不出真实结论，要打包态 + 真实项目实测校准。
- **门控可以更强**。目前全回归基线只在总结里提示用户「建议补权威需求来源」。未来可在用户门控层做成显式 gate（如全回归基线时高亮警示、引导上传 PRD）。
- **回归基线的正向价值还没用足**。它本是「防回归」的基线，未来配合「报告多版本对比」（方案第三批），可以做「这次相对上次有没有回归」的 diff——那才是回归基线的主场。
