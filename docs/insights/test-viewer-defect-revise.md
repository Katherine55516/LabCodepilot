# 报告查看器 + 缺陷报告 + 对话式修订：为什么这三项

> 技术实现见 [docs/handover/test-viewer-defect-revise.md](../handover/test-viewer-defect-revise.md)
> 上游方案见 [docs/research/framework-flow-test-integration.md](../research/framework-flow-test-integration.md) §四第一批

framework 集成方案第一批的剩余三项。它们不改测试主干，而是补齐「测完之后怎么看、怎么交付、怎么改」——把工作台从「能跑出结果」推进到「结果可用、可交付、可迭代」。

## 报告查看器：QA 看报告是看证据，不是看文件名

执行阶段每条用例都截了图（甚至录像），落在 `_evidence/`。但报告此前只把证据显示成一串文件名文本——`TC-001.png, TC-002.png`。对 QA 毫无用：判断一个 fail 是不是真 bug，得**看那张截图**；定位一个交互问题，得**看那段录像**。

所以把证据列从文本升级为缩略图（点开 lightbox 看大图）+ 录像内联 `<video>`。技术上 Next 不像 framework 能用 Electron 自定义协议，改用一个白名单 media route——这里的关键不是功能而是**安全**：证据路径来自磁盘，必须严格锁死在项目的 `_evidence/` 目录内，`../` 穿越要被挡掉（实测 `../../etc/passwd` → 404）。视频支持 Range 是为了能拖动 seek，不必为看中间一段下载整个录像。

## 缺陷报告：测试报告和缺陷单是给两拨人看的

测试报告是给**测试侧**的：四态、通过率、覆盖矩阵、失败分类。但开发要修 bug，需要的是另一种东西——一张**缺陷单**：怎么复现、预期什么、实际什么、怎样算修好。把这两者揉进一份文档，对谁都不好用。

所以缺陷报告是独立的「第三交付物」。它最关键的不是格式，而是**边界**——守 QA 铁律：

- 只挑 `status=fail` 且确属应用 bug 的用例（测试 bug / 环境问题 / flaky / blocked / pass 都不写）；
- 「修复要求」只写**期望行为 + 验收标准**（怎样算修好、怎么验证），**绝不**写修复方案 / 改哪行代码 / 优先级 / 是否发布 / 指派责任人。

这条边界是 QA 与开发 / 产品的分工线：QA 给事实和验收口径，**怎么修是开发的事、修不修是产品的事**。缺陷报告员 prompt 把这条线写死，避免 AI 越界替开发做技术决策。

## 对话式修订：把「追加指令」和「改当前产物」分开

工作台此前的 composer 只有一个动作：把你输入的话当「追加指令」存起来，喂给**下一步**的 prompt。这解决不了一个很常见的需求——**生成的需求 / 用例就差一点，想直接改它**。重跑整步太重（且会重新生成、丢掉你已认可的部分）。

所以加了「修订」：让 AI 读**当前**产物 + 按你的指令精准改写并覆盖，只动该动的部分。它和「追加指令」是两个正交动作，composer 里并存：

- **发送**（追加指令）→ 记一笔，喂下一步；
- **修订** → 改当前产物。

「修订」按钮只在能改的步（需求 / 用例，且产物已生成）出现，hint 文案讲清区别——避免用户混淆"我这句话到底改了什么"。执行结果（run.json）和报告不走修订：前者是确定性归约的产物、后者可一键重新生成，对话改它们没意义。

## 设计取舍与局限

- **三项都解耦、不动主干**：各自一个 route + 一处 UI，可独立增量上线，风险低。报告浏览的三 tab（结果 / 对比 / 缺陷）复用同一展开区，互不干扰。
- **缺陷接口信息暂缺**：缺陷单本该带失败用例的接口请求 / 响应（最利于开发定位），但执行阶段还没抓 `tests[].api`，目前只能标「未捕获」。补抓是后续硬化项——它会显著提升缺陷单对开发的价值。
- **AI 部分需真实模型**：缺陷生成、对话修订的 AI 执行在本地无凭据环境跑不通，逻辑靠 typecheck + 复用既有流式模式保证，效果待真实项目校准。
- **录像看执行是否真产**：播放器和 Range 都就绪，但有没有录像取决于执行阶段 Playwright 配置（当前以截图为主）——能力先备好，数据随执行增强而来。
