# 主进程文件日志 — 产品思考

> 技术实现见 [docs/handover/file-logging.md](../handover/file-logging.md)
>
> 相关：[insights/credential-encryption.md](./credential-encryption.md)（同样的「只保护磁盘产物、内存/管道明文是设计内」诚实边界）

## 解决什么用户问题

起因是一个真实排障：有同事用打包版时,所有模型(GLM5.1、deepseek-v4-pro…)都报「Claude Code process exited with an error」,重启、换模型都一样,而别的同事正常。这条报错其实是 `error-classifier.ts` 对「子进程非零退出」的**固定兜底文案**——里面那串「API Key / Base URL / Network」是写死的猜测,不是真实诊断。真因(退出码 + stderr)被捕获了,却**只 `console.log` 到一个打包版看不见的地方**:

- 捆绑的 Next 服务是 `utilityProcess` 子进程,stdout/stderr 经管道回传给主进程;
- 主进程把它 `console.log` 出来,但打包版主进程**没有终端接管**,等于丢弃;
- 应用从不写日志文件。

于是用户/支持只能靠「让同事从终端启动 app 重定向输出」这种极客操作才能拿到真因。**「线上崩了却没日志可查」是个硬伤**——这份功能就是补上它:让任何用户一键拿到可发出来的诊断日志。

## 为什么这样设计

**① 汇聚在主进程、包裹 `console.*`,而不是各进程各写一份。**
主进程本来就 re-`console.log` 服务端管道输出,所以包裹主进程 console 一处,就同时拿到主进程自身日志 + 整个 Next 服务输出,**零侵入服务端代码**。一个文件、一个咽喉点脱敏,远比三个进程各维护一个 logger 简单且不易漏。

**② 同步写 (`appendFileSync`) 而非异步缓冲。**
这个日志存在的全部意义是「捕获崩溃前那几行」。异步缓冲流在硬崩溃时会丢掉缓冲区——恰恰是最该留下的内容。同步写每行立即落盘,牺牲一点吞吐换「崩溃前的行一定在磁盘上」。基准实测 ~0.02ms/次,常见场景不卡 UI;真有高吞吐再做批量化(且对 FATAL/ERROR 仍同步)。

**③ 脱敏在「写盘那一刻」,且只脱密钥、保路径。**
威胁模型是「用户把日志文件发给同事/支持」——所以**保护的是文件产物**,在写盘咽喉点脱敏即可,管道/内存里短暂明文不在威胁面内(与凭证加密那份文档同一种诚实边界)。同时刻意**保留文件路径、host、git SHA**:这些正是诊断「二进制找不到 / base_url 配错」的关键,过度脱敏会让日志失去价值。这是 recall(别漏密钥) 与 precision(别糊掉有用信息) 的取舍——我们偏向「密钥用多层兜底、其余尽量留」。

**④ 用户入口放设置页一个按钮,而不是让用户去文件系统找。**
日志目录是 `~/Library/Logs/AI Native Lab/` 这种用户记不住的路径,且产品名是「AI Native Lab」而非「CodePilot」,自己找极易找错。一个「打开日志目录」按钮直接 `shell.openPath`,反馈问题时一键定位、附带发送。

## 对抗式评审驱动的修正

实现后跑了一轮多代理对抗评审(4 视角),它逼出了几个「能用但有坑」的问题,值得记录:

- **日志的崩溃监听器会静默吞掉 Sentry 的崩溃弹窗**:加 `uncaughtException` handler 把监听数顶过 Sentry 的 `<=2` 阈值,导致崩溃后用户无任何提示、app 带病存活。改用 `uncaughtExceptionMonitor`(只观测、不计数、不改退出)解决——这是「加一个看似无害的监听器却改变了既有崩溃行为」的典型教训。
- **精确脱敏一度形同虚设**:初版从 `process.env` 收集密钥,但 master key 在 logger 初始化后才生成、用户 BYOK 密钥走 `loadUserShellEnv` 从不进 `process.env`——于是最该精确脱敏的两类密钥都没被登记。改为从「真正注入服务端的合并 env」收集。
- **密钥跨管道 chunk 拆分可绕过脱敏**:按 chunk 脱敏时,一个密钥被拆到两个 `data` 事件里,两半都匹配不到。改为按完整行缓冲后再脱敏。

## 已知局限与未来方向

- **按请求注入的 provider 密钥**主进程拿不到原值,只能靠形态匹配兜底;无前缀、非 hex、低熵的密钥仍可能漏。**彻底方案**:在服务端 `runtime-log.ts` 源头用当前 provider 密钥精确脱敏后再输出,让密钥在过管道前就消失。这也会顺带让现有的服务端 console 环形缓冲更安全。
- 当前是「被动留底,用户手动打开发送」。未来可做:错误卡片直接内嵌「复制诊断信息」按钮(把最近 N 行日志 + 环境信息一键打包),把排障门槛再降一截——这是比「让用户找日志文件」更进一步的体验。
- 渲染进程目前只记 warn/error。若将来需要更全的前端行为回放,可考虑分级采样而非全量(全量会用噪音淹没真正的崩溃诊断)。
