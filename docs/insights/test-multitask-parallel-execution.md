# 测试工作台 · 多任务并行执行（产品思考）

> 技术实现见 [docs/handover/test-multitask-parallel-execution.md](../handover/test-multitask-parallel-execution.md)
> 执行计划见 [docs/exec-plans/active/test-multitask-parallel-execution.md](../exec-plans/active/test-multitask-parallel-execution.md)

## 解决什么用户问题

测试工作台原本一次只能跑一个任务，QA 要把一批模块（登录、下单、退款……）跑完，只能一个个点、一个个等。一台机器明明能同时开几个无头浏览器，却被界面强制串行。四条需求合起来就是一句话：**让一批测试任务像一条流水线那样自动跑完，机器能并行就并行，跑前别让我白跑。**

## 四个关键决策与取舍

### 1. 队列放客户端，不放服务端

服务端 globalThis 队列（参照图片批量 `job-executor.ts`）更稳——跨页面、刷新都不中断。但它要把执行步的「消费 SSE → 归约 → 落 run.json」从 HTTP 响应链里整体搬到后台 worker，再加触发/进度两条新路由，改动大、风险高。

权衡后选客户端：复用现有「逐步 SSE + 每任务 convo 隔离」的成熟链路，改动集中在一个组件，快且低风险。代价是**批量跑到一半切走测试页/刷新会中断**——和用户确认过：需求里的「后台」指的是**无头浏览器不弹窗**（已满足），不是「关掉界面还在后台跑进程」。后者真有需要，再升级服务端队列。这是「先把 80% 的价值低风险拿到手」的务实取舍。

### 2. 「后台运行」= 无头，而非后台进程

需求原文「测试执行节点默认后台运行，不弹浏览器」。代码里早就有 `headed` 全链路（默认无头），所以这一条的本质不是新建后台执行，而是**多任务时强制无头**——否则并发 3 个任务会弹 3 个 Chrome 窗口，没法看也吃资源。单任务保留「执行前确认弹窗」让用户选可见/无头（演示/观摩时有用），批量则一律无头、不打断。

### 3. 并发数放「本机设置」，不放项目环境配置

用户说「放环境配置、每人按自己电脑」。但现有「环境配置」（设置·测试账号）是**按项目存、会随 `environments.json` 导出共享**——一个人的机器并发数会污染同事的配置。并发是「这台机器能扛几个浏览器」的机器属性，不是「测哪个环境」的项目属性。所以放 `localStorage`（和「执行方式」并列），默认 2、范围 1–5。默认 2 而非更高：每个测试执行要起一个完整浏览器 + Agent，比图片批量重，2 较稳，用户按机器往上调。

### 4. 登录态预检：先做「文件存在 + cookie 过期」，不做「真起浏览器探活」

登录态在本项目就是 Playwright 的 `storageState` 文件。预检有三档：

- **(A) 文件在不在** —— 零成本，但抓不到「文件在但 cookie 早过期」；
- **(B) 文件在 + cookie 过期判断** —— 一次 fs 读 + JSON 解析，能抓过期，纯函数可单测，dev 下用 mock 文件就能验逻辑；
- **(C) 真起浏览器导航到受保护页看是否被踢回登录页** —— 最准，但每环境要起一次浏览器、慢，批量前逐环境探活成本高。

选 (B) 做执行前的门，把 (C) 留作未来「深度检查」开关。再加上执行阶段本来就有的「401 超 50% 熔断」兜底——预检不是要 100% 证明会话有效，而是**在最常见的「没捕获/早过期」情况下，别让用户白跑一整轮**。门是「提醒 + 让用户决定」（去捕获 / 仍要执行），不是硬拦——因为有些被测系统不需要登录，信息不足时默认放行。

## 「批量 = 自动批准」的隐藏细节

需求/用例两步是人工门控（待批准）。批量要无人值守跑完，就得自动批准。原 auto-chain 只推进 `idle` 步，一个卡在「待批准」的任务在批量里会卡住。所以批量把新晋任务的 `review` 步直接标 `done`（在 `pumpQueue` 里），让它越过门继续——这才兑现了「整条流水线 + 自动批准」的承诺。CDP 验证时正是靠这个，让一个待批准的「购物车」任务在批量里自动越过用例步进入执行。

## 设计原型驱动

开工前用可视化原型和用户对齐了看板形态（多选勾选框 + 并发下拉 + 批量执行 + 运行中/排队中统计 + 「排队中·第K位」徽标 + 登录态黄色警告），逐条确认方案后才动手，避免做完才发现形态不对。

## 已知局限与未来方向

- 跨页面存活：需服务端队列（见决策 1）。
- 登录态深度探活：未来「深度检查」开关（决策 4 的 C 档），可挂在目前闲置的 `healthEndpoint` 字段上。
- 并发计数对「活动手动接力任务」有 ±1 的瞬时超订，不影响正确性。
