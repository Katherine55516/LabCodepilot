# 技能创建与发现 —— 产品思考

> 技术实现见 [docs/handover/skills-discovery.md](../handover/skills-discovery.md)

## 解决什么用户问题

技能（Skills）是本应用复用提示词/自动化的核心能力。两个真实痛点让它形同虚设：

1. **应用内新建技能后「我的技能」里看不到** —— 用户填完表单、进编辑器、保存，回到列表却找不到，以为创建失败。
2. **技能调不动** —— 斜杠命令在输入框能选出来，发出去 agent 却没反应；用户手动从网上下载 skill 拖进 `.claude/` 文件夹（等价装了个项目级技能），agent 也发现不了。

这两点合起来=「技能这个功能基本不可用」。用户明确要求：**应用内创建** 和 **手动建文件夹创建** 两个场景都必须正常。

## 为什么是这样设计（而非其他方案）

### 为什么不直接「把 project 层加回 settingSources」
项目层当初被砍是为了防止 `<cwd>/.claude/settings.json` 的 `env` 覆盖用户选定服务商的鉴权（跑到错误端点）。加回去=重新引入鉴权泄漏风险。

### 为什么放弃「shadow 镜像」方案
对抗式核查发现：per-request shadow 只在 `~/.claude` 里有 cc-switch 残留鉴权 env 时才构建。绝大多数托管用户（鉴权由账号下发、不写 settings.json）走 passthrough，根本不建 shadow → 镜像方案对他们一行不执行。要补全就得「每轮托管对话都建 shadow」，把 MCP/凭证/会话记录/插件全部改道，并把曾导致 Windows 数据丢失的清理逻辑加到每一轮 —— 收益小、爆炸半径大、动的是最危险的模块。**否决。**

### 最终：双轨 + 绕开 settingSources
- **斜杠命令（用户显式调用）→ 客户端展开**：读技能正文当普通 prompt 发。SDK 端没有命令要解析，天然绕开 settingSources，所有服务商一致。保留 `/命令` 交互与气泡显示。
- **手动拖入 / 自主发现 → 应用自带 in-process MCP**：native 运行时早已用「文件系统直扫的 Skill 工具」解决了同样问题；我们把这套能力以 in-process MCP 形式补进 SDK 运行时，让 agent 在任何服务商下都能列出并执行项目技能。**复用已被验证的方案，而不是发明新机制。**

两轨服务两类截然不同的交互：一类是「我主动敲 `/x`」，一类是「让 AI 自己判断该用哪个技能」。

## 关键取舍

- **「能用」优先于「原生对齐」**：给的是「展开正文 / 工具返回正文」语义，不是 Claude Code 原生 slash command / Agent Skill 的系统级执行。对应用产出的纯提示词模板技能，二者效果等价；`$1..$9`、frontmatter、`` !`bash` ``、`@file` 等原生能力暂不替代（用户创建的技能不用这些）。完全原生对齐成本高、属独立大重构（Phase 4）。
- **只补项目级缺口**：用户级 `~/.claude/skills` SDK 已原生加载，MCP 不重复暴露，避免模型面对两个语义重叠的技能工具。
- **零开销默认**：没有项目技能的项目不注册 MCP、不注入提示词，不给普通对话增加工具发现开销。
- **诚实的本地验证边界**：本地 dev 无登录，托管真实调用以单测+代码审查覆盖，CDP 验证渲染与数据链路 —— 结论在此前提下表述。

## 已知局限与未来方向

- 非原生执行语义（见上）。
- 理想终态：按官方文档把 Agent Skills（`.claude/skills`，模型自主调用）与 Slash Commands（`.claude/commands`，用户显式 `/x`）彻底分成两条链路，并让 `system:init` 下发当前会话真实可用的 commands/skills 作为 UI 真源（见 [research/skills-agent-sdk-review-2026-03-10.md](../research/skills-agent-sdk-review-2026-03-10.md)）。本次修复在不做大重构的前提下让两个核心场景可用，为后续对齐留出空间。
