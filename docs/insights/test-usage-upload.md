# 测试用量上报：从「用户自己看」到「管理员看得见」

> 技术实现见 [docs/handover/test-usage-upload.md](../handover/test-usage-upload.md)
>
> 前置：本地统计的产品思考见 [insights/test-usage-stats.md](./test-usage-stats.md)。
> 那篇结尾写的「二期全体用户视角」，就是本篇。

## 解决什么问题

一期做完，AI 测试的使用统计只躺在**每个用户自己的机器上**：他能看自己的采纳率、通过率、报告准确度。
但管理者看不到全局——**这个 AI 测试能力到底有没有人用、用得怎么样、值不值得继续投入？**

没有这层数据，功能推广只能靠拍脑袋和口头反馈。所以二期要回答的是：
谁在用、用了多少、AI 生成的用例被采纳了多少、执行通过率如何、AI 的判断可不可信。

## 为什么长这样

### 复用「设备管理」的形状，而不是新造轮子

LabCodepilot 与 codeagent-server 之间早有成熟通道：桌面端登录、`device_id`、`POST /me/devices` 设备注册、
管理端「设备管理」菜单页。测试用量在结构上是同一类东西——**客户端上报自己的数据、管理员分页查看**。
所以整条链路（模块分层、鉴权双通道、分页响应壳、管理端菜单页）都照着 device 抄，
没有引入任何新范式。这让评审成本和后续维护成本都接近于零。

### 上报「按天计数」，而不是原始事件

原始事件流当然信息最全，但：体量大、含项目路径/用例名等本地标识、且服务端还得再实现一遍聚合口径。
按天计数则：体量小、可直接出趋势、且**口径在客户端算好**——服务端只做 SUM，永远不会算出跟用户
本地面板不一样的数字。

代价是灵活性：想加新指标就得改客户端 + 加列。所以留了 `payload` JSONB 放明细（按项目、按模型），
新维度先进 JSONB，稳定了再提列。

### 不脱敏，是一个被明确选择的取舍

上报体里带项目名/路径。这是**有意的**：管理员需要知道「大家在测哪些项目」才能判断价值分布。
代价是本地标识出了机器。这在企业内部工具的语境下可接受，且是用户拍板确认的口径。
如果哪天要收紧，脱敏只需在 `buildDailyRollup` 出口加一层——聚合层是纯函数，改动面很小。

## 三个真正难的决定

### 1. 覆盖还是累加？——都不是，是「全量重算 + 取大」

最早的设计是「服务端整体覆盖」。用户一句话点破：
**「用户把客户端的数据删除后，服务端的使用数据也就丢失了，对吗？」**

对。盲覆盖让服务端沦为客户端的**脆弱镜像**——而上云的初衷恰恰是要一份**独立于客户端的持久台账**。

最终方案：客户端每次**全量重算当天**（不发增量），服务端合并时对每个计数列取
`GREATEST(已存值, 新值)`。于是：
- 重复触发/重试/回补 → 幂等，不会重复计数（这是「不累加」的理由）；
- 客户端删库后重传 0 → **压不低服务端的历史高水位**（这是「不盲覆盖」的理由）。

一个 SQL 子句同时买到幂等和抗删除。代价诚实写进文档：虚高值会被锁住。

### 2. 熔断轮算不算？——分开算

熔断（circuit break）是执行被中断的轮次，它的用例级结果是残缺的。本地面板一直把它**整轮排除**在通过率之外。

上报时最初图省事，把熔断轮的 total/pass/fail 也加进去了，想着「服务端拿到 `circuit_broken` 标注，
需要时自己剔除」。**这行不通**——服务端只拿到求和后的数，无法再按轮次拆开。

于是拆成两件事：`executions`（执行轮次）**算**，因为用户确实发起了这次执行，那是活动量；
用例级结果和时长**不算**，因为那是质量信号。这样管理端的通过率和用户面板的通过率永远是同一个数。

**指标要分清「活动量」和「质量」——它们对残缺数据的态度是相反的。**

### 3. 状态型事件不能求和（差点上线的错）

这是真实数据救回来的一次。跑通链路后我拿本机真实库对了一遍数，发现某天：
**生成 56 条用例，却「采纳」了 165 条——采纳率 294%。**

根因：`cases_approved` 事件携带的 `finalCount` 是**当前全量状态**（该任务定稿后的总数），
不是增量。用户反复批准同一个任务，事件就反复发——库里就有同一任务一天内批准 3 次、每次 55 条。
逐条求和 = 55×3 = 165。

修法是按 `taskId` 做**日内 last-wins**（复核同理，按 `runHash|caseId`，`cleared` 即删除）——
这正是本地 `stats.ts` 一直在做的事，只是聚合上报时被漏掉了。修完再对：
采纳率 98.2%、通过率 53%、报告准确度 88.9%——**与本地面板逐项一致**。

教训：**事件流水里混着「增量」和「状态」两类语义，必须显式区分。**
且——**光有单测不够，必须拿真实数据对一次账**。单测全绿（13/13）时这个 bug 好好地活着，
因为构造的 fixture 里没人想到「同一个任务会被批准三次」。

## P2：把回归也纳进来

一期只上报功能测试。但回归才是**长期价值**所在——功能测试是「这次需求测没测」，回归是
「这个系统还稳不稳」。而且回归有个功能测试没有的独家信号：**脚本重放 vs AI 执行**。
沉淀成脚本的用例可以秒级重放、几乎零成本；还得靠 AI 现场执行的，说明沉淀还不够。
`reg_replay_ratio`（脚本占比）因此是衡量「这套回归资产成熟度」最直接的一把尺。

### 难点不在算，在「机器级」

功能测试的数据在 SQLite 事件表里，天然是机器级的；回归的数据是**文件态、按项目散落**在各自的
`AI_LabTest/` 下。要凑出机器级口径，就得先知道「这台机器上有哪些测试项目」。

答案是复用测试工作台自己的持久化文件 `test-workbench.json`——面板列项目用的就是它。
**不另维护一份项目清单**：任何"第二份真相"迟早会和第一份对不上。

### 熔断轮的处置，两侧必须同构

回归里也有熔断轮。处置方式和功能侧完全一样：**轮次数算**（用户确实发起了这一轮，是活动量），
**用例级结果不算**（中途断掉，结果不可信）。

这不是巧合，是同一条原则的两次应用：**活动量指标和质量指标，对"残缺数据"的态度是相反的。**
把这条想清楚一次，两个模块都不用再纠结。

### 一个差点变成"静默的 0"的坑

回归的按项目明细，我一开始单独放在 `payload.regression_projects[]` 里。看起来干净。

但服务端的按项目下钻，是直接对 `payload->projects` 里的 JSON **按列名**求和的。
放在另一个数组里 → 那几列**永远是 0**，而且不报错、不告警——管理员会看到一张"回归执行量全是 0"
的表，然后得出"没人用回归"的错误结论。

**一个静默的 0，比一个缺失的列危险得多。**

改法很简单：把回归明细并进**同一个** `projects[]`，键用项目全路径，字段直接用服务端列名 `reg_*`。
服务端一次 unnest 同时拿到两侧，**一行 SQL 都不用改**。代价是出现一处命名不一致（日级无前缀、
项目行有前缀），已在类型注释里写明缘由——用一点表面的不一致，换掉一整套重复的聚合逻辑，值。

### 这次没有真实数据可对账

P1 最大的收获是「拿真实数据对账」抓出了 294% 的采纳率。回归这次**做不到**：开发机上没有任何
项目真正跑过回归轮次。

退而求其次的做法是：造一份**真实文件态**的 fixture，然后让「上报聚合」和「面板聚合」
互相对账——六项指标逐项一致。这验证的是**两个实现口径一致**，但验证不了**口径本身符合真实数据的形态**
（比如真实 run.json 里会不会有我没预料到的字段组合）。

诚实地说：**回归这侧比功能侧少一层保险**。上线后应尽早找一个真在跑回归的用户，用真实数据复核一次。
这条已写进交接文档的已知局限。

## 已知局限

- **上报前就被删的数据找不回**。这是客户端遥测的天花板。触发点从最初的「打开面板时」扩到
  「登录/启动 + 每日 10/16/20 + 打开测试模块」，把采集窗口压小，但消不掉。
- **本地事件是机器级、不含用户身份**。一台机器换人登录，之后上报的历史天会归到新账号。
  要彻底解决得在埋点时就记用户——那是更大的改动。
- **跨天重复批准**仍会在各自那天各计一次。日分桶的固有代价。
- **回归缺真实数据对账**（见上）——这是目前最该补的一块。
- `reg_suites_count` 在按项目下钻里恒为 0（套件数是状态，按项目跨天求和无意义）。
- 管理端目前只有「看」。真要驱动决策，下一步该是**对比**（团队间/版本间）和**告警**（用量掉底）。
