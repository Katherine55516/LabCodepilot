# 办公模式脱敏 —— 产品思考

> 技术实现见 [docs/handover/deid-gateway.md](../handover/deid-gateway.md)
> 最后更新:2026-07-31

## 解决什么问题

办公模式的用户是公司同事,他们的对话天然带真名、手机号、邮箱、客户名、
项目代号。这些内容目前原样发给外部模型。合规上这是要命的地方:**一旦发出去
就收不回来**,而用户在按下回车那一刻根本没有机会知道自己发了什么敏感信息。

脱敏网关做的事很朴素:在内容离开这台电脑之前,把它拦下来,告诉用户
「我识别到这些是个人信息,准备替换成占位符,你看对不对」。

## 为什么是「开关 + 逐项确认」,而不是静默全自动

对接文档的建议是「生产环境默认开启且不可关闭」。我们没有照做,用户明确要求
**用户可自行开关**。这个分歧值得记下来:

- **静默全自动**的问题是,脱敏永远会有误判。「张伟发邮件」被切成「张伟发」
  是实测中真实发生的(NER 把动词吞进人名)。如果用户看不见也改不了,他会得到
  一个莫名其妙的回答,而且不知道为什么 —— 信任崩塌得比漏脱敏还快。
- **逐项确认**把最终决定权交回用户。代价是每条消息多一次弹窗。这个摩擦是
  真实的,但办公模式本来就不是高频快聊场景,一次确认换一次「我知道我发了什么」
  是划算的。

默认关而不是默认开,是因为存量办公会话不该被一次升级改变行为。想用的人点一下,
一次点击的成本远小于「昨天还好好的今天怎么每次发消息都弹窗」的困惑。

## 三个不太直觉的设计选择

**用户看到的永远是原文,模型看到的永远是占位符。** 用户气泡显示他实际打的字,
助手气泡显示还原后的回复。占位符只活在「本应用 → 模型」这一段。这意味着用户
几乎感觉不到脱敏的存在 —— 除非他主动去看。**脱敏做得越好,越不该被感知。**

**还原放在渲染层,数据库里存的是模型的原始输出。** 这不只是实现方便。它保留了
「模型到底说了什么」这个事实 —— 审计要用,排障要用,而且当模型乱改占位符时
(实测会发生),我们能如实告诉用户「有一段还原不了」,而不是猜一个替换糊过去。

**失败一定不发。** 脱敏服务挂了、网络断了、密钥错了 —— 一律不发送,输入框内容
原样留着。这条不给「跳过脱敏直接发」的逃生口。因为一旦有那个按钮,赶时间的用户
一定会点,而脱敏功能的价值恰恰全在「它从不例外」这件事上。

## 已知的不完整,以及为什么可以接受

**附件不脱敏。** 用户上传的 Excel、PDF、截图里的敏感信息照旧原样进模型。这是本期
最大的缺口。诚实地在预览弹窗里标黄提示,而不是假装覆盖了。图片脱敏(OCR + 打码)
服务端已经具备能力,是明确的下一期。

**桥接消息不过脱敏门。** 微信过来的消息不经过输入框,也就没有确认弹窗。要覆盖它,
门必须挪到服务端,但那样就没有「逐项确认」了 —— 这是产品取舍,不是做不到。

**历史回灌会过度脱敏。** 用户曾经手动"保留原文"的那个名字,在后续轮次的历史回灌里
仍会被替换成占位符。方向是安全的(宁可多脱一次),观感上模型可能显得"忘了"用户
刚才特意保留的信息。真要修,得给每个实体记住用户的逐轮决定 —— 复杂度不值当。
