# 额度用量进度条 — 产品思考

> 技术实现见 [docs/handover/usage-meter.md](../handover/usage-meter.md)

## 解决什么用户问题

用户用的是账号下发的 managed 额度(公司买单的网关额度)。他们需要随手看到"还剩多少 / 用了多少"，避免额度快耗尽时才发现。放进用户栏(点用户名展开的菜单)是最自然的位置——和"账号 / 托管配置 / 退出登录"同处，一眼可达，不占主界面空间。

## 为什么这样设计，而不是别的

- **主进程代理，而非 renderer 直连后端**：token 在主进程且已加密，renderer 不该看到 Bearer。复用现有 `apiRequest`(自动注入 Bearer + 错误分类)，renderer 只拿计算好的数字。零新增 token 暴露面，也省掉 renderer 侧的后端地址/鉴权重复实现。
- **只点开才刷新，不轮询**：额度变化不频繁，用户只在"想看时"看。轮询徒增后端压力与本地开销，还要处理菜单关闭后的定时器清理。点开即拉一次，简单且符合直觉——这也是用户明确的要求。
- **三条(总/国内/国外)、已用%、仅百分比**(用户拍板)：网关额度分国内/国外两条线分别限流，分项可见有实际意义(某条线先用尽会被拦)。"已用%"比"剩余%"更贴合"用量"语义——进度条满=快用尽，配色由绿转红是直觉化的预警。本期不显示货币($)：百分比对"还能用多久"的判断已够，货币换算(quota_per_unit)留作后续。
- **百分比放客户端算**：服务器只下发原始额度(renewal/remaining/used)，换算/分档/配色属于展示逻辑，放客户端纯函数(`usedPercent`/`levelOf`)——可单测、易调、不被服务器格式绑架。

## 已知局限与未来方向

- 不显示货币金额、不做历史/趋势、不自动刷新——都为保持轻量与低打扰。后续可按需加"剩余 $X"小字、用量曲线、或接近上限时的主动提醒。
- dev 无登录体系，本地只能 mock 验证渲染逻辑；真实数据需打包登录后验证。
