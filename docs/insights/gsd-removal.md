# 内置 GSD 下线 —— 产品思考

> 技术实现见 [docs/handover/gsd-removal.md](../handover/gsd-removal.md)
> 当初为什么内置见 [docs/insights/gsd-bundle.md](./gsd-bundle.md)（已归档）

## 用户问题

用户的原话是：GSD「已经淘汰没人用了，并且还占用着大量上下文」。

三个月前内置 GSD 的判断是对的——[当时的产品思考](./gsd-bundle.md)记录得很清楚：降低二阶能力的使用门槛，装完即用。问题出在这个判断的有效期。上游 `gsd-build/get-shit-done` 在我们内置后不久就归档了，本仓的快照自 2026-05-26 起再未更新，72 天零功能改动。一个不再演进的框架，占着**全局命令空间的 67/68 和全部 33 个 subagent**。

代价是可量化的。把这些命令与 agent 的名称加 description 按系统提示词的渲染格式拼出来，共 14,576 字节，约 **3,644 tokens**——每一次请求都要重复付费，与用户是否用到 GSD 无关。对一个主打「让 Claude Code 更好用」的客户端来说，这是我们自己制造的税。

## 为什么不能只是「默认关闭」

最省事的做法是把默认值翻成关闭，让想用的人自己开。但调研时发现**设置面板里的「停用」开关对上下文毫无作用**：`disable()` 只在插件目录里写一个 `.disabled` 标记并把 `commands/` 改名，从头到尾没有碰过 `~/.claude/` 下的任何镜像文件。用户即使手动停用了 GSD，那 67 条命令和 33 个 agent 仍原样躺在磁盘上被 Claude Code 加载。

这也解释了为什么被动删除同样不行：镜像文件由 Claude Code 直接读盘，不经过应用。删掉 installer 之后没有任何代码会再去动它们——`/gsd-*` 会继续出现在菜单里，token 会继续被占，而且**再也没有机会清理**。

所以下线的形态被这条硬约束决定了：必须先发一版带主动清理的，之后才谈得上删干净。

## 关键取舍：为什么不是纯哈希清单

最初的方案是纯哈希匹配——打包一份 sha1 清单，逐文件比对后删除。安全、零误伤，而且清单只有 30.9 KB，比原本 4.6 MB 的 bundle 还小。

但这个方案达不到用户要的「无残留」。深挖后发现两类会漏网：

**其一是四小时窗口的老用户。** vendor 流水线在 2026-05-26 09:44 到 14:04 之间连出了 v1/v2/v3 三代转换。更关键的是旧镜像逻辑遇到哈希不匹配时**只记冲突、不覆写**——这意味着在那个窗口装机的用户，其文件内容至今仍停在旧版本，后续任何一次更新都没有纠正过。纯哈希清单一个都删不掉。

**其二是手改过文件的用户。** 同一条规则的另一面。

**其三是嵌套空目录。** 旧清理逻辑只对根目录做一次 `rmdir`，而 `get-shit-done/` 下有 18 个目录、最深三层，文件删完会留一整套空壳。

## 破局点：一个可靠的身份标志

改成暴力按名删除（`rm -rf` + 通配）能清干净，但会误删用户自己安装的官方 GSD。两难。

破局点是发现了一个可靠的区分标志：**官方 GSD 的命令装在 `commands/gsd/` 子目录（命名空间 `/gsd:x`），而我们的 vendor 流水线把它们拍平成了 `gsd-x.md`（`/gsd-x`）。** 平铺形态是我们独有的产物。同理，插件目录名带 `codepilot-` 前缀，也只可能是我们写的。

于是形成了「四类目标、两种识别模式」的分策略：能唯一识别为我们的（插件目录、平铺命令）无条件删除，与文件内容和版本完全无关；与官方共用命名或路径的（agent、资源树）保留判断闸门——没有官方安装痕迹就按路径删，有就退回哈希精确删。

前两类覆盖了绝大多数文件，所以老版本用户和手改过文件的用户都能被彻底清干净；后两类保住了唯一值得保护的场景。这比「一刀切」的任何一端都更贴合实际。

## 一处故意不做

`~/.claude.json` 里有三条 `skillUsage.gsd-*` 使用计数。技术上可以删，但那是 Claude Code 自己的配置文件、由它并发写入，我们去读改写有把无关状态写坏的风险。而这几十字节是惰性计数，不进上下文、不进斜杠菜单，不构成用户要解决的问题。

**风险与收益不成比例的清理，不做比做干净更负责任。** 同理，用户项目里的 `.planning/` 是 GSD 的逐项目产出、属用户数据，也不碰。

## 用户体验

清理跑在主进程启动时，fire-and-forget，不阻塞窗口。用户装完新版第一次打开就已经清干净了，不需要点任何按钮、不需要重启第二次。跑完写一个标记文件，之后每次开机直接早退。

发版说明里用面向用户的措辞说明「移除已停止维护的 GSD 内置插件，并自动清理旧版本遗留文件，无需手动操作」即可。

## 顺带收敛的一件事

下线之后，内置插件只剩 AI_LabTest 一条路径，而它的行为是**默认禁用、由用户在设置里主动启用**——与 GSD 的默认启用强装正好相反。当初 [AI_LabTest 的设计](./ailab-plugin.md)就刻意做了这个不同选择，理由是「用户的诉求是**启用时**能正常运行，这天然意味着它可开关、按需启用，而不是常驻」。

现在回头看，那个判断比 GSD 的默认开启更经得起时间检验：**随包内置降低的是获取门槛，不该顺带替用户做「常驻」的决定。** 这条经验应当写进未来任何内置插件的默认值决策。

## 已知局限与未来

- `purge()` 与清单合计约 120 行 + 30.9 KB，需**保留 2–3 个版本再删**，否则跨版本直跳的用户永远清不掉残留。
- 官方安装的判定依赖两个目录信号。如果官方 GSD 未来改变安装布局，判定会失效——但该项目已归档，这个风险实际为零。
- `PluginsManager` 目前仍是每个内置插件硬编码一张卡片。GSD 卡片删除后只剩一张，若将来再增内置插件，应改为数据驱动列表（[ailab-plugin 的思考](./ailab-plugin.md)里已提出同一方向）。
