# 技能市场（内部）— 产品思考

> 技术实现见 [docs/handover/skills-store-internal.md](../handover/skills-store-internal.md)

## 解决什么问题

外部技能市场（skills.sh）解决的是「社区有什么好技能」；它解决不了**组织内部的技能分发**：
业务部门沉淀的提示词/脚本资产（报销流程、内部系统操作、团队评审规范）不能也不该发到公网。
在内部市场出现之前,这些资产靠聊天工具传 zip、口口相传目录拷贝——没有版本、没有更新通知、
没有权限边界。Lab AI Hub 提供了内部技能的发布与治理侧,本功能是它在桌面客户端的消费侧:
和外部市场并排的第三个 tab,搜索→看详情→一键安装,装完即出现在「我的技能」和斜杠命令里。

## 关键设计取舍

**1. 客户端只做「浏览 + 本地安装」,权限与数据一概不落地。**
服务端(BFF)已经决定不镜像 Hub 数据——权限判定全在 Hub 侧,镜像等于把权限逻辑复制一份。
客户端顺着同一逻辑:不缓存列表、不持久化详情,本地只留两样东西:安装产物(技能文件)和
安装台账(装了什么、哪个版本)。Hub 挂了只影响商店打不开,已装技能是本地文件照常可用。

**2. 走主进程而不是复用外部市场的 Next route 链路。**
表面看两个市场功能一致,底层信任模型完全不同:外部市场无鉴权、安装交给外部 CLI;
内部市场带登录态,而登录 token 的纪律是「绝不出主进程」(与问题反馈同边界)。
复用外部链路意味着 token 下发 Next 进程,破坏既有边界。代价是多一层 IPC,可接受。

**3. 安装目录名:可读性赢了唯一性建议。**
服务端文档建议本地目录用 cuid(绝对唯一)。但目录名就是用户天天敲的斜杠命令名——
`/pdf-toolkit` 和 `/ckxk2a9f3b` 的体验差距不需要论证。折中:常态用 slug,撞名才追加
id 前 8 位后缀;台账 key 恒用 skillId 保证正确性。赌的是撞名是罕见事件,而可读性是每天的事。

**4. 更新语义照搬服务端的「不变不传」。**
更新检查用 contentHash 比对(列表自带,零额外请求);真下载时带 ETag 协商,内容没变
就是一个 304,不重复传输。已下架(DEPRECATED)技能本地保留、停止更新、卡片明示——
用户的工作流不因发布方下架而立刻断掉,这是消费侧应有的温和度。

**5. 「未启用即不存在」。**
服务端没配 Hub(503)时整个 tab 不渲染,而不是显示一个永远报错的入口。私有化部署/
未接 Hub 的环境里,用户不该看到一个自己无法理解的残缺功能。probe 一次、会话级缓存。

**6. 与「我的技能」做真互通,而不是各管各的。**
装完的技能就是普通的本地技能,出现在「我的技能」里,可以在那里看、也可以在那里删。
删了之后内部市场靠台账自愈把「已安装」徽章翻回来(顺手修了「我的技能」删除 installed
技能只删 SKILL.md 留一地残骸的老 bug——残留目录还会永久占住 slug)。两个入口一份事实。

## 外部参照

- VS Code 的 Marketplace / 私有 extension gallery 双轨:企业场景必然长出内部分发渠道,
  且两者 UI 同构(用户不需要学两套心智)。本功能的三 tab 布局同理:外部与内部长得一样,
  只是货架不同。
- Claude Code 的 plugin/skill 生态:安装产物直接落 `~/.claude/skills/` 而不是自造私有
  格式,任何时候用户脱离本应用,技能文件依然是标准的 Claude Code 技能。不锁定。

## 已知局限与方向

- **无灰度/审批流**:Hub 侧上架即全员可见可装。企业场景后续可能需要「管理员先审后上」
  或按组可见,那是 Hub 侧的治理能力,客户端只需透传新的错误码/状态。
- **更新靠用户打开列表**:没有后台轮询和「N 个技能可更新」的角标。技能不是安全补丁,
  主动性要求低,但如果 Hub 侧出现高频迭代的重技能,可以考虑启动时静默比对一次。
- **无批量操作**:装/更/卸都是单个进行。列表大了以后「全部更新」是自然诉求。
- **INLINE 型技能的定位**:目前统一走 download 安装,inlineContent 只做详情预览。
  如果未来出现大量「一段提示词」级的轻技能,值得考虑免安装直接注入会话的形态。
