# 回归脚本:失败要被看见,修复不许说谎

> 技术实现见 [docs/handover/regression-script-generation.md](../handover/regression-script-generation.md)

## 用户是谁:不写代码的测试人员

这个功能的全部设计约束来自一句用户原话:**"不要手动修改,测试人员都不会写自动化脚本。"**

脚本是 AI 生成的,运行失败后不能指望用户打开 `.spec.ts` 改定位器。失败之后的每一步——看见原因、修复、验证——都必须在界面里闭环,且不需要读代码。

## 三个阶段的演进:看不见 → 看得见 → 能自愈

**v1(初版)**:脚本运行失败时,manifest 的 `status` 和 `counts` 刻意不变(设计正确:脚本可能没问题,只是被测应用没起),但没有任何东西承载失败原因——卡片渲染前后逐字节相同,唯一反馈是一个自动消失的 toast。用户的原话是"点击运行全部,没有任何反应"。

**v2(失败持久化)**:`lastRunError/lastRunAt` 写进 manifest,`summarizeRunFailure` 从 Playwright 数百行报告里提炼一行人话(优先 `net::ERR_*`,其次 `Error:` 行),卡片红字显示。原则:**失败不改状态,但必须留下解释**。

**v3(AI 修复)**:`lastRunError` 有人消费了。「重试」是盲抽(重新生成、不读失败原因),「运行」是原样重放,都不利用已知信息;「AI 修复」把失败原因 + 当前脚本 + 原用例喂回模型定向修,修复稿走与生成完全相同的校验/重放管线,全部通过才覆盖旧文件。

**v4(自动跑通流水线)**:用户一句话定了终局——"生成回归自动化脚本后,自动化运行测试,测试不通过,AI 检查修复,直至全部运行通过,这个流水线要求自动化"。前面所有零件(生成、运行、失败持久化、AI 修复)串成一条**无人值守**的链:报告生成脚本 → 自动运行 → 失败自动修 → 再跑 → 直至可修复的全过。报告流触发时默认接入,被测应用不可达则跳过、只停在生成态。

### "直至全部通过"这句话不能照字面实现

用户的心智模型假设所有失败都能修好。但现实里有两类失败**不该也不能**靠改脚本通过:被测应用没起(环境问题),和页面真实行为与用例预期不符(断言如实失败)。如果循环为了"全绿"不惜代价,要么无限重试环境问题、要么篡改断言掩盖真缺陷——那就是流水线在帮测试造假,反噬整个功能的存在意义。

所以终止条件是三选一、都不造假:全部可修复的通过 / 轮次上限 / 剩下的都已诚实归类(环境阻塞 / 需人工)。"全部通过"只对**该通过的**兑现。

### 最反直觉、也最重要的一个决定:不信模型的自评

真机实测暴露了关键风险:一条断言如实失败的用例(空名称时按钮本不禁用),模型**没有诚实拒绝**,而是当成"渲染时机问题"加等待想硬修。如果循环信它 `fixed=true` 就反复重试,会空烧三轮、还把它标成"未修复"而非"需人工"。

修法是**结构性守红线,而非依赖模型自律**:每条用例只给一次定向修复机会,一次带着确切失败原因还跑不通,就不管模型嘴上说没说修好——**跑不通就是跑不通**,直接升级人工,并把模型那句乐观的 repairNote 覆盖成真话。用重跑这个客观事实兜底,不赌模型每次都守规矩。这也是为什么必须真机跑而不能只信单测:单测证明不了"模型会不会守红线"。

## 最重要的设计决策:修复的红线

修复功能最大的风险不是修不好,是**修得太好**——模型为了让脚本通过,把断言弱化、删除或反转。那样"全绿"的代价是掩盖用例本应暴露的产品缺陷,整个测试功能的存在意义被反噬。

所以 prompt 里写死红线:只许修技术缺陷(定位器歧义、等待时机、前置数据);如果失败源于页面实际行为与用例预期不符(断言如实失败),必须返回 `fixed=false`,并用测试人员能懂的话解释"页面实际是 X、用例预期是 Y,需人工确认是产品缺陷还是用例写错"。这个解释持久化在 `repairNote`,不是弹一下就没。

真机验证时特意保留了一条"预期与实际不符"的用例(空名称时按钮并不禁用)来测这条红线——修复功能对它的正确行为是**拒绝修**。

## 为什么修复走同款校验管线而不是直接覆盖

模型的修复稿和首次生成一样不可信。`validateAndPublish` 的静态校验(import allowlist、秘密扫描、断言存在性)→ Playwright collect → 安全时真实重放,全部通过才原子替换;任何一步失败,旧脚本原样保留。修复永远不会让状态变得比修复前更糟。

## 闭环要闭全:别让某类失败偷偷变成死胡同（2026-07-11）

真机又暴露两个"卡 0/1 存在缺口、点什么都不动"的死胡同——都不是生成不出来,是生成/校验的**某类失败没有出路**。

**其一:静态校验失败没有自纠。** 运行时失败有 AI 修复闭环,但模型首次生成若结构不合规(把一条用例拆成多个 `test()`、标题漏用例 ID),`validateAndPublish` 静态校验一挂就 dead-end 成 `failed`——而「重试缺口」只是拿同一个 prompt 再赌一次,网关模型大概率再拆一次。修法是把运行时那套闭环**对称地补给静态失败**:静态挂了就把**确切的校验错误**喂回模型定向修一次,改好才采纳。同时给生成 prompt 加一段**具体结构骨架**(一个顶层 `test()`、用 `test.step` 分步)从源头压低不合规率——描述规则不如给一个能照抄的模板,弱模型尤其吃这套。

**其二:只读用例重放失败被埋成死态。** 只读用例生成期会真机重放一次确认;可这一步在被测应用没启动时必然 `ECONNREFUSED`,而旧代码把它判成 `failed`——偏偏 `failed` 这个态既不被「运行」(只跑 verified/needs_review)、也不被「AI 修复」(只碰带 `lastRunError` 的)接手,连自动流水线都不为它触发。于是被测应用没起,只读用例就永久卡死,唯一出路是重新生成、再撞同一堵墙。这暴露一个更本质的问题:**`failed` 是个没有恢复通道的黑洞态**,任何"其实还有救"的失败都不该掉进去。修法:脚本既已过静态+加载校验,重放失败就落盘、标 `needs_review` 并把原因记进 `lastRunError`,让它落进既有闭环——被测应用起来后一跑就转 verified,真有脚本缺陷就进 AI 修复。只有"连加载都过不了"的 malformed 脚本才保留 `failed`(那种该重新生成)。

一句话教训:**修复闭环的价值不在于修得多好,而在于没有一类失败会掉出闭环之外。** 为此把"哪些态可运行/可修复"抽成显式谓词(`isRunnableStatus`/`isFixableCase`)并单测——下次谁再加一个状态或一条恢复路径,漏了哪个态一测就红。

## 沉淀的脚本终于开始"上班":回归执行走快车道(2026-07-13)

脚本生成链建成后一直只有"资产",没有"收益"——回归轮次照旧全量 AI 执行。本次打通最后一公里:
**有合格脚本的用例直接重放脚本(秒级/条、零 token),没有的走 AI;全覆盖时整轮不起智能体**。
脚本覆盖率越高,回归越快越省,这是"AI 探索一次、脚本沉淀、回归重放"闭环的终态形状。

三个用户拍板的设计决策:

1. **脚本失败不转 AI,直接判失败**(备选是自动转 AI 复核)。理由:失败是带 Playwright 错误证据的
   执行结果,不是"没执行";自动转 AI 会掩盖脚本腐化、且每轮为烂脚本烧 token。代价是脚本腐化会
   误伤红线——对冲手段是**连败 ≥2 强制提示**(错误信息直接给出修复路径),把"脚本坏了"这个事实
   推到用户脸上而不是藏起来。这与本文档"失败要被看见"的一贯立场同构。
2. **范围放宽到干净的 needs_review**(备选仅 verified)。写数据用例生成期不自动重放、永远进不了
   verified,但回归轮次本来就要写数据(AI 执行同样写)——此时重放它们是安全的。mock 脚本绝不重放(假测)。
3. **开关默认开、可关**。关闭 = 全 AI,保留排障与"脚本判的对不对"的对照通道。

一个容易被忽略但致命的联动:脚本重放判定的 pass 会再次触发报告后的脚本生成任务,而重放没有 MCP
轨迹(trace 为空)→ 语义指纹必然漂移 → 若不处理,每轮回归都会拿空轨迹把好脚本重新生成一遍(churn +
质量下降)。修法是生成侧识别 `via:'script'` 直接跳过——**判定本就来自脚本,无新知识可学**。

## 已知局限与方向

- 修复一次只消费一条失败信息,不带页面 DOM 快照;定位器修复靠模型对 Playwright 语义的先验(如 `exact: true`)。带上失败瞬间的 DOM/截图能进一步提高修复率,但 payload 与脱敏成本要权衡。
- 每条用例只 1 次修复机会是刻意的保守取舍:堵住了 AI 空烧轮次,但真正需要 2 步的修复链(修好定位器 A 才暴露 B)会被过早升级人工。用户可再点一次「AI 修复」补第二刀。
- 需人工的用例目前止步于 `repairNote` 解释,没有后续动线(如一键转缺陷、或改用例预期的建议流)。
- 流水线自动运行含写操作的脚本(如"创建学科"),会在被测库里留下测试数据。这与手动「运行全部」一致,但自动化后累积更快——被测环境的种子数据清理是配套课题。
- 生成期【静态/加载(collect)】失败的用例仍无落盘脚本、不归 AI 修复管,走「重试缺口」重新生成(静态失败现会先自纠一次,仍不过才落到这里);但生成期【重放】失败的只读用例已改为落盘 `needs_review`+`lastRunError`、进闭环,不再是死态(见"闭环要闭全")。

### 按钮收敛:零件不该和流水线并排摆

用户实测后的直接反馈:"「重试缺口」「自动跑通」「运行全部」「AI 修复」这几个按钮有没有冗余的"。有——「运行全部」「AI 修复」是历史零件,「自动跑通」是后来把它们串成的流水线,零件忘了收。对不写代码的测试人员,四个动作按钮就是四次选择困难。收敛后卡片只剩一条主线:**查看脚本 + 自动跑通**,「重试缺口」只在真有生成缺口时出现(修正了它此前"任何运行失败都冒出来、点了空转"的误导条件),重试完成后自动接流水线;单条精修收进脚本弹框。原则:**卡片给测试人员一个不用思考的主动作,弹框给需要外科手术的人**。
