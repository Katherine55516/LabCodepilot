## 解决什么用户问题

办公模式让 AI 能干活，但只能「叫一次动一次」——用户在场、发指令、等结果。而办公场景里相当一部分工作是**例行的**：每天早上整理昨天的数据、每周一汇总上周的报表、工作日定时检查一批文件。这类工作的价值恰恰在于「不用我记得」，让用户每天手动去戳一次 AI，等于把闹钟塞回用户脑子里。

定时任务的回答：**把例行工作交给公司沙箱服务器，关掉客户端、关掉电脑都照常跑**。用户回来打开 app，看到的是「你不在时跑了 3 次 · 3 成功」，点进去是每一次的完整过程和产物。AI 从「随叫随到的助手」变成「下班后还在干活的同事」。

## 关键设计决策与理由

### 1. 服务端调度，而不是本机调度（D1）

这是整个功能最大的一个决策。本应用其实**早就有一套本机调度器**（`task-scheduler.ts`：cron/interval/once、补跑、退避都齐），复用它做定时任务是成本最低的路——但被否了，原因只有一条：**跑在用户电脑上的「定时」承诺不可信**。办公用户的电脑晚上关机、周末合盖，「每天早上 9 点」在本机语义下实际是「下次开机时补跑」，用户拿到的是迟到的日报。调研里把这条列为「体验一致里唯一做不到便宜的」：Routines 的核心卖点就是关机也在跑，绕开它等于做了个假货。

代价是三件本可不做的事：服务端要能**无客户端在场**时拿到用户的模型凭证（账号后端新开内部接口）、要自己驱动完整 agent 回合（执行器 + 四护栏）、要有自己的存储与调度循环。这些都做了，因为它们是承诺的成本，不是可选项。

**顺带的减法**：旧本机定时任务的 MCP 工具已下线。两套「定时任务」并存时模型会挑错工具，且挑错的表现是「已创建」而非报错——任务建在了一个界面早已隐藏的系统里，用户永远等不到结果。静默失败比功能缺失更伤信任，所以砍掉了通往旧系统的所有路径。

### 2. 定时会话不进办公对话列表（用户反馈驱动）

原设计把每次运行物化成会话后直接放进办公对话列表，加个「定时」分组。用户看了原型后否掉：「很乱很疑惑」——每天跑 3 个任务，一周后列表里塞满 21 条不是用户亲手发起的会话，真正的对话被淹没。

改法是把**存储复用**和**导航归属**拆开：运行记录仍物化成 `chat_sessions`（聊天渲染、工具折叠、产物下载整套零成本复用），但办公列表查询排除它们，唯一入口是「定时任务」页的三层导航（列表 → 详情+运行历史 → 某次运行的只读回放）。第三层还加了「← 上一次 / 下一次 →」——横向比对连续几天的运行结果，是定时任务特有的浏览需求，普通对话列表给不了。

这条曾引入一个新失败模式：用户在对话里让 AI 建了定时任务，然后**在原对话里一直等结果**——结果永远不会出现在那里。所以 MCP 工具的成功回复被强制要求带一句「运行结果会出现在左侧『定时任务』里，不会打扰这个对话」。

### 3. 任务独占一个持久工作区（D2）

每次运行不是全新环境，而是同一个沙箱工作区的延续——昨天生成的表，今天可以接着读。这与 Claude 云端 Routines 相反（它每次全新 clone），理由是办公例行任务天然是**增量的**：日报要对比昨天、周报要累积一周。技术上这条几乎免费——routineId 直接当会话 id 用，现成的容器/卷/文件通道/归属校验全部零改动复用。副作用（状态越积越脏）交给用户在指令里自己清理，表单里明确写了这一点。

### 4. 凭证反向直取 + 独立密钥（D3/D4）

客户端不在场，服务端拿什么调模型？答案是沙箱服务器凭内部密钥向账号后端换取该用户的凭证，用完即废（token 有效期 ≤60 秒）。安全上最重要的一条：这把密钥与用户 token 的签发密钥**必须是两把**。沙箱是跑不可信 agent 代码的机器，被攻破概率天然高于账号后端；复用同一把密钥会让「攻破沙箱」从「冒充用户访问沙箱」升级为「批量导出全体用户的模型 API key」——质变而非量变。

### 5. 护栏按「没人盯着」设计

交互回合出问题用户会看见、会中止；定时任务没人盯着，所有失败都要**自动止血**：坏凭证立即中止（不做会白烧 181 秒退避）、15 分钟硬超时、输出 8MB 上限、并发上限 4、每人每天 20 次配额、连续失败 10 次自动停用。这些数字都偏保守——无人值守场景里，宁可用户偶尔碰到「今天配额用完了」，也不能让一个写错的任务每天烧钱烧到月底。

### 6. 「会话正常退出」不等于「任务达成」

实测抓到的最好教训：一次运行 exit 0、状态 success、花了 $0.39，但用户的指令根本没被执行（参数拼接 bug 把二进制路径当成了 prompt，模型一本正经地介绍了一遍那个路径是什么）。**绿色不等于任务达成**。所以运行历史里能看到每次的完整回放而不只是状态灯，创建表单里强制提醒「每次运行都是全新对话，指令必须能独立看懂」——让用户有能力自己核对「它到底干了什么」。

## 与 Claude Routines 的异同

| | Claude 云端 Routines | 本功能 |
|---|---|---|
| 跑在哪 | Anthropic 云 | **公司自有沙箱服务器**（数据不出公司） |
| 关机能跑 | ✅ | ✅ |
| 工作区 | 每次全新 clone | **持久累积**（D2） |
| 最小间隔 | 1 小时 | **15 分钟** |
| 模型 | 订阅套餐决定 | **跟随账号下发配置**（可按任务指定） |
| 创建入口 | 对话 / 管理页 | 对话（MCP）/ 管理页 / 「存为定时任务」三条 |
| 结果呈现 | 云端会话列表 | 独立「定时任务」页三层导航，不混入对话列表 |

相同的是体验骨架：自然语言创建、云端无人值守执行、回来看汇总。不同的本质在部署形态——我们的用户数据与模型凭证都在公司体系内闭环，这是自建沙箱路线相对官方云的核心卖点，也是这个功能敢对内网用户开放的前提。

## 未来方向与已知局限

- **运行历史永久保留**（D12）目前没有清理策略。按每人每天 20 次的配额上限，单用户一年最多 7300 条记录 + transcript 原文，量级尚可，但需要在用户数上来后重新评估。
- **不能访问内网**（D15）。例行任务最自然的诉求之一（「每天拉一下内网系统的数据」）目前做不到，egress 维持拒私网四段。放开需要单独的安全评审，且大概率是白名单制。
- **离线期间不推送**（D14）。用户不开 app 就不知道任务失败了——连续失败 10 次自动停用是兜底，但「第一时间知道」要等将来接远程推送渠道（如已有的微信桥接）。
- **旧本机调度器的清理**（D16）：引擎与界面还在，存量任务仍会触发，模型已够不着。等本功能稳定后单独起 PR 清理。
- **运维缺口两条**：内部凭证密钥没有 admin 配置页（改动要动 env + 重建容器）；凭证接口的「token 不合法」与「用户无配置」都回 404（防探测），排障时有歧义。
