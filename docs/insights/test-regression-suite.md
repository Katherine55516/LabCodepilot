# 回归集 + 用例门控 + 操作审计(产品思考)

> 技术实现见 [docs/handover/test-regression-suite.md](../handover/test-regression-suite.md)

## 解决什么问题

1. **「这版能不能发?」没有机器判据。**测试报告只有通过率,但 90% 通过率里挂掉的那 10%
   可能是登录——通过率高不等于能发版。用户定义:**不通过会阻塞系统运行的用例 = 回归用例**,
   本迭代把它做成「回归集」:AI 生成时按「失败后果」自动打标,报告里回归集未全过就是红色
   「不可发版」,发版判断从人肉扫表变成一条红线。
2. **一键「运行任务」跑完四步,用例根本没人看过。**AI 生成的用例(以及它推荐的回归集标签)
   直接进了执行——错的用例测出来的结果没有意义。现在「运行任务」在用例设计完成后**必停**,
   用户审阅/调整(包括回归标签)后点批准才继续,批准后执行→报告仍一键到底。
3. **谁在什么时候批准了什么,无从查起。**门控要有意义就必须留痕。所有关键操作(批准/运行/
   修订/停止/导入/删除/AI 推荐)落到项目目录的审计文件,删任务也留痕,任务详情里一键查看。

## 为什么这样设计(而不是别的)

- **tags 复用而非新字段**:「回归测试」标签早已存在于用例编辑表格,只是没人产出、没人消费。
  打通「AI 产出→导入导出→报告消费」比再造一个 `isRegression` 字段迁移成本低得多。
- **与「回归基线」硬隔离**:系统里 `verification:"回归基线"` 是「预期来自现状锁定」的 oracle
  概念,与「失败即阻塞」的回归集**正交**(名字撞车但含义无关)。代码用 `suite*` 命名、规则
  文档写正交区分表——这是本功能最大的长期风险点(后人/AI 混淆两口径会污染通过率)。
- **门控只加一停,不加三停**:讨论过「每步都批准」与「执行后再确认」,用户拍板只在用例后停
  ——需求分析产物会被用例步再消化一次,执行结果由报告呈现,唯有用例是「测试的契约」,
  停这一处收益最大、打断最小。多任务批量维持直通(批量的意义就是无人值守)。
- **审计文件独立于报告目录**:报告目录随任务删除,审计放 `AI_LabTest/audit/` 不受删除影响
  ——「删任务留痕」是审计的底线要求,借目录结构免费获得,无需在删除逻辑里做白名单。
- **存量推荐不让 AI 写文件**:revise 模式(AI 覆盖整份产物)对「只改标签」场景太重且会丢
  字段。行协议(@@RECOMMEND)+ 代码 merge,AI 只判定、平台只动 tags,风险面缩到最小。

## 已知局限与方向

- 回归集判定质量取决于需求文档质量;克制原则(≤30%)靠 prompt 约束,无硬校验。
- 批量模式绕过门控是有意取舍;若未来「批量也要审」,可给 pumpQueue 加同款 gatedRunAll 逻辑。
- 审计只记「做了什么」不记产物 diff;要追「批准时用例长什么样」可结合 cases.json 的 git 历史。
- 报告历史对比(diffRuns)暂未纳入回归集维度,快照里已有 suite 字段,需要时前端补展示即可。
