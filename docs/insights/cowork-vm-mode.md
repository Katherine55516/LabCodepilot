# Cowork 办公模式 — 产品思考

> 技术实现见 [docs/handover/cowork-vm-mode.md](../handover/cowork-vm-mode.md)
> 完成时间:2026-07-14 · 状态:macOS MVP(E1-E5)已交付内部试用

## 解决什么用户问题

AI Native Lab 的既有形态是研发工具:会话绑项目文件夹,agent 直接读写真机文件。这对开发者是效率,对**办公场景**是障碍——"我想让 AI 帮我处理一个 Excel/改一批文档",用户既不想选'项目文件夹',更不放心把整台电脑的文件系统交给 agent。信任门槛是办公场景铺开的第一障碍。

办公模式的回答:**agent 在一台本地虚拟机里干活,你的电脑它根本看不见**。文件通过对话发进去、产物通过卡片拿出来,交换面收窄到"你亲手给的"和"你亲手取的"。安全故事从"请相信 AI 不会乱动"变成"AI 想动也动不着"——后者才能讲给非技术用户听。

## 关键设计决策与理由

### 1. 双栏切换,而不是会话内开关

POC 阶段做的是输入条上的"沙箱"开关(成本最低,验证转发桥拓扑)。实测后用户拍板改为**侧边栏「办公 / 研发」双栏**(参照 Claude 桌面版 Home/Code),模式建会话时定死:

- **心智模型**:办公和研发是两种"工作场所",不是一条会话的某个属性。开关语义下,同一会话可以一半在真机一半在 VM——文件在哪、产物是谁的,没人说得清。
- **隔离承诺的完整性**:模式不可变,才能对一条办公会话说"它从头到尾没碰过你的电脑"。为此连 API 层都锁死(建后改模式直接 400)。
- **列表语义**:办公对话不绑项目文件夹,按时间平铺——办公用户根本没有"项目"概念,强行分组是研发思维的泄漏。

### 2. 拷贝语义,而不是官方 Cowork 的目录挂载

官方 Cowork 用 VirtioFS 把真机目录双向挂进 VM(agent 改动实时落回真机)。我们选择**拷贝**:上传拷一次、下载拷一次,VM 与真机文件系统零共享面。

- 挂载的便利(实时同步)恰恰是隔离的漏洞:agent 在 VM 里 `rm -rf` 挂载目录,真机文件就没了。拷贝语义下 agent 最多毁掉自己工作区的副本。
- 办公场景的文件交换是低频、小批量、有明确"交付"节点的——拷贝的交互成本(发附件/点下载)与用户心智天然吻合;研发场景那种高频全目录读写才需要挂载。
- 工程上省掉 VirtioFS 的平台差异(macOS/Windows 实现完全不同),P2 Windows 移植只需搬运输通道。

### 3. 隔离承诺是刚性的:宁可报错,绝不静默降级

POC 时代"沙箱不可用就悄悄回退宿主执行"——对产品这是**隔离违约**:用户以为在沙箱里,文件实际落了真机。E1 把它改成三道硬守卫(VM 不可用硬失败并明说"没有在真机上执行任何操作";native runtime 直接拒绝;外部 MCP 一律不加载)。原则:**宁可这轮对话失败,不可破坏承诺**。错误文案里那句"本回合已终止,没有在真机上执行任何操作"就是承诺的落地。

### 4. 能力做减法:办公会话只留"对话 + 文件收发"

办公会话隐藏了全部研发特性(文件树/Git/任务面板/计划模式/权限选择器/斜杠命令/@ 引用/回滚)。这不只是"简洁",每一项都有隔离或诚实理由:

- **@ 引用、文件树**引用的是宿主路径——对 VM 里的 agent 是无意义的幻觉,留着就是在骗用户。
- **权限选择器**:VM 隔离本身就是权限故事,办公会话创建即全自动(full_access),不弹批准。"不用一次次点允许"反而成了卖点。
- **外部 MCP**:stdio 类在 VM 里没有 npx/uvx,必然静默失败;与其半残,不如明确不加载并写进 agent 的系统提示(agent 自己知道边界,不会瞎承诺)。
- **斜杠命令/技能**:宿主侧概念,VM 内不存在,连输入 `/` 的弹窗都不给。

### 5. 产物卡片 = 唯一的"取件口",必须永远反映真相

产物清单最初是"只增不减"的累计合并,用户实测立刻抓到:agent 删掉的文件还赖在卡片上,点下载没反应。修复把语义整体升级为**回合末权威快照**——卡片展示的永远是 VM 工作区此刻真实存在的文件,删除实时消失、全删光卡片消失、下载命中已删文件会明说并自动刷新。取件口撒谎一次,隔离故事的可信度就清零,这里值得为对账多付一次 RPC。

### 6. 存储要自我管理(用户提出的担忧)

删除会话时 VM 在睡觉 → guest 里的会话目录成孤儿 → 日积月累占满虚拟盘。方案是**启动时对账**:VM 每次就绪,对照数据库现存会话清单,删掉 guest 里多余的目录。选"启动时对账"而不是"删除时重试队列",因为前者一个幂等操作覆盖所有失败路径(删除失败/崩溃/手动清库),后者要维护队列状态。

## 用户实测驱动的迭代

内部试用(3.1.10→3.1.13)四轮反馈,全部当日修复:斜杠弹窗漏网、CLI 工具跳转被办公 landing 吞掉预填、切栏主区不跟随、产物删除不刷新(两轮:对账缺失 + 空快照被吞)。共性教训:**隐藏一个入口 ≠ 关闭一条路径**(按钮藏了,快捷键/直输/跳转还在);**语义改造要贯通到事件链每一层**(服务端改快照语义,前端还留着增量守卫,就会出现"只删不建的回合不刷新"这种切面 bug)。

## 镜像流水线(M1-M4,3.1.15→3.1.17):从"内部试用"到"装上就能用"

办公模式 E5 交付后最大的鸿沟不是功能而是**分发**:五项资产(3GB 镜像、seed、SSH 密钥、253MB claude 二进制、brew 装的 vfkit)全靠手工复刻,换台机器就是死的。流水线的目标只有一句话:**全新 Mac 装上 DMG 就能用办公模式,零手动预置**。

**最重要的方案决策是一次"倒置"**:原设想"CI 构建定制镜像 + 托管分发",在"GitHub 国内几乎不可用、中科大只镜像公共开源项目(托管不了自制产物)"的双重约束下走不通。倒过来想——**不自制镜像**:上游 Debian 底镜走中科大(公共镜像天然可达),我们的全部定制(daemon、systemd、关 sshd)改成应用本地生成 cloud-init seed **首启自注入**;claude 二进制走 npmmirror 的 SDK 平台子包(与宿主 SDK 天然同版本);vfkit 打进 app 包。结果:**零自建托管、零 CI 产物、SSH 照样彻底退役**,分发问题整个消解而不是被解决。教训:当"托管在哪"变成难题时,先问"能不能不托管"。

**显式下载而非静默预热**(用户拍板):官方 Cowork 启动即偷跑下载曾被用户吐槽"未经提示占了 10GB"。我们选择用户点「下载沙箱环境(约 3.2 GB)」才开始——尊重不用此功能的用户的流量与磁盘,代价是首开用户要等一次下载(进度条 + 下载中禁发提示补偿感知)。

**信任由实证支撑,不由声明支撑**:流水线每期都以"取证"收尾——guest 内 `systemctl is-enabled ssh` 应答 masked、断点续传后最终 sha512 通过(前缀重哈希的硬证明)、打包后 vfkit 与 brew 原件逐位一致。其中打包实证抓到真坑:electron-builder 会用默认 entitlements 重签 vfkit,剥掉 Virtualization.framework 硬要求的 entitlement——不实测就发布,用户拿到的就是"沙箱起不来"的包。**"必须 POC"清单上的项,没有一项是白列的。**

**升级机制顺势而为**:daemon 升级 = seed 模板版本 bump(cloud-init per-instance 语义,instance-id 变即重灌),不造热更新协议;guest claude 二进制偏斜 = health 上报大小、宿主比对重推;镜像升级 = 设置页可选按钮,**升级下载期间办公照常可用**(usable 与 overall 分离的语义就是为这个)。

## P3 安全强化(3.1.17 后):从"保护真机"到"保护凭证与数据"

E1-E5 + 流水线守住的是"agent 碰不到你的电脑"。但办公模式的核心用法是**把不可信文件喂给 agent**——一份被提示注入的文档,可以指挥 agent 干它权限内的坏事。P3 换了个威胁模型:**保护你的凭证与数据**。

**范围是一次减法,不是加法**:安全能做的很多(白名单、出网收口、每会话网络隔离…),但用户明确**只做两项 + 审计,不做出网白名单**——因为白名单会让"画图装包、查网页、下链接"这些真实办公用法失效,用户判断自由联网的产品价值 > 数据外流防护,并接受这个风险。这是个知情决策。安全设计的第一步常常是问"这个威胁用户在乎吗",而不是"技术上能不能防"。

**每会话隔离用最朴素的手段**:不上 bwrap/命名空间,就是 Linux 用户 + setuid 降权 + 目录 700。云镜像自带,不往镜像塞新东西,文件系统权限层面封死跨会话读。朴素方案的坑不在设计而在**启动时序**——daemon 提权到 root 有个 cloud-init 竞态窗口,dev 单测测不出,两次撞到"claude 秒退"才挖出来(就绪判定必须确认 daemon 已 root 才开跑,fail-secure)。教训:凡涉及 VM 内进程权限的改动,单测给不了信心,必须冷启动实测。

**凭证不进 VM 的关键是"换个地方注入"**:真 key 从来都要用,问题只是"在哪注入"。原来在 VM 里(claude 的 env),提示注入就能偷;改成在宿主的代理里注入——VM 里的 claude 只拿一个可废止的一次性 token,真 key 永不过河。POC 先验最不确定的假设(claude 接受本地 http base_url 吗?),过了才产品化。通道选型上,NAT 网关比 vsock 反向简单得多,而且和"通用出网走 NAT"统一——**能用现成的网络路径,就不造新的隧道**。

**审计放宿主侧,不放 VM**:宿主是 VM 的唯一出入口(vsock + 代理),所有"数据进出"和"凭证使用"都必经宿主;宿主侧日志 VM 被攻陷也改不了,更可信,还省掉改 daemon 的一轮冷启动实测。审计的正确位置由信任边界决定——记录方不能是被审计方。

## 已知局限

- **仅 macOS(Apple Silicon)**:Windows 走 WSL2 是 P2;Intel Mac 明确不支持(用户拍板)。
- **数据外流未收口(有意为之)**:VM 内 agent 可自由出网(NAT),被注入的 agent 理论上能把工作区文件 POST 到任意地址——这是用户接受的风险(换自由联网的办公价值)。P3 保护的是**凭证**(不进 VM)与**会话间隔离**,不是数据外流。
- **会话隔离到用户级,非命名空间级**:每会话独立 Linux 用户 + 目录 700(P3-A);没有每会话独立网络命名空间(与自由上网决策冲突,不做)。
- **产物≠工作区全量**:卡片只列 agent 产出(不含历史上传原件),打包下载才是全量——语义上有意为之,但可能需要向用户解释。
- **底镜 3GB 未压缩**:vfkit 只认 raw,qcow2 转换需重依赖不值得;将来嫌大可加公司 OSS 挂 zstd 压缩源(manifest 天然多源,架构不用动)。
- **真证书签名待解**:接 Developer ID 签名/公证时,vfkit 须用同 Team ID 重签且带 virtualization entitlement(handover 坑18);宿主代理明文 loopback 在单 VM 可接受,多 VM 或更强隔离需求下要重新评估。

## 未来方向

1. **P2 Windows**:WSL2 私有 distro;拷贝语义使移植面收窄到传输通道一层。
2. **办公技能生态**:VM 内预装 pandoc/libreoffice 等办公工具链,让"处理文档"开箱即用——这是办公模式从"安全"走向"好用"的下一步。
3. **审计可视化**:审计日志现只落盘(readRecentAudit 已备),可加设置内查看面供企业合规。
4. **消息排队**(D4 后置项):下载中发消息、就绪后自动开跑(调研 §7.1 完整设计在案)。
