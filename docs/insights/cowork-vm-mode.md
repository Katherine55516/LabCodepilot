# Cowork 办公模式 — 产品思考

> 技术实现见 [docs/handover/cowork-vm-mode.md](../handover/cowork-vm-mode.md)
> 完成时间:2026-07-14 · 状态:macOS MVP(E1-E5)已交付内部试用

## 解决什么用户问题

AI Native Lab 的既有形态是研发工具:会话绑项目文件夹,agent 直接读写真机文件。这对开发者是效率,对**办公场景**是障碍——"我想让 AI 帮我处理一个 Excel/改一批文档",用户既不想选'项目文件夹',更不放心把整台电脑的文件系统交给 agent。信任门槛是办公场景铺开的第一障碍。

办公模式的回答:**agent 在一台本地虚拟机里干活,你的电脑它根本看不见**。文件通过对话发进去、产物通过卡片拿出来,交换面收窄到"你亲手给的"和"你亲手取的"。安全故事从"请相信 AI 不会乱动"变成"AI 想动也动不着"——后者才能讲给非技术用户听。

## 关键设计决策与理由

### 1. 双栏切换,而不是会话内开关

POC 阶段做的是输入条上的"沙箱"开关(成本最低,验证转发桥拓扑)。实测后用户拍板改为**侧边栏「办公 / 研发」双栏**(参照 Claude 桌面版 Home/Code),模式建会话时定死:

- **心智模型**:办公和研发是两种"工作场所",不是一条会话的某个属性。开关语义下,同一会话可以一半在真机一半在 VM——文件在哪、产物是谁的,没人说得清。
- **隔离承诺的完整性**:模式不可变,才能对一条办公会话说"它从头到尾没碰过你的电脑"。为此连 API 层都锁死(建后改模式直接 400)。
- **列表语义**:办公对话不绑项目文件夹,按时间平铺——办公用户根本没有"项目"概念,强行分组是研发思维的泄漏。

### 2. 拷贝语义,而不是官方 Cowork 的目录挂载

官方 Cowork 用 VirtioFS 把真机目录双向挂进 VM(agent 改动实时落回真机)。我们选择**拷贝**:上传拷一次、下载拷一次,VM 与真机文件系统零共享面。

- 挂载的便利(实时同步)恰恰是隔离的漏洞:agent 在 VM 里 `rm -rf` 挂载目录,真机文件就没了。拷贝语义下 agent 最多毁掉自己工作区的副本。
- 办公场景的文件交换是低频、小批量、有明确"交付"节点的——拷贝的交互成本(发附件/点下载)与用户心智天然吻合;研发场景那种高频全目录读写才需要挂载。
- 工程上省掉 VirtioFS 的平台差异(macOS/Windows 实现完全不同),P2 Windows 移植只需搬运输通道。

### 3. 隔离承诺是刚性的:宁可报错,绝不静默降级

POC 时代"沙箱不可用就悄悄回退宿主执行"——对产品这是**隔离违约**:用户以为在沙箱里,文件实际落了真机。E1 把它改成三道硬守卫(VM 不可用硬失败并明说"没有在真机上执行任何操作";native runtime 直接拒绝;外部 MCP 一律不加载)。原则:**宁可这轮对话失败,不可破坏承诺**。错误文案里那句"本回合已终止,没有在真机上执行任何操作"就是承诺的落地。

### 4. 能力做减法:办公会话只留"对话 + 文件收发"

办公会话隐藏了全部研发特性(文件树/Git/任务面板/计划模式/权限选择器/斜杠命令/@ 引用/回滚)。这不只是"简洁",每一项都有隔离或诚实理由:

- **@ 引用、文件树**引用的是宿主路径——对 VM 里的 agent 是无意义的幻觉,留着就是在骗用户。
- **权限选择器**:VM 隔离本身就是权限故事,办公会话创建即全自动(full_access),不弹批准。"不用一次次点允许"反而成了卖点。
- **外部 MCP**:stdio 类在 VM 里没有 npx/uvx,必然静默失败;与其半残,不如明确不加载并写进 agent 的系统提示(agent 自己知道边界,不会瞎承诺)。
- **斜杠命令/技能**:宿主侧概念,VM 内不存在,连输入 `/` 的弹窗都不给。

### 5. 产物卡片 = 唯一的"取件口",必须永远反映真相

产物清单最初是"只增不减"的累计合并,用户实测立刻抓到:agent 删掉的文件还赖在卡片上,点下载没反应。修复把语义整体升级为**回合末权威快照**——卡片展示的永远是 VM 工作区此刻真实存在的文件,删除实时消失、全删光卡片消失、下载命中已删文件会明说并自动刷新。取件口撒谎一次,隔离故事的可信度就清零,这里值得为对账多付一次 RPC。

### 6. 存储要自我管理(用户提出的担忧)

删除会话时 VM 在睡觉 → guest 里的会话目录成孤儿 → 日积月累占满虚拟盘。方案是**启动时对账**:VM 每次就绪,对照数据库现存会话清单,删掉 guest 里多余的目录。选"启动时对账"而不是"删除时重试队列",因为前者一个幂等操作覆盖所有失败路径(删除失败/崩溃/手动清库),后者要维护队列状态。

## 用户实测驱动的迭代

内部试用(3.1.10→3.1.13)四轮反馈,全部当日修复:斜杠弹窗漏网、CLI 工具跳转被办公 landing 吞掉预填、切栏主区不跟随、产物删除不刷新(两轮:对账缺失 + 空快照被吞)。共性教训:**隐藏一个入口 ≠ 关闭一条路径**(按钮藏了,快捷键/直输/跳转还在);**语义改造要贯通到事件链每一层**(服务端改快照语义,前端还留着增量守卫,就会出现"只删不建的回合不刷新"这种切面 bug)。

## 已知局限

- **仅 macOS(Apple Silicon)**:Windows 走 WSL2 是 P2;Intel Mac 未验证。
- **镜像手动预置**:VM 镜像与 claude 二进制(~3.3GB)需按 README 手工放置,没有下载流水线——这是内部试用与公开发布之间最大的一段路。
- **网络未收口**:VM 内 agent 可自由出网(NAT)。凭证经 env 过河不落 VM 盘,但 P3 之前谈不上"数据不出去"。
- **同际会话并发**:单 VM 多会话靠目录隔离,没有每会话独立用户/命名空间(P3)。
- **产物≠工作区全量**:卡片只列 agent 产出(不含历史上传原件),打包下载才是全量——语义上有意为之,但可能需要向用户解释。

## 未来方向

1. **镜像流水线**(公开发布的前提):镜像+daemon 烘进安装包或首启下载+后台预热,SSH 彻底退役。
2. **P2 Windows**:WSL2 私有 distro;拷贝语义使移植面收窄到传输通道一层。
3. **P3 安全强化**:宿主代理注入 token(凭证永不进 VM)、出网白名单、每会话非特权用户。
4. **办公技能生态**:VM 内预装 pandoc/libreoffice 等办公工具链,让"处理文档"开箱即用——这是办公模式从"安全"走向"好用"的下一步。
