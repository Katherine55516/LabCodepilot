# 冒烟测试：把一份提示词变成第三种测试形态（产品思考）

> 技术实现见 [docs/handover/smoke-test.md](../handover/smoke-test.md)

## 解决什么问题

用户此前的冒烟测试是**手工投喂提示词**：一份带 `<系统名称>`/`<URL>`/cookie/`<模块入口>`/场景清单占位符的 md 模板，每次冒烟复制一份、手填五处、粘给 AI。痛点不在提示词本身（它已被打磨得很好），在**重复劳动与配置漂移**：环境地址和登录态每次重填、全局规则每次随文携带（改一处要改所有副本）、结果散落在对话里无法沉淀复核。

产品化的判断标准很简单：**每次都相同的内容沉淀进平台，每次都不同的才留给表单。**拆完发现每次真正变的只有三样——模块名称、模块入口、场景清单。这就是新建冒烟任务只有 3 个必填项的由来。

## 为什么是"第三形态"而不是别的做法

- **不做成功能测试的"轻量模式"**：冒烟回答的问题（主流程通不通）与功能测试（新功能对不对）不同，用例形态（轻场景 vs 12 列）、执行方式（自主探索 vs 按步骤）、结论口径（能否进入下一阶段 vs 双口径通过率）全都不同。硬塞进功能测试会让两边的口径互相污染——冒烟场景被拉去算八维覆盖率，或功能用例被降级成两栏场景。
- **不照抄回归的独立工作区**：回归的库/套件/轮次是跨任务聚合结构，冒烟没有这些概念。照抄形态是纯开销（回归工作区约 2000+ 行独立组件树）。冒烟本质上就是"一种更轻的任务"，所以走任务子类型：看板、流程视图、排队并发、报告区、审计、统计，全部白拿。
- **入口做成第三段页签**与回归对齐（形态=页签），功能看板不被冒烟任务打散，入口一眼可见。

## 几个反直觉的设计决策

**无门控（创建即跑）**。功能测试的用例设计有人工门控，冒烟却砍掉了确认环节。理由：冒烟的价值密度在"快"——提测后第一时间知道主流程通不通；场景是用户自己手写的（不是 AI 生成的），"确认自己刚写的东西"是仪式而非保险。补偿机制是场景事后可改可重跑。如果未来加入 AI 生成场景（P2），生成来源可能需要恢复一道停顿——那时"确认 AI 猜的东西"才有真实价值。

**缺预期不臆造**。场景行没写预期结果时，平台不替用户编一个，而是原样保留并在表单实时标出"N 条未写预期结果"。替用户编预期等于把"锁现状"伪装成"验对错"——这是测试产品最不该越的界。同理，场景整理 prompt 的铁律是"只审不改写"：发现问题列成审核提醒交用户裁定。

**Bug 复核不发明新机制**。用户要求"人工对 Bug 清单复核"，最省事的做法是新建一套复核状态。但平台已有报告复核体系（report_reviewed 事件 + AI 判定准确度 KPI + DB 回显），而冒烟的 Bug 恰好与失败场景 1:1——复核一条 Bug 就是复核一条场景判定。于是三个动作（确认缺陷/误报/程度不符）直接映射到既有 verdict（accurate/false_fail/severity_mismatch），零新事件类型，冒烟的复核自动汇入全局准确度统计。**新增的只有人工可写的两个字段**（严重级别、备注），落在旁路 bugs.json，绝不碰 run.json——"四态由代码算、不由人改"是这个测试模块从第一天起的立身之本。

**双记录结论**。复核把全部失败判为误报后，横幅转"通过（经人工复核，N 项误报已排除）"，但 AI 原判在场景表和报告 md 里原样保留。不做"复核后改写报告"：报告是 AI 产物的快照，复核态是叠加层。这保住了两件事——追溯（AI 当时怎么判的）和统计诚实（准确度 KPI 的分母不被事后修饰）。严重级别同理：人工改后 UI 显示"AI: 致命"小字，改动可见、原判可查。

**复核态绑定执行轮（runHash）**。重跑执行后，上一轮的"误报"标记如果还挂在同名场景上，会让新一轮的真失败被旧复核掩盖。所以覆盖层严格按 runHash 绑定：重跑即失效，旧页面的写入被 409 挡住。宁可让用户重复复核一次，不让复核结论错挂轮次。

**体验观察与四态正交**。原提示词的特色章节"奇怪交互/体验问题"（响应慢、无反馈、状态不同步）被保留为 `@@OBSERVATION` 通道，但明确划界：观察不影响 pass/fail、不产生 Bug、不计入通过率。执行 prompt 里专门写了护栏"不要因为发现体验问题就把功能正常的场景判 fail"——否则冒烟结论会被体验瑕疵稀释，"主流程通不通"变成"体验好不好"。

## 用户反馈驱动的迭代（三轮沟通全记录在方案 §7）

1. 初版原型把"被测地址"做成了新建表单的输入框 → 用户指出**环境配置是通用的，应沿用**。改为只读环境块 + 可选任务级覆盖，"冒烟不建第二套环境体系"升级为设计原则。
2. 用户要求**提示词所有 `<>` 占位符转为页面输入** → 产出占位符→页面来源映射表（方案 §4.7），并在表单底部加了"以下内容由平台提供"只读说明块——让用户确认那三段固定内容"没丢，只是被平台接管了"。
3. 用户要求 **Bug 清单列表化 + 人工复核**、场景输入框文案对齐原提示词措辞、AI 生成降为 P2（仅手动录入）——每条都收敛为上面的具体设计。

## 已知局限

- 自主探索执行没有固定步骤兜底，判定质量依赖 AI 对页面的观察——与用户手工投喂提示词时代同性质，产品化没有让它变差，但也没有让它变稳。
- `@@OBSERVATION` 是新标记，网关模型的裸写遵从性需打包实测（@@RESULT 有过被 markdown 装饰污染的前科，解析器已容忍装饰，但观察丢失只能靠 prompt 纪律）。
- 场景质量完全取决于用户录入的颗粒度；表单提示语与实时解析预览是仅有的两道软约束。

## 未来方向

- **AI 生成场景**（P2 首位）：按模块描述生成主流程场景；届时"生成后停一下确认"的门控值得恢复。
- **从功能任务提炼**：`CASE_TAGS` 里既有的「冒烟测试」人工标签是天然的数据源——用户在功能用例上打过标的，就是他们心中的主流程。
- **定时冒烟**：部署后自动跑一轮 + 通知，把"提测第一时间"推进到"部署零时刻"。
- **统计分桶与上报**：Stats 看板冒烟独立口径、usage-rollup `smoke_*` 字段（需守住冻结契约的增列纪律）。
