# 测试工作台 · 回归用例库(产品思考)

> 技术实现见 [docs/handover/regression-library.md](../handover/regression-library.md)
> 前置特性:[test-regression-suite.md](./test-regression-suite.md)(回归集标签)

## 解决什么用户问题

上一版给了「回归集标签」——单个任务里,哪些用例是「失败即阻塞发版」的核心用例。但标签**散落在各任务里**:测了 8 个功能,就有 8 份用例文件,回归用例埋在各自的 cases.json 里。用户下次发版想「把所有该跑的回归用例跑一遍」,没有一个地方能一次看到、一次跑完。

用户原话:**「我希望每一次测试任务跑完后,这个测试任务的回归测试用例都能放到回归用例库中。」**——要的是一个**跨任务汇集**的地方,让回归用例从「一次性标签」变成「持续积累的资产」,并且能整体重跑。

## 三个关键决策(用户拍板)

### 1. 入库范围:全部「回归测试」标签用例,不看本次结果
不是「只入库跑通过的」。理由:回归用例**失败恰恰是下次发版最该重跑监控的**——如果只沉淀通过的,失败的回归用例反而被漏掉,与「回归 = 盯住会阻塞发版的东西」的初衷相悖。库定义的是「**该重跑哪些**」,与「这次通没通过」解耦。

### 2. 入库时机:用例设计完成后,不等执行
用户原始说「跑完后」,澄清时改成**「用例设计完过后」**。这更准也更自洽:既然入库不看执行结果(决策 1),用例一设计好、标签一打上,就能沉淀——不必等到执行甚至报告。技术上也更干净:后端在用例设计步流结束时自动 upsert,不依赖用户是否真去跑。

### 3. 本轮就做「一键重跑」
用户明确要「连把库当跨任务套件一键重跑一起做」。这是库的**价值闭环**:光沉淀不能跑,库只是个清单;能整体重跑,它才成为「发版前跑一遍回归」的实际抓手。

## 为什么这样设计而不是别的

### upsert by 来源任务,而非追加
同一任务会反复跑、反复改用例。若每次入库都追加,库会迅速被重复用例淹没。改成「**某任务再次入库=覆盖它上次的全部贡献**」:库永远反映各任务**当前**的回归集,改了标签(加/减)库自动同步。代价是实现上要按来源任务删旧再插新,但换来库永远干净、可信。

### 项目级,不是全局
一个项目 = 一个被测系统。库落在项目的 `AI_LabTest/` 下、每项目独立。这样重跑时能直接复用项目已配置的被测环境(`environments.json`)——跨项目聚合会立刻遇到「打哪个地址、用哪套账号」的死结。

### 重跑复用现有执行机器,不另造
「一键重跑」没有新写一行执行逻辑:把库聚合成一个用保留任务名(`回归用例库`)的普通用例集,然后走**完全相同的** `/api/test/run` 执行+报告流程。好处是可达性闸门、登录态注入、录像、四态归约、回归集红线——全部免费继承。跨任务用例 id 会撞号(两个任务都有 TC-001),用「来源任务::原ID」命名空间化解决,避免执行结果串号。

### 入口放项目头,不放任务详情
库是项目级资产,最初误放在任务详情头(要先选中某个任务才够得着),CDP 实测时立刻发现别扭——改到项目看板头(与「环境配置/新建任务」同排),不选任务就能进库。**入口位置要匹配数据的作用域**。

### 自动入库失败必须静默
入库是「增强」,不是「主线」。它绝不能因为写库出错就拖垮「出用例」这件用户真正要的事——所以全链路 fire-and-forget、失败静默,和操作审计同一策略。

## 已知局限与未来方向

- **真实 AI 打标质量未验证**:库入库的「是不是回归用例」完全取决于上一层 AI 按「失败即阻塞」标准打的 `tags`。这层判断的准确度,dev 无凭证跑不了真实 AI,需打包登录后终验。库本身只是忠实汇集,不替 AI 判断。
- **重跑报告未按来源任务分组**:目前按用例呈现,溯源信息(idMap)已具备,可后续在报告里按来源任务归组,让「哪个功能的回归挂了」一眼可见。
- **导出**:库暂只支持查看+移除,未做 xlsx 导出;真正的价值也不在导出,而在「一键重跑」。
- **积累越久越值钱,也越需要维护**:库会随项目持续变大。未来可能需要「按上次重跑时间排序」「标记长期不过的用例」等治理手段,避免库变成一个没人跑的僵尸清单。

# v2 一期：从「能重跑」到「可信的发版回归」（2026-07-10）

> 技术实现见 [docs/handover/regression-library.md](../handover/regression-library.md) v2 章节;竞品对标与决策全文见 [docs/research/regression-library-v2-benchmark-proposal.md](../research/regression-library-v2-benchmark-proposal.md)

## 为什么有 v2:v1 的三个「回答不了」

v1 交付后用户要求对标市场成熟回归测试产品(TestRail/Xray/MeterSphere/Azure Test Plans)。多代理竞品调研 + 独立批判后,暴露 v1 回答不了的三个问题:**这轮比上轮多挂了什么**(同环境重跑覆盖上一轮,历史即焚);**哪个功能的回归挂了**(报告按命名空间 runId 平铺);**能不能只跑一部分**(永远全量,AI 执行烧时间烧 token)。

## 关键决策(用户拍板)

1. **模块不做独立功能**——不建模块树。`module` 只是用例字段,检索与套件条件消费它;「按范围圈选」统一由套件承担,不引入第二套组织概念。
2. **套件提至一期**——用户认定套件是核心。技术上也自洽:发起弹窗本来就要重做,一期不做套件、二期回头再改一遍弹窗是返工;套件只依赖库本身,零轮次数据依赖。
3. **轮次原子性**——一轮=一套件×一环境×一模式。多套件诉求用并集套件解决,未来高频再考虑「批次」容器(对齐 TestRail Plan 语义),不打破轮次原子性——否则套件交集去重后红线口径说不清。

## 为什么这样设计而不是别的

- **套件=保存的查询,不是文件夹**(Azure Query-based Suite/TestRail Dynamic Filter 的共识,也是 MeterSphere/禅道用户抱怨多年的缺失):查询套件存条件不存清单,新入库命中自动进入,零维护;静态套件留给精挑细选的发版集。**标签管进库,套件管圈跑**,两层各司其职。
- **快照是执行历史可信度的地基**:AI 高频改写用例,upsert 直接覆盖——没有快照,三周前报告里的 TC-003 会被今天的第 5 版张冠李戴。竞品铁律「执行记录必须绑定用例不可变副本」(TestRail Close 即快照)在 AI 场景从最佳实践升级为必需品。成本一次文件拷贝。
- **delta 用交集口径**:两轮套件可能不同,上一轮没跑到的用例不判「新增失败/已修复」——结论只能建立在实际执行过的范围上。复测轮不作 delta 基准,同理。
- **中断惰性收口**:桌面应用被随手关掉是常态,不依赖进程退出钩子;读侧发现 running 超 2h 视图归一 aborted,不回写(避免读放大)。
- **估算宁缺毋滥**:时长估算用近 3 个已收口轮的实测均值;无历史显式「首轮暂无估算」,不出瞎数。token 估算因无数据源明确不做,不放占位假数。
- **并发写用 seq 不用时间戳**:实测发现 updatedAt 毫秒粒度在同刻写入时失效(单测抓出),换单调写入序号。

## 批判环节改掉了什么(值得记的教训)

独立批判代理对综合方案的修正,多数进了实现:复测轮红线必须按合并口径(2/2 通过≠可发版,二期实现、数据结构一期预留 parentRoundId/mode);跨轮翻转≠flaky(版本在变,「挂了又修好」恰是回归正常工作的样子,终判须同版本重跑——三期);rev 字段级 diff 时间线降级(AI 是唯一改写者,快照对照已够,省 M 级工作量);pinned 含义落在当下(必跑白名单)而非为未来智能裁剪预留概念。

## 批 H 追加(2026-07-10):从弹窗到页面

上线当天用户用真实项目(21 条用例)体验后反馈:回归用例库装在弹窗里不对——**功能测试与回归测试是项目下两种平级的测试类型**,回归测试应是和任务看板同级的整页工作区,而不是看板上的一个弹窗。改造为项目头类型切换(功能测试|回归测试)+页内子页签,只有「发起回归」保留为确认对话框。教训:**容器的规格要匹配内容的地位**——当一个功能从「附属操作」长成「一类工作」,弹窗就该让位给页面(与 v1「入口位置要匹配数据作用域」是同一条设计肌肉)。

## 未来方向(按期)

二期:失败复测环(合并红线)、评审门禁(pending 曝光+存量回填 approved)、缺陷实体闭环、rev、手工结果兜底、xlsx 导出。三期:stats 逐用例历史→flaky(AI 就地复核终判)/连败/stale 队列、隔离区(带「隔离中 N 条未计入」强制曝光护栏)、AI 失败归因。远期差异化:变更驱动选例(桌面工具拿得到 git diff,TestRail 们结构性做不到)、用例自愈、语义去重。

# v2 二/三期：从「可信的发版回归」到「可治理的回归资产」（2026-07-10）

> 执行计划见 [regression-library-v2-phase23.md](../exec-plans/active/regression-library-v2-phase23.md)
> 交互原型（用户提供，6 屏）：Artifact `6b854a65-79f4-40bc-89ca-769a29c16680`

## 为什么还要二/三期：一期回答不了的问题

一期让「发版前跑一遍回归」变得可信（轮次留痕 + 快照）、可圈选（套件）、可读（按来源任务分组 + delta）。但库跑了几周之后，用户会开始问一些一期答不了的问题：

1. **「这条用例老是红，到底是产品坏了还是用例坏了？」** —— 一期只给 pass/fail，不给归因。
2. **「这条一会儿红一会儿绿，是 flaky 还是真有问题？」** —— 一期没有跨轮视图，判不了。
3. **「有条用例挂了一个月了，明天要发版，我能不能先绕过它？」** —— 一期只能删，删了就再也没人记得它挂过。
4. **「AI 刚重新生成了用例，我上周确认过的那些还算数吗？」** —— 一期没有评审态，也没有版本。

这四个问题都不是「跑得更快」能解决的，它们是**资产治理**问题。用例库跑起来那天就成了资产，资产需要状态、版本、生命周期和护栏。

## 关键设计决策

### 隔离必须被曝光，否则它就是遮羞布

「先绕过它」是真实需求——不能强迫用户在「删掉这条回归用例」和「发不了版」之间二选一。所以有了隔离区：隔离的用例不进聚合、不计红线。

但隔离天然是个危险功能：它把「回归挂了」变成「回归全绿」，而且**没有任何人会主动去看隔离区**。所以隔离从设计第一天就带着三道护栏：

- 每份轮次报告的横幅**强制**显示「⛔ 隔离中 N 条未计入」，用户躲不开；
- 隔离占比 >10% 时健康度页顶部告警；
- 每次隔离/恢复都记审计，能回溯「谁在发版前把哪条挂掉的用例隔离了」。

还有一处克制：健康度的**连败队列不提供「隔离」按钮**，只提示转缺陷。连续失败 3 轮以上的用例，正解是修，不是藏。给了按钮，人就会点。

### 评审态不参与发版红线

原型里「待确认 / 已确认」很自然会让人想做成硬门禁：没确认的用例不许跑、或者没确认就不许发版。但存量项目里有成百上千条用例，一旦上线就是**一夜之间全项目无法发版**。

所以：存量条目读为 `approved`（零迁移），新入库默认 `pending`，评审态只影响「仅执行已确认用例」这个开关和库里的曝光。红线口径一个字没改。治理功能不能以「让所有人先停下来做数据清洗」为代价上线。

### upsert 不能抹掉人工资产

`depositTask` 的语义是「用当前用例集刷新这个任务的库贡献」——一期它就是删旧插新。二期加了 `_lib` 之后，这个实现会**把用户手动确认过的评审态、隔离状态、rev 历史全部抹掉**，而且是静默的。

改成按 `originalId` 继承。判断「用例内容是否真变了」用语义指纹（排除 `id`/`tags`——打标是「是否入库」的决策，不是内容变更），变了才 `rev+1` 并记一条时间线。

### 跨轮结果不物化

原型注释里写的是 `回归用例库.stats.json`（每轮收口时增量写入逐用例结果）。实现时选了读侧现算：`run.json` + 快照 `idMap` 已经是唯一真相源，再存一份必然带来漂移（谁修了 run.json？存量轮次怎么回填？），而收益只是省几十次文件读。限流近 20 轮 + 进程内缓存，成本就没了。

**真相源只能有一个**，这条比性能重要。

### 预览必须和实跑共用一个函数

发起弹窗要显示「将执行 N 条」，而真正圈选在服务端。最省事的写法是前端照着规则重算一遍——然后它就会漂移：pinned 忘了并入、隔离忘了排除、复测轮的口径和全量轮不一样。

所以 `resolveRunScope` 是唯一实现，预检接口和发起接口都调它。这不是洁癖，是因为**「预检说 12 条、实跑 15 条」这类 bug 极难被发现**，用户只会觉得「这个数字好像不太准」，然后再也不信任预检卡。

同一类问题在实现中被抓到过一次：模式提示写着「4 条失败 + 📌必跑」，但 4 是**含 pinned 的总数**（失败只有 2 条）。数字名实不符，于是把 `baseFailedCount` 与 `hits` 分开返回。

### 复测轮的红线是合并口径

「仅复测上轮失败」是个很自然的功能，也是个很自然的陷阱：复测轮只跑 2 条失败用例，两条都过了 → 报告显示 `2/2`、100% → 「可以发版了」。

但另外 14 条用例这轮压根没跑，它们的最新状态还停在上一轮。真实结论可能是 13/15。所以复测轮**不看自身通过率**，看合并口径（每条用例截至该轮的最新结果）。实现里这条被单测和端到端各钉了一遍。

顺带一条：复测轮的基准**只取全量轮**。拿另一个复测轮当基准，失败集会逐轮收缩，最终把真正没修好的用例漏出回归范围。

### AI 归因是建议，不是结论

失败归因分四类（产品缺陷 / 测试用例问题 / 环境问题 / 疑似 flaky），喂给模型的事实里**必须包含跨轮历史**——「连续 4 轮失败」和「反复翻转」指向完全不同的结论，只看单轮永远分不清。

模型没有 Write 权限，平台在流尾 harvest `@@VERDICT` 行落盘（沿用 recommend 路由的范式）。分类不在枚举内的整条丢弃。UI 上标明「AI 归因」来源，转缺陷仍走人工确认。

归因产物随轮存放、随轮删除——**同一条用例这轮判「产品缺陷」，下轮修好了，不该在库里留下一条永久标记**。

### 中断的轮次不给发版结论

实现报告页时发现：一个已中断、没有执行结果的轮次会被渲染成红色的「0/0 不可发版」。看起来「保守=安全」，其实是**在伪造一个它没有的结论**——这轮根本没跑出结果，既不是可发版也不是不可发版。改成中性提示。

## 已知局限与未来方向

- **真 flaky 判定还没做**。跨轮翻转 ≠ flaky（版本一直在变），健康度的 flaky 队列只是候选。最终判定需要「AI 就地复核：同版本连跑 3 次」——入口已经在抽屉和健康度页里置灰占位。
- **行身份漂移**：矩阵的行身份是 `(来源任务, 原ID)`。AI 重新生成用例时改了 id，这条用例的历史就断了。需要在重生成时做身份继承提示。
- **自然语言转套件条件**（「只跑上轮挂过的预约相关 P0」）：原型里有，本轮置灰。
- **轮次产物只增不减**：磁盘保留策略仍是技术债务。

# 一个静默的 catch，让整轮回归撒了谎（2026-07-10）

模型把判定行写成了 `**@@RESULT {…}**`。解析器 `JSON.parse` 抛异常，`catch` 块把它吞了。三条判定全丢，平台兜底把它们补成「未执行」。报告显示 **0/3 全阻塞**，而模型判的是 **2 通过 1 失败**。

这不是解析器写得不够聪明的问题，是三个更深的问题。

## 一、同一份输入，不能有两套宽严不一的解析器

`script-trace` 用正则抽 `{…}`，宽容；`harvestResults` 用「slice 到行尾 + JSON.parse」，严格。于是 trace 里 caseId、工具轨迹、截图、录像一应俱全——**唯独结果是空的**。

排查时这份「几乎完整」的证据反而是最大的干扰：它证明执行完全正常，于是你会去怀疑执行、怀疑环境、怀疑用例，唯独不会怀疑解析。

现在 `markers.ts` 是唯一实现，服务端与客户端共用。

## 二、宽容的方向，取决于两类错误的代价

「要不要允许标记不在行首」看起来是个洁癖问题，其实是个风险问题：

- **漏采一行** = 该用例的真实判定丢失，被改写成 blocked。灾难。
- **多采一行** = 产出一个 id，但下游一律按 id 白名单过滤（`reduce` 按 `caseIds` 对齐、归因按快照 `idMap` 反解、`applyRecommend` 只改 cases.json 里已有的 id）。编造的 id 到不了任何地方。无害。

代价不对称，宽容的方向就定了：**宁可多采，不可漏采**。

评审时有人提出，应该保留那个朴素解析器，好让 `malformed` 计数继续暴露「判定被吞」的信号。这是本末倒置——**为了检测 bug 而故意留着 bug**。正确做法是解析器容忍，同时另找一个与格式无关的信号。

## 三、UI 上的沉默，才是这个 bug 真正的伤害

模型跑完了三条用例、截了图、录了像，UI 上没有任何异常。用户看着它跑，看着它「完成」，然后看到 0/3。中间没有任何一刻可以让人察觉「不对」。

所以执行进展面板不只是「让用户看到 AI 在干什么」的功能，它是一层**可观测性**：

- **对账锚点是 `tool_use` 计数**，不是 `@@CASE_START` 或 `@@RESULT`。后两者都是模型自由文本，同一次 markdown 装饰会把它们一起污染，背离就被一起掩盖了。`tool_use` 是 SDK 结构化帧，与模型的格式漂移无关。这是从事故里学到的：**监控信号不能和被监控的东西共用一条失败路径**。
- **跑完却没收到判定的用例，标「⚠ 无判定」，不是「待执行」**。它明明跑完了。一个骗人的状态，比没有状态更糟。
- **中断与判定丢失显式区分**。中断的轮天然缺判定，把两者混为一谈，真事故就会淹没在噪音里。

## 正常路径不该为诊断买单

对账条在正常时只是一行安静的 `✓`。三源读数只在背离时才拆开。诊断能力如果让每一次正常执行都变吵，它迟早会被人关掉。

## 附带发现

修完之后顺手核对了同类调用方，又找出两个「从来没成功过」的功能：`media` 路由取不到轮次维度的证据（截图点不开），`script-job-manager` 读不到轮次的 run.json（回归脚本一次都没生成过）。三者同源——v2 一期把产物迁进 `report/{task}/{roundId}/` 时，漏改了三个调用方，而它们全都用 `try/catch` 或软失败把错误咽了下去。

**静默失败会一直静默下去，直到有人从别的方向撞上它。**
