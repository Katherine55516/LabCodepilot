# 测试工作台 · 回归用例库(产品思考)

> 技术实现见 [docs/handover/regression-library.md](../handover/regression-library.md)
> 前置特性:[test-regression-suite.md](./test-regression-suite.md)(回归集标签)

## 解决什么用户问题

上一版给了「回归集标签」——单个任务里,哪些用例是「失败即阻塞发版」的核心用例。但标签**散落在各任务里**:测了 8 个功能,就有 8 份用例文件,回归用例埋在各自的 cases.json 里。用户下次发版想「把所有该跑的回归用例跑一遍」,没有一个地方能一次看到、一次跑完。

用户原话:**「我希望每一次测试任务跑完后,这个测试任务的回归测试用例都能放到回归用例库中。」**——要的是一个**跨任务汇集**的地方,让回归用例从「一次性标签」变成「持续积累的资产」,并且能整体重跑。

## 三个关键决策(用户拍板)

### 1. 入库范围:全部「回归测试」标签用例,不看本次结果
不是「只入库跑通过的」。理由:回归用例**失败恰恰是下次发版最该重跑监控的**——如果只沉淀通过的,失败的回归用例反而被漏掉,与「回归 = 盯住会阻塞发版的东西」的初衷相悖。库定义的是「**该重跑哪些**」,与「这次通没通过」解耦。

### 2. 入库时机:用例设计完成后,不等执行
用户原始说「跑完后」,澄清时改成**「用例设计完过后」**。这更准也更自洽:既然入库不看执行结果(决策 1),用例一设计好、标签一打上,就能沉淀——不必等到执行甚至报告。技术上也更干净:后端在用例设计步流结束时自动 upsert,不依赖用户是否真去跑。

### 3. 本轮就做「一键重跑」
用户明确要「连把库当跨任务套件一键重跑一起做」。这是库的**价值闭环**:光沉淀不能跑,库只是个清单;能整体重跑,它才成为「发版前跑一遍回归」的实际抓手。

## 为什么这样设计而不是别的

### upsert by 来源任务,而非追加
同一任务会反复跑、反复改用例。若每次入库都追加,库会迅速被重复用例淹没。改成「**某任务再次入库=覆盖它上次的全部贡献**」:库永远反映各任务**当前**的回归集,改了标签(加/减)库自动同步。代价是实现上要按来源任务删旧再插新,但换来库永远干净、可信。

### 项目级,不是全局
一个项目 = 一个被测系统。库落在项目的 `AI_LabTest/` 下、每项目独立。这样重跑时能直接复用项目已配置的被测环境(`environments.json`)——跨项目聚合会立刻遇到「打哪个地址、用哪套账号」的死结。

### 重跑复用现有执行机器,不另造
「一键重跑」没有新写一行执行逻辑:把库聚合成一个用保留任务名(`回归用例库`)的普通用例集,然后走**完全相同的** `/api/test/run` 执行+报告流程。好处是可达性闸门、登录态注入、录像、四态归约、回归集红线——全部免费继承。跨任务用例 id 会撞号(两个任务都有 TC-001),用「来源任务::原ID」命名空间化解决,避免执行结果串号。

### 入口放项目头,不放任务详情
库是项目级资产,最初误放在任务详情头(要先选中某个任务才够得着),CDP 实测时立刻发现别扭——改到项目看板头(与「环境配置/新建任务」同排),不选任务就能进库。**入口位置要匹配数据的作用域**。

### 自动入库失败必须静默
入库是「增强」,不是「主线」。它绝不能因为写库出错就拖垮「出用例」这件用户真正要的事——所以全链路 fire-and-forget、失败静默,和操作审计同一策略。

## 已知局限与未来方向

- **真实 AI 打标质量未验证**:库入库的「是不是回归用例」完全取决于上一层 AI 按「失败即阻塞」标准打的 `tags`。这层判断的准确度,dev 无凭证跑不了真实 AI,需打包登录后终验。库本身只是忠实汇集,不替 AI 判断。
- **重跑报告未按来源任务分组**:目前按用例呈现,溯源信息(idMap)已具备,可后续在报告里按来源任务归组,让「哪个功能的回归挂了」一眼可见。
- **导出**:库暂只支持查看+移除,未做 xlsx 导出;真正的价值也不在导出,而在「一键重跑」。
- **积累越久越值钱,也越需要维护**:库会随项目持续变大。未来可能需要「按上次重跑时间排序」「标记长期不过的用例」等治理手段,避免库变成一个没人跑的僵尸清单。

# v2 一期：从「能重跑」到「可信的发版回归」（2026-07-10）

> 技术实现见 [docs/handover/regression-library.md](../handover/regression-library.md) v2 章节;竞品对标与决策全文见 [docs/research/regression-library-v2-benchmark-proposal.md](../research/regression-library-v2-benchmark-proposal.md)

## 为什么有 v2:v1 的三个「回答不了」

v1 交付后用户要求对标市场成熟回归测试产品(TestRail/Xray/MeterSphere/Azure Test Plans)。多代理竞品调研 + 独立批判后,暴露 v1 回答不了的三个问题:**这轮比上轮多挂了什么**(同环境重跑覆盖上一轮,历史即焚);**哪个功能的回归挂了**(报告按命名空间 runId 平铺);**能不能只跑一部分**(永远全量,AI 执行烧时间烧 token)。

## 关键决策(用户拍板)

1. **模块不做独立功能**——不建模块树。`module` 只是用例字段,检索与套件条件消费它;「按范围圈选」统一由套件承担,不引入第二套组织概念。
2. **套件提至一期**——用户认定套件是核心。技术上也自洽:发起弹窗本来就要重做,一期不做套件、二期回头再改一遍弹窗是返工;套件只依赖库本身,零轮次数据依赖。
3. **轮次原子性**——一轮=一套件×一环境×一模式。多套件诉求用并集套件解决,未来高频再考虑「批次」容器(对齐 TestRail Plan 语义),不打破轮次原子性——否则套件交集去重后红线口径说不清。

## 为什么这样设计而不是别的

- **套件=保存的查询,不是文件夹**(Azure Query-based Suite/TestRail Dynamic Filter 的共识,也是 MeterSphere/禅道用户抱怨多年的缺失):查询套件存条件不存清单,新入库命中自动进入,零维护;静态套件留给精挑细选的发版集。**标签管进库,套件管圈跑**,两层各司其职。
- **快照是执行历史可信度的地基**:AI 高频改写用例,upsert 直接覆盖——没有快照,三周前报告里的 TC-003 会被今天的第 5 版张冠李戴。竞品铁律「执行记录必须绑定用例不可变副本」(TestRail Close 即快照)在 AI 场景从最佳实践升级为必需品。成本一次文件拷贝。
- **delta 用交集口径**:两轮套件可能不同,上一轮没跑到的用例不判「新增失败/已修复」——结论只能建立在实际执行过的范围上。复测轮不作 delta 基准,同理。
- **中断惰性收口**:桌面应用被随手关掉是常态,不依赖进程退出钩子;读侧发现 running 超 2h 视图归一 aborted,不回写(避免读放大)。
- **估算宁缺毋滥**:时长估算用近 3 个已收口轮的实测均值;无历史显式「首轮暂无估算」,不出瞎数。token 估算因无数据源明确不做,不放占位假数。
- **并发写用 seq 不用时间戳**:实测发现 updatedAt 毫秒粒度在同刻写入时失效(单测抓出),换单调写入序号。

## 批判环节改掉了什么(值得记的教训)

独立批判代理对综合方案的修正,多数进了实现:复测轮红线必须按合并口径(2/2 通过≠可发版,二期实现、数据结构一期预留 parentRoundId/mode);跨轮翻转≠flaky(版本在变,「挂了又修好」恰是回归正常工作的样子,终判须同版本重跑——三期);rev 字段级 diff 时间线降级(AI 是唯一改写者,快照对照已够,省 M 级工作量);pinned 含义落在当下(必跑白名单)而非为未来智能裁剪预留概念。

## 未来方向(按期)

二期:失败复测环(合并红线)、评审门禁(pending 曝光+存量回填 approved)、缺陷实体闭环、rev、手工结果兜底、xlsx 导出。三期:stats 逐用例历史→flaky(AI 就地复核终判)/连败/stale 队列、隔离区(带「隔离中 N 条未计入」强制曝光护栏)、AI 失败归因。远期差异化:变更驱动选例(桌面工具拿得到 git diff,TestRail 们结构性做不到)、用例自愈、语义去重。
