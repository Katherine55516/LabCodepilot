# 对话流空闲超时 — 产品思考

> 技术实现见 [docs/handover/stream-idle-timeout.md](../handover/stream-idle-timeout.md)
> 执行计划见 [docs/exec-plans/active/stream-idle-timeout-rework.md](../exec-plans/active/stream-idle-timeout-rework.md)

## 用户问题

同事反馈：对话「330 秒无响应就被自动掐断并停止」。根因是一个客户端空闲超时——连续 330s 收不到任何 SSE 事件就 abort 对话流。慢首包的国内 provider（百炼 qwen3.x-plus 等，后端排队、首包可能静默几分钟）首字节还没来就被当成「断了」误杀，用户被迫重开会话。

## 关键洞察：心跳「不能识别」，只能「豁免」

最初的直觉修复（也是 issue B-019 里写的方向）是「补一个 15s 心跳」。深入分析后否决了它：

> **心跳无法区分「在合法地慢等」与「已经卡死但连接还在」**——这两种情况在所有可观测层面完全相同：同一个开着的 socket、零字节流动。

所以「补无条件心跳」不是在「识别」慢等，而是在「无差别豁免」所有还连着的情况——包括真卡死。后果是客户端唯一的卡死兜底被废掉：上游真卡死（连着但永不产出）时计时器永不触发，UI 永久转圈、既不完成也不报错。我们把这个判断固化在决策日志里，避免后人重蹈。

## 为什么这样设计：按「实质内容」计时

既然「慢」和「死」在纯静默下无法区分，就换一个计时口径——不数「距上次**任何**信号」，而数「距上次**真实产出**」：

- keep_alive / 状态心跳只代表「还连着」，**不**重置掐断计时；
- 只有模型真实内容（文本/思考/工具活动）才重置；
- 于是慢首包/慢思考只要**最终吐出内容**就不会被误杀；而「连着但永远不产出」的真卡死，仍会在一个**给得很宽的硬上限**后被兜住。

这是对「既不误杀、又仍能兜住卡死」这对矛盾诉求能给出的最优解：不是真正的「识别」（物理上做不到），而是用「有没有真实进展」这个唯一可观测的差异作为判据。

## 取舍

- **990s（16.5min）的阈值**：故意给得很宽。它须大于最坏的合法「无实质内容间隙」（慢首包 + 上下文压缩重试），也要大于 300s 的权限自动拒绝。代价是真卡死要等满阈值才报错——这是「不误杀优先」的自觉选择。终值待线上实测慢首包数据再校准。
- **先止血再治本**：先把 330s 提到 990s（保留兜底、只推迟误杀）顶住线上，再上「按实质内容计时」的治本。两步都不牺牲兜底。
- **服务端补心跳降为可选**：一旦客户端不再用 keep_alive 做判据，「服务端 SDK 路径补心跳」就**不再影响是否误杀**，只剩「长首包期间保持连接温热 + UI 知道仍连着」的体验价值，故降为可选、暂缓。
- **工具进度算「实质」**：长工具靠进度 ping 续命不被误杀，且单工具另有 300s 工具超时把关，不会与本机制打架。
- **权限等待暂停计时**：模型阻塞在用户侧不算卡死，且权限本身有 300s 自动拒绝兜底。

## 已知局限与未来方向

- 「连着但永不产出」的真卡死仍需等满 990s 才报错（无信号可更快区分）。若要更快，可叠一个短「连接 idle」计时器（keep_alive 重置）专门抓「连接死但 fetch 未报错」的罕见情形——更复杂、收益有限，暂不做。
- 阈值目前是全局常量；未来可做成 provider 级可配置（对个别异常慢后端单独放宽）。
- UI 目前靠既有的渐进式「Preparing response…」避免完全冻结；可选增强一个「模型响应较慢、仍在等待（已等 N 分钟）」的首包久等提示（Phase 3）。
