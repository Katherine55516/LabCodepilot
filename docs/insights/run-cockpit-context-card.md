# RunCockpit 上下文用量卡片 — 产品思考

> 技术实现见 [docs/handover/run-cockpit-context-card.md](../handover/run-cockpit-context-card.md)
> 相关：上下文压缩的产品思考见 [context-management.md](./context-management.md)

## 解决什么用户问题

旧的"百分比圆环"只回答一个问题：**上下文用了百分之几**。但用户真正关心的往往是后续问题：

- 还能聊多久？（总量 / 已用 / 剩余）
- 这些 token 花在哪了？（是历史对话堆积，还是缓存？）
- 我现在用的是哪个模型、什么权限、花了多少钱？

圆环把这些信息压成一个色环，用户要么看不到，要么要去别处找。新卡片把"本次运行"的全貌收进一个点击即达的面板：**用量构成 + 运行配置 + 花费**一屏可见。

## 为什么是"迷你点阵 + 展开卡片"这个形态

- **触发器要轻**：常驻输入框右下角，不能抢注意力。迷你点阵（10 格）比圆环信息量更高——它本身就预告了"构成"这件事（不同颜色的格子），点开是顺理成章的深入。
- **点阵优于进度条**：进度条只能表达"满了多少"，点阵能用**颜色分段**表达"由什么组成"，与展开后的明细列表是同一套视觉语言，认知连贯。
- **展开才加载**：弹窗内容（模型目录 fetch、明细计算）只在用户第一次点开时才挂载（`next/dynamic` + Radix 仅 open 时挂子树），聊天首屏零成本。

## 诚实数据原则（最关键的取舍）

源项目的卡片能显示「工具 / 规则 / MCP / Skills」等逐类 token，因为它有运行时记账链路。**本项目后端暂不上报这些**（`token_usage` 只有 input/output/cache/cost）。

面对这个差距有三个选择，我们选了**诚实实现**：

- ❌ 估算（用 SDK 初始化的 system prompt / tools 列表猜 token）——源规格记录过踩坑史：早期用固定值喂假数据，导致用户发"你好"也显示"Skills 1.5K"。**假数据比没有更糟**，它会侵蚀用户对整个数字的信任。
- ❌ 先做后端精确记账再上线——工作量大、依赖 SDK 是否暴露这些细分（很可能拿不到），会无限期阻塞一个本可立即交付的可视化。
- ✅ **按现有真实数据渲染**：能算的（对话历史、缓存、真实费用）精确显示，算不出的（工具/规则/MCP）显示 0 并**自动隐藏**。代码结构预留 `compiler` 入参，后端将来能上报时一行接通即点亮——不返工。

所以本项目卡片是目标形态的**真子集**：形态、点阵、对话历史/缓存、本次运行、真实费用全部一致，只是少了三行需要后端支撑的明细。用户看到的每个数字都为真。

## 为什么用 `cost_usd` 而不是 tokenlens

源项目用 `tokenlens` 按模型单价算钱。本项目的 `token_usage` 里已经带了 SDK 回报的 `cost_usd`（真实结算值）——直接用它**更准**（含缓存折扣、阶梯计价等 SDK 已算好的因素）、**无需新依赖**、**不挑模型**（第三方模型 tokenlens 未必有价表，但 SDK 给了真实值）。顺带省掉了源规格里为隔离 tokenlens 重依赖而存在的一整层 `ContextProvider`。

## 与上下文压缩的关系

本卡片是**展示层**，不触碰 [context-management](./context-management.md) 的压缩逻辑。两者互补：压缩系统在 80% 阈值自动 compact，卡片让用户**看见**自己离阈值还有多远、构成是什么——把原本隐式的系统行为变得可解释。

## 已知局限与未来方向

- **工具/规则/MCP 三行**：依赖后端运行时记账，当前隐藏。这是最大的待补项，也是设计时刻意留好接口的地方。
- **pending 预估**：输入框挂了 @提及/附件时，理论上可在触发器显示 `+10K` 预告下一轮增量。入参已预留，链路未接。
- **多服务商"问题块"**：源规格在卡片底部会提示"服务商/CLI 有问题 → 前往修复"。本项目第一期未做（图中也没有），可按需补。
