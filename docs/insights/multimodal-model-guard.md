# 多模态模型标识 + 上传拦截 — 产品思考

> 技术实现见 [docs/handover/multimodal-model-guard.md](../handover/multimodal-model-guard.md)

## 用户问题

后台下发的模型有的支持多模态（Kimi-K2.6、Qwen3.6-Plus），有的纯文本。用户遇到两个体验断点：

1. **看不出哪个能传图**：模型列表只有名字，用户得靠记忆或试错。
2. **传了图才报错**：选了非多模态模型上传图片，请求发到模型端直接报错——用户既不知道为什么失败，也不知道"换个模型就行"。

错误发生在最末端（模型 API 拒绝），离用户的操作（点上传）很远，归因成本高。本功能把约束**前移到上传那一刻**，并在列表里**提前标注能力**，让用户在选择和操作两个节点都有清晰反馈。

## 设计权衡

### 为什么用 description 关键词判定，而不是加结构化字段

后台 `ModelConfig` 没有显式的 `multimodal: boolean`，但 description 文案里通常会写"多模态"。两条路：
- **A. 推动后台加结构化 capability 字段** → 最干净，但跨团队、跨版本，周期长，且老配置仍缺字段。
- **B. 前端用 description 含「多模态」判定** → 零后端改动、零 DB 迁移（description 已落 `notes` 列），当天可上线。

选 B。它是"利用现有数据的务实解"，代价是依赖文案规范（description 必须写"多模态"）。这是一个**可演进**的决定：未来后台若提供结构化字段，把判定函数从"关键词匹配"换成"读字段"即可，调用方（hook → 选择器 + 拦截）不用动。判定规则被收敛在 `src/lib/model-multimodal.ts` 一处纯函数，正是为这次演进留的缝。

### 为什么"无法判断时放行"而不是"拦截"

判定只对 managed 模型可靠（有 description）。本地/BYOK provider、本地开发无登录数据时，description 为空——此时：
- **拦截**（严格）：会误伤本地接入的多模态模型、阻断本地开发调试。
- **放行**（宽松）：只拦"能证明非多模态的 managed 模型"，其余不管。

选放行。这条功能的目标是**消除一个确定的错误**（managed 非多模态模型传图报错），不是做通用能力门禁。宁可漏拦未知模型（大不了回到原来的末端报错），也不要误拦正常模型——**新增约束不应让已能用的场景变不能用**。

### 为什么 image-gen 模式要绕过

CodePilot 的图片生成模式里，用户上传的图是**参考图、喂给图像模型**的，跟当前对话模型是否多模态无关。若不绕过，开了 image-gen 还选着文本对话模型时传参考图会被误拦。所以拦截显式加了 `!imageGen.state.enabled` 条件——**约束要精确匹配它针对的场景，不能殃及无关流程**。

### 为什么拦截做成"组件通用校验 + 业务侧 policy"

上传汇聚点在共享组件 `PromptInput` 里。两种做法：
- 让 PromptInput 直接认识"多模态"——快，但把业务概念塞进通用组件，污染复用性。
- 给 PromptInput 加一个**通用** `validateFile` 钩子，"多模态 policy"留在 MessageInput。

选后者。PromptInput 只知道"有人给了我一个文件校验器"，不知道多模态为何物；以后任何"按条件拒某类文件"的需求都能复用这个钩子。**通用组件只暴露机制，不内置策略。**

## 已知局限 / 未来方向

- 判定依赖 description 文案含「多模态」，后台改文案口径会影响判定 → 长期应迁到结构化 capability 字段。
- 目前只在"上传时"拦截 + "列表里"标注；未来可在触发按钮折叠态也显示能力标识，或在切到非多模态模型且已有图片附件时主动提示。
- 媒体类型目前按 MIME 前缀（image/audio/video）粗粒度判定，够用；若将来要区分"支持图不支持音"等细分能力，需要更细的 capability 模型。
