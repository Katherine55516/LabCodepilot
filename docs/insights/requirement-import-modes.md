# 导入需求：保留原文 + 二选一（产品思考）

> 技术实现见 [docs/handover/requirement-import-modes.md](../handover/requirement-import-modes.md)

## 解决什么用户问题

测试同学手里往往**已经有一份需求文档**（PRD、Word、md）。改造前，导入需求后要么直接用它、要么让 AI 归一，但两者共用一个 `{任务}-需求.md`：

- 一旦点了 AI 归一，**原始文档就被覆盖没了**——用户失去了「回到原文」的能力，也不敢轻易点 AI。
- 「用我自己的文档」和「让 AI 帮我整理」是两种**真实且不同**的意图，却没有显式入口，全靠用户猜「跑不跑 AI」，容易误操作。

用户的诉求很直接：**保留我的原始文档，让我自己选是让 AI 归一，还是直接拿我的文档去出用例。**

## 为什么这样设计

**选择放在任务内的需求分析节点，而不是新建弹窗。** 用户原话是「到任务中用户可以选择」。导入是「给料」，处理方式是「加工决策」——把决策留在能看到原文预览、能反复权衡的节点里，比在新建弹窗里预先押注更自然。弹窗保持极简，只管导入。

**原始文档按原样保留，不转 md。** 用户明确「就保留原始文档，不需要转换成 md」。所以 `{任务}-需求-原始.{ext}` 存的是上传件的**原始字节**（可下载、可存档、可追溯），而不是又生成一份「原文的 md 副本」。`{任务}-需求.md` 这个名字被让给 AI 归一产物——只有选「生成 md」时才出现，语义干净：md = AI 的东西，原始 = 用户的东西。

**docx 的「必经一次抽取」如实告知，而不是假装能直接读。** 用户质疑「聊天框能直接传 docx 分析，为什么这里不行」。答案是诚实的：需求/用例步用 Agent SDK 的本地 `Read` 工具，读不了二进制 docx；聊天产品那套是服务端文档抽取管线，两条不同的路。所以我们保留原始 `.docx`，同时用 mammoth 抽一份文本喂 AI——docx 体验和 md 一致，但不粉饰「AI 直接读了你的 docx」这件没发生的事。

**无人值守时停下来等用户选，而不是替他默认。** 批量「运行任务」会自动批准门控往下跑，但导入需求的处理方式是个**有信息含量的决策**（要不要花时间让 AI 归一、要不要保留 md）。与其替用户押一个默认（generate-md 更慢、use-original 可能漏结构化），不如在这个岔口停下等他选一次——这也是用户选的（「停下来等我选」）。

## 关键取舍

- **用例设计始终读一个「需求来源」变量，而非硬编码 需求.md。** generate-md 指向 `需求.md`，use-original 指向原文/抽取文本。代价是 prompt 要多一个来源参数；收益是两种模式复用同一条用例链路、后端只切一个路径。
- **use-original 直喂原文时，原文常无 REQ-ID。** 于是在 cases prompt 里追加 `USER_UPLOAD` 提示：就地给每条需求编 `REQ-NNN`，保住 TC↔REQ 追溯和需求覆盖矩阵。这是「让用户少加工」与「保住用例质量口径」之间的平衡。
- **选择即人工接管（退出批量自动）。** 一旦用户在节点做了选择，该任务转为按正常门控推进，而不是继续无人值守自动跑到报告。取舍：可预测 > 全自动；用户已经在动手了，就把控制权交回给他。

## 第二轮迭代：预览要的是「我的文档」，不是「你解析出来的东西」

上线后用户第一反应是：点「预览原始文档」看到的还是**解析后的纯文本**——标题、表格、缩进全没了，「这不是我的文档」。这验证了一个朴素的产品判断：**「保留原始文档」的价值最终要靠「看到原始文档」来兑现**，字节级存了但展示的是抽取文本，用户感知不到「保留」。

恰好应用的文件树预览体系已建好 docx/pdf 富渲染（doc-preview Phase 1-3），于是把测试工作台接上：docx 原件用 DocxViewer 按原版式渲染，另配「用系统应用打开」（Word/WPS）做保真兜底——docx-preview 对复杂表格/图片的渲染可能有出入，给用户一条 100% 保真的退路，成本只是一个按钮（Electron shell.openPath 现成）。

同轮顺手修掉了**打包版 docx 导入失败**的根因（mammoth 未做 standalone 依赖收录，照 xlsx 前科的成熟修法处理）——否则「保留原文 + 富预览」在打包版上游就断了。

PDF 导入这轮问过用户，答复「先不处理」——扫描件（无文字层）的成本/体验问题让它后置，入口先不开。

## 已知局限与未来方向

- **PDF 需求暂不支持**（用户明确本轮不做）：Agent SDK 的 Read 能直接读 PDF、PdfViewer 也现成，未来接入是低成本增量；主要待决的是扫描件的提示/拦截策略。
- **generate-md 的再生成是全量重跑**：每次从原文归一，不做增量 diff。原文很大时可考虑分段/增量。
- **批量 + 导入需求会停在待选择**：这是刻意的（Q3），但意味着大批量里混入导入需求任务时，需要人来一个个选。未来可给「本批统一走某模式」的批量默认选项。
- **docx 富预览依赖 docx-preview 的渲染保真度**：复杂版式（多层嵌套表格、艺术字）可能有出入，「用系统应用打开」是兜底。
