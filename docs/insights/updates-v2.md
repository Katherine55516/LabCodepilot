# 自动更新（研发平台 V2）— 产品思考

> 技术实现见 [docs/handover/updates-v2.md](../handover/updates-v2.md)

## 解决什么问题

应用从开源 fork 演进为公司自有的「AI Native Lab」客户端后，旧的更新机制有两个硬伤：

1. **检查的是别人的仓库**：更新检查写死查上游 `op7418/CodePilot` 的 GitHub Releases，而构建实际发布到自有仓库。等于拿上游的版本号和安装包提示自家用户——版本对不上、点下载下到的是别人的包。
2. **"自动更新"其实从未实现**：`electron/updater.ts` 是个故意留的空壳，preload 也没暴露更新桥，所谓 native 自动更新是永不执行的死代码。用户感知到的只有"弹个窗、跳浏览器自己下"。

公司侧把更新做成了和登录/模型配置同一套服务（研发平台 V2 接口 + CDN 分发），客户端需要对接成**真·应用内自动更新**：检查 → 下载 → 校验 → 安装，全程在应用内完成。

## 关键设计决策与理由

**为什么不用 electron-updater。** V2 接口返回的是「CDN 直链 + sha256 + 文件大小」的自定义 JSON，不是 electron-updater 期望的 `latest.yml`/blockmap feed 格式。强行适配要再造一层 feed，不如直接在主进程自己下载+校验+安装，更贴合接口、更可控。

**为什么放主进程。** 登录 token 在主进程且**永不过 IPC**；下载落盘、sha256 校验、拉起安装器、退出重启也只能在主进程做。而渲染层的更新弹窗/进度/重启按钮早就是为"主进程驱动"设计的，复用度极高——这是改造成本远低于预期的原因：真正缺的是主进程那一段。

**复用登录体系，不另造轮子。** base URL 用登录的 `getBackendBase()`、认证用登录的 `apiRequest()`（自动注入 Bearer）。更新检查本质就是登录体系里 `fetchUsage()`（查额度）的克隆，零新增鉴权代码路径。

**检查只提示、点击才下（check-only）。** 起初倾向"后台自动下载"（参考的两个方案都这么做，配合复用可做到秒装）。但用户最终选择只提示、点击才下——核心顾虑是移动网络/计流量下自动下 100MB+ 安装包不友好。这是一个明确的"省流量优先于极致顺滑"的产品取舍。跨会话复用（pending）仍保留，所以"点了下载但没装、关掉重开"不会重下。

**避免重下与自动安装借鉴姊妹项目实战方案。** 固定文件名 + 同 hash 复用 + `pending-update.json` 跨会话三层避免重下、sha256 三处校验；Windows 用 `shell.openPath`（等价双击，非 `/S` 静默——历史上 `/S` spawn 被拒提权、PowerShell 被国内杀软拦）、macOS 写脱离脚本 `hdiutil`+`ditto` 覆盖。这些都是别人踩过坑沉淀下来的，直接内化避免重走弯路。

**对照 Trae 方案的取舍。** Trae（Inno Setup + electron-updater generic feed + 静默安装 + sha512）是另一套技术栈，不照搬；但它的「安装前进程优雅退出」点醒了一个真坑——本应用进程树更重（内置 Next 服务 + ~230MB 的 `claude.exe` SDK 子进程都在安装目录里），Windows 覆盖安装会被未退子进程锁文件。好在现有 `killServer()` 已做 `taskkill /T` 连根杀，正好覆盖。另外吸收了它的「后台预下载（最终被 check-only 否决）/重定向处理/Windows 签名提醒」。

**强制升级阻断而非提醒。** `must_upgrade=true` 时弹窗不可关、无"稍后"、隐藏关闭 X，只能「立即升级」或「退出应用」，配合模态遮罩阻断主界面——这是"必须升级才能用"的强约束，用于后台需要强制收敛旧版本的场景。

## 设计边界 / 已知局限

- **真实下载/安装无法在 dev 验证**：dev 没有 Electron 主进程，下载/安装是真 OS 操作，只能打包后验证；dev 阶段靠 CDP 注入 mock 验证渲染逻辑 + 纯函数单测。这是个诚实的边界，不是偷懒。
- **macOS 公证**：当前签名但未公证，ditto 就地覆盖不依赖公证机制本身，但下载包的 Gatekeeper/quarantine 真实行为需打包实测；遇拦截再评估去 quarantine 或开公证。
- **强制升级非"启动即硬阻断"**：弹窗在首检返回后出现（数秒窗口），未做到登录 gate 那种 boot 层硬门。若后续需要"未升级连界面都进不去"，可在 boot 阶段加门。
- **只服务 win-x64 / mac-arm64**：Intel mac 暂不考虑；linux 不在更新范围。
- **服务端 ops（上传 CDN + 登记版本含 sha256/size）由运营手动负责**，客户端只按接口判定 + 下载安装。
- **版本号字符串精确比较**：客户端 `current` 必须与后台录入版本号完全一致；客户端仅在 pending 复用/离线兜底处用 semver 兜底，不改变升级判定。

## 未来可能的方向

- 真正的"启动即强制"boot 门（强制升级时连主界面都不加载）。
- channel（beta/alpha 内测通道）接 UI 开关——当前固定 stable，参数位已预留。
- 下载断点续传 / 差量更新（需服务端支持）。
- Windows 代码签名补齐（免 SmartScreen，提升升级顺滑度）。
- 失败回滚（装前备份旧目录）作为健壮性增强。
