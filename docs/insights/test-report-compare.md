# 报告多版本对比：为什么它是「回归基线」的主场

> 技术实现见 [docs/handover/test-report-compare.md](../handover/test-report-compare.md)
> 上游方案见 [docs/research/framework-flow-test-integration.md](../research/framework-flow-test-integration.md) §四第三批

## 解决的用户问题：单次报告答不了「有没有退步」

一次测试报告告诉你「这次有几条 pass / fail」。但回归测试真正要回答的是一个**跨次**的问题：**这次相对上次，哪些用例从通过变成了失败？通过率是涨了还是跌了？** 单份报告无能为力——而这恰恰是「改了代码后会不会弄坏原来好的功能」这个最常见担忧的答案。

此前 `run.json` 是覆盖式的（重跑即覆盖、无历史），所以这个问题在平台里根本问不出来。报告多版本对比补上了这一环：留存历史快照 + 选两版本 diff。

## 这正是 oracle 双轴埋的伏笔兑现

在 [oracle 双轴的产品思考](./test-oracle-dual-rate.md)里写过一句话：

> 回归基线的正向价值还没用足。它本是「防回归」的基线，未来配合「报告多版本对比」，可以做「这次相对上次有没有回归」的 diff——那才是回归基线的主场。

这一批就是把那句话做实。回归基线用例（oracle = 现状锁定）在单次报告里只能说「现状已锁定」，看起来没什么用；但**它的全部意义在于「下一次还是不是这样」**。多版本对比让回归基线第一次有了用武之地——它锁定的现状，正是对比的基准线。

## 为什么对比要分双口径

对比沿用了报告的双口径（执行通过率 + 功能验证通过率），而且**功能验证通过率的变化才是真正的回归信号**：

- 回归基线用例永远 pass（它照抄现状），把它们算进通过率，通过率会被"垫高"且几乎不波动——用它做对比，回归信号被稀释。
- 功能验证通过率排除了回归基线，它的下跌＝真有功能退步。所以对比卡片把「功能验证通过率」放在第一位。

这就是为什么双口径不是报告阶段的一次性设计，而是贯穿到对比：两个阶段共用同一套 `funcCounts`，口径一致才能跨次比较。

## 几个设计取舍

- **文件快照，不上数据库**。沿用 framework 的 `.history/` 思路（SHA-1 去重、文件名即时间序）。理由：run.json 本就是文件产物，历史跟着产物走最自然；跨设备/DB 持久化是更大的工程，当前价值不值那个成本。重跑无变化时 SHA-1 去重，不堆重复快照。
- **默认对比「上一版 vs 最新」**。打开即是最常想看的对比（刚跑完想知道相对上次的变化），同时允许手选任意两版本。
- **diff 放纯函数、前端跑**。版本切换是高频交互，让它本地算（后端只给数据），切版本零延迟。
- **只做对比，没做同批的另外三项**。第三批原有 4 项（对比 / 产物行级 diff / ETA / 并发），用户只选了对比。这是「按需」原则的体现——并发对「一次跑一个任务」的内嵌形态价值低；ETA、行级 diff 是体验锦上添花，可后续按需补（行级 diff 能复用这批的快照机制）。

## 已知局限与未来方向

- **历史要靠真实多次执行积累**。本批是 mock 验证的逻辑正确性；真实回归曲线需要在有模型的环境里跑 ≥2 次才显现。
- **快照只增不删**。长期会堆积，未来可加「保留最近 N 份 / 按时间归档」。
- **用例 id 是对比的锚点**。重构用例 id 会让对比失真——但这本就是 id 作为「用例稳定标识」的应有之义，正常迭代不受影响。
- **下一步可做的**：产物（需求/用例）的行级 diff（看需求改了哪几行）、回归趋势折线（多次通过率连成曲线）——都建立在这批的历史快照之上。
