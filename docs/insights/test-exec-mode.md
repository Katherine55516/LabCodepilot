# 测试执行方式选择 + 执行前确认弹窗（产品思考）

> 技术实现见 [docs/handover/test-exec-mode.md](../handover/test-exec-mode.md)

## 解决什么用户问题

AI 驱动的「测试执行」此前**只能后台无头跑**：用户看不到浏览器在点什么、跳到哪、为什么判这个
四态。两类诉求被堵住：

1. **观察 / 演示 / 调试**：第一次跑一个项目，用户想亲眼看 AI 怎么操作真实页面——尤其用例
   judged 成 fail/blocked 时，「肉眼看一遍」比读日志快得多，也更信得过。
2. **被测地址不确定**：local 模式下被测前端常是本机任意端口（`localhost:5173/siway/`、
   `localhost:3001`…），跑之前用户想**先确认地址、点一下测连通**，而不是白跑一整轮才发现 404。

## 为什么这样设计

**把「选模式」和「确认地址 + 测连通」合并到一个执行前弹窗**，而不是塞进设置页或顶部工具栏：

- 这三件事都是「按下执行那一刻」才关心的决定，放在执行入口最贴近心智；设置页太远、容易忘。
- 对齐原 ai-lab-test 框架规则 `§0.4 选执行模式` + `§0.3 被测地址探活`——本就是「执行前」的两道关，
  桌面应用此前把它们藏进了引擎默认值，这次把决定权还给用户。

**默认仍是后台无头**：绝大多数回归 / 批量场景要的是快和四态结果，不是看热闹。有头是「想看时
才开」的增量能力，默认零回归。选择**持久化**，所以用户改一次后续都跟随，不必每次点。

**「运行任务」全流水线不二次弹窗**：流水线是「一键跑完、自动门控」的心智，中途弹模态打断它会
很反直觉。它复用上次选择即可；弹窗只服务「我现在就想跑这一步测试执行」的精确入口。

**测试连接放服务端探活**：被测前端（dev server）通常不带 CORS 头，浏览器端 fetch 跨源会被拦成
opaque，分不清「真不可达」还是「被 CORS 拒」。放 Next 服务端发请求无同源限制，能给出真实可达性
+ 状态码——这正是用户点「测试连接」想要的确定答案。任意 HTTP 响应都算可达：服务在监听就别拦。

## 关键取舍：打包态有头要不要依赖系统 Chrome

随包只装了 `chrome-headless-shell`（只能无头、体积小），没带完整 chromium。于是有头运行在
打包版有三条路：

| 方案 | 代价 | 取舍 |
|---|---|---|
| **走系统 Chrome 通道**（选用） | 依赖用户机器装了 Google Chrome；没装则有头失败 | 零体积增加，多数用户有 Chrome；无头不受影响。**选它** |
| 随包完整 chromium | 安装包 +~150MB | 为一个非默认能力背全量浏览器，不值 |
| 有头时报错引导用户装 Chrome | 体验有断点 | 作为「未装 Chrome」的兜底提示，后续补 |

诚实的边界：**有头是 best-effort**。dev 态用本机 chromium 一定能弹；打包态弹的是用户的系统
Chrome。这对「观察/演示」场景完全够用（用户本就在自己机器上看），不追求「保证任意环境都能有头」。

## 已知局限 & 未来方向

- 打包态未装 Chrome 时有头会失败，目前只在执行流里暴露错误——后续可在弹窗里**预探测 Chrome
  可用性**并禁用有头选项 + 给一行提示，把失败前移。
- 有头目前不带 `slowMo`（原框架 headed project 配了 1s 慢放便于观察）。若用户反馈「太快看不清」，
  可在有头模式注入慢放。
- 被测链接覆盖是一次性的、不落 `environments.json`。若用户反复手填同一个 local 端口，未来可考虑
  「记住为该任务的 local 地址」。
